# Phase 11.1: DOCX Template Style Extraction — Context

**Gathered:** 2026-04-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Apply the org's uploaded DOCX template styles to exported proposals. At export time, fetch the org's template from Supabase Storage, extract `word/styles.xml`, `word/theme/theme1.xml`, and `word/numbering.xml` from it, and inject them into the generated DOCX via a JSZip XML swap. Output matches org branding and formatting.

**Not in this phase:**
- Headers, footers, page-layout matching (REQ-10.4c — separate phase)
- Export to PowerPoint (backlog)

</domain>

<decisions>
## Implementation Decisions

### Style Injection Approach
- **D-01:** XML swap via JSZip. Generate the DOCX first with the `docx` package, then post-process the zip: replace `word/styles.xml`, `word/theme/theme1.xml`, and `word/numbering.xml` with the equivalents extracted from the org's template DOCX. Styles-only swap is naive — theme carries colors/fonts that styles reference, numbering carries list definitions.
- **D-02:** Styles from `styles.xml` reference the theme via `word/theme/theme1.xml`. Both must be swapped together or the color/font references break silently.
- **D-03:** Implement as an isolated utility function: `applyTemplateStyles(generated: Blob, template: Blob): Promise<Blob>`. Any failure (missing `styles.xml`, malformed zip, etc.) returns the original generated DOCX unchanged and logs the error. The export pipeline must never fail due to a styling problem.

### Style Name Inspection (Upload-Time)
- **D-04:** Run style name inspection in the **existing Edge Function** that processes template uploads. The Edge Function already has the file open — adding inspection is essentially free. Client-side re-inspection on every Settings page load would mean refetching and decompressing for all templates unnecessarily.
- **D-05:** Persist inspection result as `style_inspection jsonb` on the `templates` table. Store which standard Word style names were found and which are missing (e.g., `{ found: ["Heading 1", "Normal"], missing: ["Heading 2", "Heading 3"] }`). This enables the UI to render specific actionable warnings rather than generic ones.
- **D-06:** The column is nullable. If `styles.xml` is malformed or missing, the inspection fails gracefully without breaking the upload — set `style_inspection` to `null` (unknown state), not a false positive.
- **D-07:** Warning surfaces in **Settings → Templates only** — not at export time. The upload context is when the user can act on it (they have the file, can fix it in Word, or swap it). Export-time re-surfacing creates a sync-bug surface area with no benefit since the inspection result is already in Settings.
- **D-08:** Warning must be specific and actionable: name which styles are missing ("Heading 3 style not found"), state the consequence ("headings at that level will use default formatting"), and link to a how-to-fix guide. Vague warnings get dismissed; specific ones get fixed.

### Export-Time Template Fetch and Swap
- **D-09:** Client-side. The generated DOCX is already in the browser. The template is fetchable via a Supabase Storage signed URL. JSZip handles sub-10MB files in milliseconds. No server resources, secrets, or auditable artifacts required — Edge Function overhead is not justified here.
- **D-10:** `ProposalDetail.tsx` currently fetches only `name` from the `templates` table. Extend the query to also fetch `file_path` and `source` so the export flow knows whether a DOCX template is available and where to fetch it.
- **D-11:** Only templates with `source = 'uploaded'` and a `.docx` extension in `file_path` are eligible for style extraction. PDF templates and prebuilt templates have no `styles.xml` to extract.

### Fallback When No DOCX Template
- **D-12:** "No template uploaded" is the baseline state for most users — not a degraded state. Export proceeds with Phase 11's built-in Calibri defaults and produces a professional document. No warning shown.
- **D-13:** "Template uploaded but not a DOCX" (e.g., PDF) or "template failed style inspection" are handled by the upload-time inspection in Settings → Templates. Do not re-surface these at export time.
- **D-14:** Add a **one-time, dismissible discoverability nudge** shown post-export to users who have never engaged with the templates feature. Promotional voice, not error voice: "Want exports to match your firm's branding? Upload a template in Settings." Shown once per user, does not gate the export.

### Template File Size Cap
- **D-15:** Hard cap of **10MB** on template uploads in `TemplatesTab.tsx`. JSZip on a modern browser handles ~10MB comfortably; 50MB is multiple seconds and noticeable memory pressure on lower-end devices. CRO templates are almost always under 5MB.
- **D-16:** Hard reject at upload time, not a soft warning. A degraded export at the end of a long workflow is worse than an upload-time rejection with clear guidance.
- **D-17:** Rejection message must be specific and actionable: show the actual file size, name the most likely cause ("large embedded images often cause this"), and tell the user what to do ("try compressing images in Word before re-uploading").
- **D-18:** Do NOT match the 50MB document upload limit. Documents and templates have different processing paths and different downstream costs. The "consistency" argument does not apply when the artifacts are functionally different.

### Claude's Discretion
- Exact naming of the `style_inspection` JSONB schema keys (beyond the shape described above)
- Whether to fetch the template DOCX eagerly at page load or lazily at export click (lazy is simpler and acceptable given the one-time-per-export cost)
- Signed URL TTL for the template fetch

</decisions>

<specifics>
## Specific Ideas

- "Swap styles + theme + numbering — not just styles alone. Styles reference theme colors/fonts; lists reference numbering.xml."
- "The real cap is 'the largest template that can be swapped client-side without the user noticing.' JSZip on a modern browser handles ~10MB in a few hundred ms; 50MB is multiple seconds."
- "Reject 'match the 50MB document limit' reasoning. Documents and templates have different processing paths and different downstream costs."
- "The inspection answers a question about the template, not about the export. Templates don't change between exports — running the check every time wastes work and warns the user at the moment they can least act on it."
- "Hard reject at upload, not soft warning. The cost of a degraded export at the end of a long workflow is worse than the cost of an upload-time rejection."
- "The one-time discoverability nudge should use promotional voice, not error voice. Users who'd benefit from template uploading might not know it's a feature."

</specifics>

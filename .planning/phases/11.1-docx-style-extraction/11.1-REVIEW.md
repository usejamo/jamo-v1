# Phase 11.1: Code Review Report

**Reviewed:** 2026-04-29
**Depth:** standard
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Phase 11.1 adds DOCX style extraction: a ZIP-swap utility (`applyTemplateStyles`), a style-inspection step in the Edge Function, a `style_inspection` DB column, and UI wiring in `ProposalDetail` and `TemplatesTab`. The core extraction logic is solid and the D-03 fallback-on-error pattern is correctly applied throughout.

Four warnings were found, all in `supabase/functions/template-extract/index.ts`:

1. The `fileData` Blob is converted to an `ArrayBuffer` twice — once for mammoth (to parse HTML) and once for `inspectDocxStyles` — but the first `arrayBuffer()` call already drains the readable stream on some runtimes, meaning the second call may return an empty buffer and cause `inspectDocxStyles` to silently return `null` instead of actual results.
2. The `parseSectionsFromText` heuristic (`isShortNoPunct`) matches virtually every short line, producing false-positive "sections" from boilerplate text in PDFs.
3. The section insert at step 8 does not deduplicate by name; duplicate heading detections will insert multiple rows with the same `template_id`+`name`, with no DB constraint to prevent it.
4. The `TemplatesTab.test.tsx` test only validates a string message it constructs itself — it never exercises the actual component or function, so the size-cap logic is entirely untested.

Three info items round out the review.

## Warnings

### WR-01: Double `arrayBuffer()` call may drain the Blob stream before style inspection

**File:** `supabase/functions/template-extract/index.ts:253-304`

**Issue:** At step 5 (line 257), `fileData.arrayBuffer()` is called and the resulting buffer is passed to mammoth. At step 8.5 (line 302), `fileData.arrayBuffer()` is called a second time on the **same** `fileData` Blob to pass to `inspectDocxStyles`. In Deno's Fetch/Blob implementation the body stream is consumed on the first read; subsequent `arrayBuffer()` calls return an empty `ArrayBuffer`. This causes `JSZip.loadAsync` inside `inspectDocxStyles` to receive 0 bytes and throw, so `inspectDocxStyles` returns `null` and `style_inspection` is never populated for any DOCX — silently.

**Fix:** Store the buffer from the first call and reuse it:

```typescript
// step 5
const buffer = await fileData.arrayBuffer()
const result = await mammoth.convertToHtml({ buffer })
// ...

// step 8.5
if (ext === 'docx') {
  styleInspection = await inspectDocxStyles(buffer)  // reuse, don't re-call arrayBuffer()
}
```

### WR-02: `parseSectionsFromText` `isShortNoPunct` heuristic over-matches, polluting sections for PDF templates

**File:** `supabase/functions/template-extract/index.ts:38-40`

**Issue:** The condition `isShortNoPunct = trimmed.length < 80 && !/[.!?,;]$/.test(trimmed)` matches any line under 80 characters that does not end in sentence-terminal punctuation. This includes page headers, footer lines, table cell content, figure captions, and single-word lines like "or", "and", "Figure 1". On a typical PDF proposal template these rules can produce dozens of false sections, pushing the `sections.length >= 3` confidence threshold high while `wordCount` may also clear 200, meaning `isLowConfidence` stays `false` despite near-useless section data.

**Fix:** Require at least 3 words and exclude lines that are purely numeric or contain only stop-words:

```typescript
const wordCount = trimmed.split(/\s+/).length
const isShortNoPunct =
  trimmed.length < 80 &&
  wordCount >= 3 &&           // exclude single words and short fragments
  !/[.!?,;]$/.test(trimmed) &&
  !/^\d+$/.test(trimmed)      // exclude page numbers
```

### WR-03: No deduplication guard on `template_sections` insert — duplicate headings produce multiple rows

**File:** `supabase/functions/template-extract/index.ts:282-297`

**Issue:** `parseSectionsFromHtml` and `parseSectionsFromText` can return duplicate section names when a heading appears more than once (e.g., "Executive Summary" repeated in a multi-page header). The bulk insert at step 8 inserts all of them with no deduplication. The migration (`20260429000025_style_inspection.sql`) adds no unique constraint on `(template_id, name)`, so the database also does not protect against this. The result is duplicate `template_sections` rows that appear in the UI section list.

**Fix (application layer):** Deduplicate by name before inserting:

```typescript
const seen = new Set<string>()
const sectionInserts = sections
  .filter(s => {
    if (seen.has(s.name)) return false
    seen.add(s.name)
    return true
  })
  .map((s, idx) => ({ ... }))
```

A unique constraint `UNIQUE (template_id, name)` in a follow-up migration would also be a good defence-in-depth measure.

### WR-04: `TemplatesTab.test.tsx` tests a string literal, not the component — the size-cap logic is not actually covered

**File:** `src/components/settings/TemplatesTab.test.tsx:1-18`

**Issue:** The test constructs the expected error message string itself and asserts on that string's contents. It never imports or calls `handleFileUpload`, never renders `TemplatesTab`, and never simulates a file drop with a large file. As written the test passes regardless of what the actual component does — it verifies the test author's math, not the production code. If the size check or message template in `TemplatesTab.tsx` regresses, this test will not catch it.

**Fix:** Render the component and simulate an oversized file upload, then assert on the rendered error message:

```tsx
import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { TemplatesTab } from './TemplatesTab'

it('shows size-cap error for a file over 10 MB', async () => {
  render(<TemplatesTab />)
  const oversizedFile = new File([new ArrayBuffer(11 * 1024 * 1024)], 'big.docx', {
    type: 'application/vnd.openxmlformats-officedocument.wordprocessingml.document',
  })
  const input = screen.getByRole('...') // or use a data-testid
  await userEvent.upload(input, oversizedFile)
  expect(await screen.findByRole('alert')).toHaveTextContent('10.5 MB')
  expect(screen.getByRole('alert')).toHaveTextContent('compress')
})
```

## Info

### IN-01: `parseSectionsFromText` description-gathering loop uses a lookahead of up to `i+5` but can silently accumulate stop-heading lines as description text

**File:** `supabase/functions/template-extract/index.ts:42-49`

**Issue:** The inner loop breaks when it encounters another heading, but the break condition (`next === next.toUpperCase() && /[A-Z]/.test(next) && next.length < 80`) is less strict than the outer heading condition (`isAllCaps || isShortNoPunct`). Lines that would be treated as headings by the outer loop (because `isShortNoPunct` is true) but are not ALL-CAPS will be appended to the description of the prior section rather than breaking the inner loop. This is a minor accuracy issue rather than a bug, but it can cause description text to bleed across heading boundaries.

**Fix:** Mirror the outer heading condition in the break check, or extract a shared `isHeading(line)` function used in both places.

### IN-02: `ProposalDetail.tsx` uses `(proposal as any)?.selected_template_id` — unsafe cast suppresses type error

**File:** `src/pages/ProposalDetail.tsx:314,331`

**Issue:** `proposal` is typed from the `useProposals()` context and does not include `selected_template_id` in its type. Rather than extending the type, both the `useEffect` dependency and the `select` call cast to `any`. If the field is renamed or removed from the DB schema the TypeScript compiler will not flag these call sites.

**Fix:** Add `selected_template_id?: string | null` to the `Proposal` type (or wherever `useProposals` resolves its type), then remove the `as any` casts.

---

### IN-03: `handleDelete` in `TemplatesTab.tsx` does not surface storage or DB errors to the user

**File:** `src/components/settings/TemplatesTab.tsx:378-392`

**Issue:** `handleDelete` calls `supabase.storage.remove()` and `supabase.from('templates').delete()` but discards both return values without checking for errors. A failed storage delete (e.g., permission error) silently succeeds from the user's perspective while leaving the file in the bucket. A failed row delete is similarly silent.

**Fix:** Check errors and surface them through the existing `uploadError` state or a dedicated `deleteError` state:

```typescript
const { error: storageErr } = await supabase.storage.from('documents').remove([template.file_path])
if (storageErr) { setUploadError('Failed to delete template file. Please try again.'); return }
const { error: deleteErr } = await supabase.from('templates').delete().eq('id', templateId)
if (deleteErr) { setUploadError('Failed to delete template. Please try again.'); return }
```

## Style Injection Approach

| Option | Description | Selected |
|--------|-------------|----------|
| XML swap (JSZip) | Generate DOCX, post-process zip: swap word/styles.xml, word/theme/theme1.xml, word/numbering.xml with template's equivalents | ✓ |
| Parse and translate | Parse styles.xml, extract font/color/spacing, pass to docx API. Cleaner but limited to API surface | |

**User's choice:** XML swap — but with important scope clarification.

**Notes:** User identified that "swap styles.xml alone" is naive. Styles reference `theme1.xml` for colors/fonts, and lists reference `numbering.xml`. Correct scope for v1 is swapping all three files. User also specified the swap must be implemented as an isolated utility (`applyTemplateStyles(generated, template) → Blob`) with defensive failure handling — any error returns the original DOCX unchanged.

## Style Name Inspection

| Option | Description | Selected |
|--------|-------------|----------|
| At export time | Check style names when user clicks Export. Warn before proceeding | |
| At upload time (Edge Function) | Run inspection in existing Edge Function, persist result, surface in Settings | ✓ |
| Both | Flag at upload and remind again at export | |

**User's choice:** Upload time, in the existing Edge Function.

**Notes:** User emphasized that inspection answers a question about the template (which is fixed), not about the export (which is per-use). Running client-side on every Settings page load would mean re-fetching and re-decompressing for all templates. Server-side persists the result once and makes it queryable. Schema chosen: `style_inspection jsonb` (not a boolean) so the UI can render specific warnings ("Heading 3 missing") rather than generic ones. Nullable on inspection failure — a malformed `styles.xml` must not break the upload.

## Export-Time Template Fetch and Swap

| Option | Description | Selected |
|--------|-------------|----------|
| Client-side (browser) | Browser fetches signed URL, JSZip does the swap, all in-browser | ✓ |
| Edge Function | Server fetches template, performs swap, returns patched DOCX | |

**User's choice:** Client-side.

**Notes:** User clarified the right reasons: generated DOCX is already in the browser, template is fetchable via signed URL, JSZip is fast for sub-MB files. Edge Functions earn their place when server resources/secrets/auditable artifacts are needed — none apply here. User also specified that `ProposalDetail.tsx` must extend its `templates` query to include `file_path` and `source`.

## Fallback When No DOCX Template

| Option | Description | Selected |
|--------|-------------|----------|
| Silent fallback | Export proceeds with Calibri defaults. No warning shown | |
| Notice in export flow | Brief notice before export that no template is available | |
| Warning in Settings only + discoverability nudge | Settings surfaces inspection issues. One-time promotional nudge post-export for new users | ✓ |

**User's choice:** Option 3 with refinement.

**Notes:** User distinguished two separate cases: (1) "No template uploaded" = baseline state, not degraded — no warning, export proceeds with defaults. (2) "Uploaded but unusable" = already handled by upload-time inspection in Settings → Templates, don't re-surface at export. Added: one-time dismissible post-export nudge for users who've never engaged with templates ("Want exports to match your firm's branding?"). Promotional voice, not error voice.

## Template File Size Cap

| Option | Description | Selected |
|--------|-------------|----------|
| 10MB hard cap | Client-side check in TemplatesTab. Hard reject with specific message | ✓ |
| Match 50MB document limit | Consistent with rest of app | |
| No cap for now | Don't add complexity until evidence of problem | |

**User's choice:** 10MB hard cap.

**Notes:** User justified the 10MB number: JSZip handles ~10MB in a few hundred ms; 50MB causes noticeable memory pressure on lower-end devices; CRO templates are almost always under 5MB. User explicitly rejected "match 50MB" reasoning — documents and templates have different downstream costs. Hard reject (not soft warning) — a degraded export at the end of a long workflow is worse than an upload-time rejection. Message must be specific: show actual file size, name most likely cause, tell user what to do. Existing `FileUpload.tsx` has a 50MB cap but `TemplatesTab.tsx` uses its own upload handler with no cap — this phase adds the missing check.

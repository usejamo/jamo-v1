# Phase 14.3: Edge Identity Hardening - Context

**Gathered:** 2026-07-03
**Status:** Ready for planning

<domain>
## Phase Boundary

Harden four edge functions to derive caller identity (`user_id`/`org_id`) from the verified Supabase JWT instead of trusting request-body values, closing a live cross-tenant impersonation vector. Edge-functions-only, backward-compatible, independently deployable, and a **prerequisite go-live gate** for Phase 15 (invite-based multi-tenant provisioning). Split out of Phase 15's SPEC as its own deployable unit.

</domain>

<decisions>
## Implementation Decisions

### Identity Derivation
- **D-01 — Derive identity from the verified JWT via `auth.getUser()`; ignore body values.** Reuse the existing correct exemplars verbatim in shape: `analyze-proposal-gaps/index.ts:180-224`, `generate-proposal-section/index.ts:418-431`, `section-ai-action/index.ts:54-65`.
- **D-02 — Shared JWT-auth helper (recommended).** Extract a small helper (get authenticated user + org from the request's JWT, with a consistent 401 on missing/invalid) rather than copy-pasting into four functions. Exact shape is planner discretion; do not over-engineer.

### Caller-Shape Safety (the core risk)
- **D-03 — Audit callers before flipping each function.** `chat-with-jamo` and `salesforce-oauth-*` are user-authenticated surfaces (safe to require a JWT). `retrieve-context` is a RAG utility that is likely called **server-to-server by other edge functions with the service role** — those calls have no end-user JWT. Its fix must branch: user-authenticated call → derive + validate `org_id` from JWT; trusted internal service-role call → accept the explicitly-passed `orgId`. Do NOT blanket-require `auth.getUser()` on `retrieve-context` without confirming there are no internal callers.
- **D-04 — Backward-compatible deploy.** A valid JWT is already sent on every authenticated call, so the edge fix works without a coordinated frontend release. Clients may keep sending the now-redundant body `user_id` (harmless, ignored). Optional client cleanup to stop sending it is deferred.

### Deployment & Regression
- **D-05 — Deploy all four functions explicitly and regression-check.** execute-phase does not deploy; deploy via `supabase functions deploy` (or MCP) after code lands. Regression gate: confirm `chat_sessions` writes still land for an authenticated user after the body→JWT switch (this is the exact behavior the `edge-chat-session-writes-not-landing` memory documents in its current, pre-14.3 form).

### Claude's Discretion
- Exact shape of the shared JWT-auth helper.
- Whether to fold the optional client-side body `user_id` removal into this phase or defer it.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- Three functions already derive identity from the JWT correctly — copy their pattern (D-01) rather than inventing one.

### Established Patterns
- Edge functions use the service role for privileged DB writes; the JWT is used to identify the *caller*. The fix separates "who is calling" (JWT) from "what they may touch" (org scoping).

### Integration Points
- `chat-with-jamo`, `salesforce-oauth-initiate`, `salesforce-oauth-disconnect`, `retrieve-context`; a possible new shared `_shared/auth.ts`-style helper.

</code_context>

# Phase 14.3: Edge Identity Hardening — Specification

**Created:** 2026-07-03
**Ambiguity score:** 0.09 (gate: ≤ 0.20)
**Requirements:** 2 locked

## Goal

Edge functions derive the caller's `user_id`/`org_id` from the verified Supabase JWT (`auth.getUser()`) instead of trusting request-body values, closing a live cross-tenant impersonation vector — shipped and deployed independently, as a prerequisite gate before invite-based multi-tenant provisioning (Phase 15) introduces untrusted tenants sharing the instance.

## Background

Split out of Phase 15's SPEC as an independent deployable unit: it is edge-functions-only (no schema, no frontend), backward-compatible with current clients (a valid JWT is already sent on every authenticated call), and it fixes a live vulnerability that is logically upstream of the multi-tenancy Phase 15 builds.

Scouting confirmed the vulnerability. `supabase/functions/chat-with-jamo/index.ts:85-97` destructures `org_id` and `user_id` from the request **body** and never calls `auth.getUser()`; those values drive all session reads/writes (`:117,135,239,278,310`) and RAG scoping (`:143`). The same body-trust pattern exists in `salesforce-oauth-initiate/index.ts:33`, `salesforce-oauth-disconnect/index.ts:25`, and `retrieve-context/index.ts:161`. Correct JWT-derivation exemplars already exist in the codebase: `analyze-proposal-gaps/index.ts:180-224`, `generate-proposal-section/index.ts:418-431`, `section-ai-action/index.ts:54-65`.

**Caller-shape caveat (must verify):** `retrieve-context` is used for RAG and may be invoked **server-to-server by other edge functions with the service role** (no end-user JWT). Naively switching it to `auth.getUser()` would break those internal calls. Its fix must distinguish user-authenticated calls (derive + validate org from JWT) from trusted internal service-role calls (body `orgId` acceptable). This caller analysis is the core risk of the phase.

## Requirements

1. **chat-with-jamo JWT identity**: `chat-with-jamo` derives identity from the verified JWT.
   - Current: `chat-with-jamo/index.ts:85-97` reads `user_id`/`org_id` from the request body; `auth.getUser()` is never called.
   - Target: `user_id` (and `org_id`) are derived from the authenticated JWT via `auth.getUser()`; body-supplied identity is ignored for all session reads/writes and RAG scoping.
   - Acceptance: a request whose body carries a `user_id`/`org_id` different from its JWT is served using the JWT identity only (session rows and RAG scoped to the JWT's user/org, never the body's); existing authenticated chat flow still lands `chat_sessions` writes.

2. **Body-trust cleanup (salesforce-oauth-*, retrieve-context)**: Remaining body-trusted identity paths derive org/identity from the JWT, accounting for internal callers.
   - Current: `salesforce-oauth-initiate/:33`, `salesforce-oauth-disconnect/:25`, and `retrieve-context/:161` read `org_id`/`orgId` from the body.
   - Target: `salesforce-oauth-initiate`/`disconnect` derive `org_id` from the authenticated JWT. `retrieve-context` derives + validates `org_id` from the JWT for user-authenticated calls; trusted internal service-role calls (from other edge functions) continue to pass `orgId` explicitly.
   - Acceptance: for `salesforce-oauth-initiate`/`disconnect`, a request with a mismatched body `org_id` operates on the JWT-derived org (or is rejected). For `retrieve-context`, a user-authenticated call with a mismatched body `orgId` is served by the JWT org (or rejected), while existing internal service-role callers still function.

## Boundaries

**In scope:**
- JWT-derived identity in `chat-with-jamo` (ignore body `user_id`/`org_id`)
- JWT-derived org in `salesforce-oauth-initiate` and `salesforce-oauth-disconnect`
- `retrieve-context` hardened for user-authenticated calls while preserving internal service-role callers
- Optional shared JWT-auth helper for edge functions (extract/validate user+org)
- Caller-shape audit of all four functions (which calls are user-authenticated vs internal service-role)
- Explicit deployment of all changed functions + verification in the live project

**Out of scope:**
- `handle_new_user` trigger hardening / server-bound invite identity — that is Phase 15 (coupled to the `invites` table)
- Any invite / provisioning / admin-panel work — Phase 15
- Removal of the now-redundant client-side body `user_id` from `chat-with-jamo` requests — optional, non-blocking, may be deferred (the edge fix is backward-compatible without it)
- New auth features (SSO, MFA, etc.)

## Constraints

- Hosted Supabase project `fuuvdcvbliijffogjnwg`; RLS org-isolation must remain intact.
- Edge functions must be **deployed explicitly** (execute-phase commits but does not deploy) — an acceptance criterion verifies deployment, not just commit.
- Changes must be **backward-compatible** with current deployed clients: a valid JWT is already sent on authenticated calls, so no coordinated frontend release is required.
- Reuse the existing JWT-derivation exemplars (`analyze-proposal-gaps`, `generate-proposal-section`, `section-ai-action`) for consistency.

## Acceptance Criteria

- [ ] `chat-with-jamo` uses JWT-derived `user_id`/`org_id`; a body with mismatched identity is served by JWT identity only.
- [ ] Existing authenticated chat flow still lands `chat_sessions` writes after the change (no regression of the body→JWT switch).
- [ ] `salesforce-oauth-initiate` and `salesforce-oauth-disconnect` no longer trust body `org_id` (JWT-derived or rejected on mismatch).
- [ ] `retrieve-context` is hardened for user-authenticated calls AND all pre-existing internal service-role callers still function (verified by listing callers).
- [ ] A caller-shape audit is recorded for all four functions (user-authenticated vs internal service-role).
- [ ] All four changed functions are deployed to the live project (verified deployed, not just committed).

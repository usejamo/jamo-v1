# Phase 14.3 Plan 03: Branch retrieve-context on caller shape Summary

Hardened `retrieve-context` (the highest-risk plan in the phase) by branching on caller identity before scoping the RAG RPC filters: the internal service-role caller (`chat-with-jamo/rag.ts`) keeps trusting body `orgId` exactly as before, while the user-authenticated caller (`useProposalGeneration.ts`) now derives and validates its org from the verified JWT, closing a live cross-tenant RAG chunk exfiltration path.

## What Was Built

**Task 1 — Branch retrieve-context on caller shape and scope by effectiveOrgId** (commit `42b2ff0`)

- Added `import { isInternalServiceRoleCall, getAuthedUserAndOrg, jsonError } from '../_shared/auth.ts'` to `retrieve-context/index.ts`, matching the relative-import style already used by `chat-with-jamo/index.ts`.
- Kept the existing body destructure (`orgId, query, therapeuticArea, k_regulatory, k_proposal`) and presence validation (`orgId`/`query` required) unchanged — the internal branch still needs the raw body `orgId`.
- Immediately after the presence check, added the branch:
  - `isInternalServiceRoleCall(req)` true → `effectiveOrgId = orgId` (body value, zero behavioral change for `chat-with-jamo/rag.ts`).
  - Else (user call) → `getAuthedUserAndOrg(req, corsHeaders)` resolves `jwtOrgId`; if body `orgId` is present and differs from `jwtOrgId`, return `jsonError(403, 'org mismatch', corsHeaders)`; otherwise `effectiveOrgId = jwtOrgId`.
  - `getAuthedUserAndOrg` throws a `Response` on missing/invalid JWT or null org — caught and returned directly (401), per the documented `_shared/auth.ts` contract.
- Replaced `org_id_filter: orgId` with `org_id_filter: effectiveOrgId` at all four RPC call sites: `match_chunks_vector`, `match_chunks_fts`, `match_chunks_vector_proposals`, `match_chunks_fts_proposals`. Grep-confirmed zero remaining `org_id_filter: orgId` occurrences.
- Retained the existing service-role `supabase` client (unchanged) for all RPCs — only the org VALUE feeding the filter changed, not the client used to run the query (both the internal branch and RLS depend on the service-role client).

**Task 2 — Un-skip retrieve-context/test.ts, cover both branches** (commit `a3a914b`)

- Imported `isInternalServiceRoleCall` from `_shared/auth.ts` directly into `test.ts` and added three active (non-skipped) `Deno.test` assertions exercising the exact branch predicate `index.ts` now uses:
  - Service-role bearer → `true` (internal branch selected).
  - User JWT bearer → `false` (user branch selected).
  - Missing `Authorization` header → `false` (falls through to user branch, which will 401 via `getAuthedUserAndOrg`).
- Added two `ignore: true` integration scaffolds (naming 14.3-05 as the live-validation owner, matching the established `chat-with-jamo/test.ts` pattern) for the full request/response behaviors that require a live Supabase auth server + RPCs: internal-caller-preserved chunk retrieval, and user-mismatch real-403 response.
- File is no longer entirely skipped — the branch-selection logic is now actively exercised locally with zero network dependency.

## IMPORTANT — Live Verification Required (14.3-05)

**This plan's core risk (internal-RAG-caller preservation) is verified by static analysis + grep only in this environment. It MUST be live-verified in 14.3-05 before this phase is considered go-live-safe:**

1. **Internal caller unchanged:** With `chat-with-jamo` live, trigger a tool call that invokes `fetchRagContext` (e.g. `propose_edit`, `answer_with_citations`, `check_regulatory_compliance`) and confirm `retrieve-context` still returns non-empty `regulatoryChunks`/`proposalChunks` for the org passed in the body — i.e. RAG did not silently start returning empty results (rag.ts swallows errors on any non-2xx, so a regression here is otherwise invisible).
2. **User-call cross-tenant rejection:** From `useProposalGeneration.ts`, call `retrieve-context` with a body `orgId` that does NOT match the calling user's JWT-derived org and confirm a real 403 is returned (not a silent org override, not chunks from the wrong org).
3. **User-call happy path:** Confirm a normal user call (body `orgId` omitted, or matching the JWT org) still returns chunks scoped correctly.
4. **A2 assumption (T-14.3-12):** Confirm the Supabase project's edge gateway `verify_jwt` setting does not itself reject the service-role bearer before the function code runs (accepted risk per threat model, verified live in 14.3-05).

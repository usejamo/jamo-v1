## Caller-shape audit (AC-5)

- **chat-with-jamo** = user-authenticated. `getAuthedUserAndOrg(req, corsHeaders)` derives `userId`/`orgId` from the caller's JWT (via `../_shared/auth.ts`) before any `chat_sessions` read/write; body-supplied `user_id`/`org_id` are intentionally never destructured/trusted.
- **retrieve-context** = BOTH.
  - Internal service-role caller: `chat-with-jamo/rag.ts` (`fetchRagContext`) calls `retrieve-context` with `Authorization: Bearer ${SUPABASE_SERVICE_ROLE_KEY}` and a body-supplied `orgId`. `isInternalServiceRoleCall(req)` detects this by comparing the bearer token to the `SUPABASE_SERVICE_ROLE_KEY` secret (unspoofable from outside) and, when true, trusts the body `orgId` as-is — behavior unchanged from pre-hardening.
  - User caller: `useProposalGeneration.ts` calls `retrieve-context` with the end-user's JWT. In this path `getAuthedUserAndOrg` derives `orgId` from the JWT, and a mismatched body `orgId` is rejected with 403 rather than trusted.
- **salesforce-oauth-initiate** = user. `getAuthedUserAndOrg` derives `orgId` from the JWT for `signState` + the `oauth_pending` insert; a mismatched body `org_id` is rejected with 403 (tamper-attempt detection only — the body value is never used for the write).
- **salesforce-oauth-disconnect** = user. Same pattern — `orgId` from the JWT drives the `salesforce_connections` lookup and Vault revoke; a mismatched body `org_id` is rejected with 403.

## A2 note

`retrieve-context` stays `verify_jwt=false` so the internal service-role RAG call from `chat-with-jamo/rag.ts` passes the API gateway trivially (a service-role bearer token is not an end-user JWT and would otherwise be rejected at the gateway before the function body's `isInternalServiceRoleCall` check ever runs). ## Anomalies

1. **chat-with-jamo required a `deno.json` import map that was not in the original file list.** The plan's file trace explicitly said "chat-with-jamo (NO deno.json)," matching what's on disk in the repo (`supabase/functions/chat-with-jamo/` has no `deno.json`). However, the hardened `index.ts` now imports `../_shared/auth.ts`, and `_shared/auth.ts` imports `createClient` from the bare specifier `'supabase'`. Deploying with exactly the file list as given failed:
   ```
   BadRequestException: Failed to bundle the function (reason: Relative import path "supabase" not prefixed with / or ./ or ../ ... at .../_shared/auth.ts:5:30)
   ```
   This is confirmed by inspecting the **currently-live v15 bundle** via `get_edge_function`: v15's `index.ts` does NOT import `_shared/auth.ts` at all — it still reads `org_id`/`user_id` straight from the request body (the pre-hardening, vulnerable code this phase is meant to replace). So v15 never needed an import map for `'supabase'`; the new hardened code does.
   - **Fix applied for this deploy only**: added a `deno.json` to the `files[]` payload (not committed to the repo) with `{"imports": {"supabase": "npm:@supabase/supabase-js@2"}}` — the same mapping already used by `retrieve-context`, `salesforce-oauth-initiate`, and `salesforce-oauth-disconnect` — and passed `import_map_path: "deno.json"` explicitly.
   - **Follow-up needed**: this `deno.json` exists only in the deployed bundle, not in git. A future deploy of `chat-with-jamo` done differently (e.g. `supabase functions deploy` reading only the repo tree) would hit the same bundle failure unless `supabase/functions/chat-with-jamo/deno.json` is added to the repo. Flagging for the orchestrator/user to decide whether to commit that file in a follow-up change.

2. **`import_map_path` must be passed explicitly, or the deploy tool reuses the previous deployment's stale absolute path.** The first attempt at `retrieve-context`, `salesforce-oauth-initiate`, and `salesforce-oauth-disconnect` omitted `import_map_path` (relying on the default), and all three failed:
   ```
   BadRequestException: import map path does not exist - .../source/file:///tmp/user_fn_..._<old-version>/source/.../deno.json
   ```
   The tool appears to default `import_map_path` to the *previous* deployed version's absolute `file://` path rather than resolving `deno.json` from the new `files[]` payload. Passing `import_map_path: "deno.json"` explicitly on the retry resolved this for all four functions.

No other anomalies. No sibling imports were found beyond the ones already listed in the plan (chat-with-jamo's tool files, rag.ts, and context.ts have no additional relative imports; retrieve-context and the two salesforce functions likewise had no undocumented siblings).

## Summary

The vulnerability is confirmed and narrow: four edge functions read tenant identity (`user_id`/`org_id`) from the request **body** and never verify it against the JWT. Three of the four (`chat-with-jamo`, both `salesforce-oauth-*`) are called **only** from the client with a real user JWT in the `Authorization` header, so they can safely adopt the existing `auth.getUser()` exemplar pattern outright. The fourth, `retrieve-context`, is the core risk: it has exactly **two** callers — one internal server-to-server call from `chat-with-jamo/rag.ts` using the **service-role key** as the bearer token (no end-user JWT), and one user-authenticated client call from `useProposalGeneration.ts:183`. It therefore must branch on caller shape rather than blanket-requiring a user JWT.

The codebase already contains three correct, copyable exemplars. The canonical shape: build an anon-key Supabase client with the request's `Authorization` header, call `auth.getUser()`, return 401 on null/error, then resolve `org_id` via a `user_profiles` lookup keyed by `user.id` (**org_id is NOT reliably in the JWT** — this is documented in `analyze-proposal-gaps:226-228` and is the single most important gotcha). A `_shared/` directory already exists and is imported by deployed functions, so a shared `_shared/auth.ts` helper is fully feasible (D-02).

**Primary recommendation:** Extract a `_shared/auth.ts` helper exposing `getAuthedUserAndOrg(req)` (returns `{userId, orgId}` or throws a 401) and `isInternalServiceRoleCall(req)` (token === `SUPABASE_SERVICE_ROLE_KEY`). Apply `getAuthedUserAndOrg` to `chat-with-jamo` and both `salesforce-oauth-*`; apply the branch (`isInternalServiceRoleCall` → trust body `orgId`; else derive+validate from JWT) to `retrieve-context`. Deploy all four via Supabase MCP `deploy_edge_function` (or CLI `npx supabase functions deploy <slug> --project-ref fuuvdcvbliijffogjnwg`) with `verify_jwt=true`, then run the `chat_sessions` regression check.

## Q1: retrieve-context caller audit (THE core risk)

**How it reads identity today** (`supabase/functions/retrieve-context/index.ts`):
- `:161` — `const { orgId, query, therapeuticArea, k_regulatory, k_proposal } = await req.json()` — **fully body-trusted `orgId`**.
- `:167` — validates only that `orgId` and `query` are present.
- `:175-178` — creates a **service-role** client (`SUPABASE_SERVICE_ROLE_KEY`). **`auth.getUser()` is never called.** The `orgId` flows straight into `match_chunks_vector` / FTS RPCs (`:199` `org_id_filter: orgId`) — so any caller can read any org's chunks. [VERIFIED: source read]

**Every caller (whole-repo grep for `retrieve-context` invocations):**

| Caller | file:line | Shape | JWT? | Verdict |
|--------|-----------|-------|------|---------|
| `chat-with-jamo/rag.ts` `fetchRagContext` | `supabase/functions/chat-with-jamo/rag.ts:35-50` | Internal edge→edge `fetch()` to `/functions/v1/retrieve-context` | **Service-role key** as bearer (`:41` `Bearer ${SERVICE_ROLE_KEY}`), `orgId` in body (`:44`) | **INTERNAL** — must keep passing `orgId`; cannot require user JWT |
| `useProposalGeneration.ts` | `src/hooks/useProposalGeneration.ts:183` | Client `supabase.functions.invoke('retrieve-context', …)` | End-user session JWT (auto-attached by supabase-js) | **USER** — must derive+validate `orgId` from JWT |

(Other grep hits — `retrieve-context/test.ts`, `useProposalGeneration.test.ts`, planning docs — are not runtime callers.) [VERIFIED: Grep + source read]

**Required design — branch on caller shape:**
```
token = req.headers.Authorization.replace("Bearer ", "")
if (token === Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")) {
  // INTERNAL (chat-with-jamo/rag.ts): trust body orgId as-is
} else {
  // USER call: build anon client w/ auth header, auth.getUser() → 401 if null,
  // resolve real orgId from user_profiles, use THAT (ignore/reject mismatched body orgId)
}
```
This preserves the internal caller unchanged while closing the vector for user calls. **Gateway `verify_jwt=true` is fine** — the service-role key is itself a valid JWT and passes the gateway; the in-code branch is what distinguishes internal vs user.

## Q2: The correct JWT-derivation pattern (copy target)

Three exemplars; **org_id comes from a `user_profiles` lookup, not a JWT claim.** [VERIFIED: source read]

**`analyze-proposal-gaps/index.ts:180-224` (strictest — anon+JWT for all reads):**
```ts
// user_id intentionally absent from request schema — always derived from JWT (:192)
const authHeader = req.headers.get('Authorization')
if (!authHeader) return 401 'Missing Authorization header'          // :204-210
const supabase = createClient(supabaseUrl, supabaseAnonKey, {
  global: { headers: { Authorization: authHeader } },              // :212-214
})
const { data: { user }, error: authError } = await supabase.auth.getUser()
if (authError || !user) return 401 'Unauthorized'                   // :217-223
const userId = user.id                                             // :224 canonical identity
// org_id NOT reliably in JWT → look up user_profiles (:226-228)
const { data: profileRow } = await supabase.from('user_profiles')
  .select('org_id').eq('user_id', user.id).single()
```

**`section-ai-action:54-69` / `generate-proposal-section:418-439` (two-client variant):** a `userClient` (anon+JWT) for `auth.getUser()`, plus a service-role `supabase` client for the `user_profiles.org_id` lookup and privileged writes:
```ts
const userClient = createClient(URL, ANON_KEY, { global: { headers: { Authorization: authHeader ?? '' } } })
const { data: { user } } = await userClient.auth.getUser()
const { data: profile } = await supabase                 // service-role client
  .from('user_profiles').select('org_id').eq('user_id', user!.id).single()
const orgId = profile!.org_id
```

**Recommendation for the shared helper:** adopt the two-client variant (identity via anon+JWT `userClient`; keep a service-role client for privileged writes). Return `{ userId, orgId }` and throw/return a consistent 401 when `user` is null. Note the exemplars are inconsistent on null-safety (`analyze-proposal-gaps` guards `authError || !user`; `generate-proposal-section` uses non-null `user!` — the helper should always guard). ## Q4: salesforce-oauth-initiate / -disconnect

Both are **user-authenticated only** — called from `src/components/SalesforceConnection.tsx:68` (initiate) and `:82` (disconnect) via `supabase.functions.invoke`, which attaches the user session JWT. [VERIFIED: Grep + source read]

- **initiate** (`index.ts:33`): `const { org_id, is_sandbox } = await req.json()` — body-trusted. Then `signState(org_id, nonce, consumerSecret)` at `:50` embeds `org_id` into a **signed CSRF state** later validated at callback. Deriving `org_id` from the JWT instead **strengthens** the CSRF/identity binding (the state now provably binds the authenticated user's org, not an attacker-supplied one). Insert into `oauth_pending` at `:61-66` uses `org_id`.
- **disconnect** (`index.ts:25`): `const { org_id } = await req.json()` — body-trusted; drives `salesforce_connections` lookup `.eq('org_id', org_id)` (`:43`) and Vault token revoke/delete. A mismatched body `org_id` could disconnect another tenant's Salesforce — derive from JWT.

Both create a **service-role** client for privileged work; add the two-client pattern: `userClient` for `auth.getUser()`, `user_profiles` lookup for `org_id`, keep the service-role client for writes/Vault. Both import from `_shared/` already (`salesforce-crypto.ts`), confirming shared-module imports work here.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Verify caller identity | Custom JWT decode/verify | `supabase.auth.getUser()` with anon-key client + auth header | Verifies signature + expiry server-side; exemplars already use it |
| Resolve org from user | Trust body / decode a custom claim | `user_profiles` lookup by `user.id` | org_id is NOT reliably in the JWT (documented `analyze-proposal-gaps:226-228`) |
| Distinguish internal vs user call | New shared-secret header | Compare bearer to `SUPABASE_SERVICE_ROLE_KEY` | Internal caller already sends it (`rag.ts:41`); zero new surface |
| Org data isolation | Manual per-query filtering only | Keep RLS intact + JWT-derived scoping | Constraint: "RLS org-isolation must remain intact" |

## Common Pitfalls

### Pitfall 1: Blanket-requiring auth.getUser() on retrieve-context
**What goes wrong:** the internal `chat-with-jamo/rag.ts` call (service-role bearer, no end-user) starts returning 401 → RAG silently returns empty (`rag.ts:51-52,70-72` swallow errors), so chat answers lose all regulatory/proposal context with **no visible error**. **Avoid:** branch on `isInternalServiceRoleCall` first.

### Pitfall 2: Deriving identity AFTER the first session read
**What goes wrong:** chat-with-jamo reads `chat_sessions` at `:109-118` before the authed client exists at `:158`. If you only swap variables in place, the read still runs on the anon client / wrong ordering. **Avoid:** hoist identity derivation to the top of the try block.

### Pitfall 3: Committing without deploying
**What goes wrong:** verification passes on committed source while production runs the stale (vulnerable) version — exactly the Phase 14.2.3 failure mode. **Avoid:** explicit deploy step + confirm version bump via `list_edge_functions`.

### Pitfall 4: MCP deploy dropping sibling files
**What goes wrong:** deploying `chat-with-jamo` without `rag.ts` (and `_shared/auth.ts`) breaks the import at runtime. **Avoid:** pass every referenced file in the MCP `files` array.

### Pitfall 5: org_id null on the user_profiles lookup
**What goes wrong:** `.single()` returns null org_id if a profile is missing → downstream writes violate `chat_sessions.org_id NOT NULL` / RLS `WITH CHECK`. **Avoid:** guard and 401/500 explicitly rather than passing `null`.

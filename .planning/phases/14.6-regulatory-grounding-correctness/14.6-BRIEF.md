## Objective

Three deliverables, **in strict priority order** so the correctness fix ships even if the seeder slips:

1. **(b) PRIMARY — Regulatory grounding correctness (live bug).** Retrieval currently mislabels
   proposal-history chunks as regulatory context and silently swallows zero-regulatory-retrieval; and
   the section-generation prompt asserts ICH-GCP compliance unconditionally. Fix the root cause (a tier
   collapse), then make the compliance claim conditional on actually having regulatory grounding.
2. **(a) SIBLING — Ingest supersession hardening.** `ingest_regulatory_document` silently no-ops when
   `--supersedes` is passed but unresolved; make it RAISE.
3. **(third) — Starter-corpus seeder.** A one-command, manifest-driven seeder to populate the
   (currently empty) regulatory corpus, depending on (a) and (b) being correct.

## Priority / framing (locked)

- Lead with **(b)** — it is a live correctness defect in shipped *compliance* behavior, not a feature.
- **(a)** is (b)'s natural sibling and a prerequisite for a trustworthy seeder.
- The **seeder** is third; if the phase is time-pressured, (b) ships first, then (a), then the seeder.
- The proposed **default manifest contents** are a PROPOSAL and remain gated on a clinical-domain
  review before locking — do not treat the drafted list as a spec.

## (b) PRIMARY — Regulatory grounding correctness

### Root cause (fix the class, not the two symptoms)

`fetchRagChunks` (`src/hooks/useProposalGeneration.ts`, the return around lines 214–216) collapses the
two retrieval tiers into one array and discards the meta:

```ts
const regulatory = data?.regulatoryChunks ?? []
const proposal   = data?.proposalChunks ?? []
return [...regulatory, ...proposal]   // <-- the defect: tiers merged, retrievalMeta dropped
```

`retrieve-context` already returns everything needed — `regulatoryChunks`, `proposalChunks`,
`retrievalMeta { regulatoryCount, proposalCount, belowThreshold, regulatoryRelaxationLevel }`, and a
pre-built `systemPromptBlock` — but all of it dies in that merge. Downstream,
`generate-proposal-section/index.ts` conditions purely on the merged `ragChunks.length > 0` and dumps
whatever's there under a single `[REGULATORY CONTEXT]` header (lines ~140–142 and ~252–254).

**Both observed symptoms are downstream of the collapse:**
- **Mislabeling:** when `regulatoryCount=0` but proposals exist, proposal-history chunks are emitted
  under `[REGULATORY CONTEXT]`.
- **Silent-empty:** when both are 0, the block is omitted and the section generates ungrounded, with no
  visible signal (only a server-side `console.warn('Below minimum chunk count')`).

**The fix is the tier separation, done once.** Keep `regulatoryChunks` and `proposalChunks` (and at
least `regulatoryCount`) *separate all the way through to `generate-proposal-section`*, so the edge
function can condition on `regulatoryCount` specifically rather than a merged length. Do NOT patch the
two symptoms independently — that is more fragile than fixing the collapse.

### Required changes

1. **Client contract (`useProposalGeneration.ts` + payload type):** stop merging in `fetchRagChunks`.
   Carry the two tiers separately to the edge function (e.g. payload `regulatoryChunks` +
   `proposalChunks`, or a `{ regulatoryChunks, proposalChunks, regulatoryCount }` shape) — replacing the
   single `ragChunks` field on `GenerateSectionPayloadV2`. Thread through both call sites
   (`generateAll` ~475, `generateSection` ~543) and `streamSection`. (Reusing retrieve-context's already
   -correct `systemPromptBlock` end-to-end is a viable alternative to rebuilding — planning's call.)
2. **Edge (`generate-proposal-section/index.ts`):** label regulatory chunks under `[REGULATORY
   CONTEXT]` and proposal-history chunks under a separate `[PROPOSAL HISTORY]` header (never conflate).
   When `regulatoryCount === 0`, emit an explicit "no regulatory grounding available for this
   section/geography" marker.
3. **Conditional compliance assertion (the part that matters most):** the system prompt
   (`CRO_PROPOSAL_SYSTEM_PROMPT`, ~line 27) asserts *"compliant with ICH-GCP (E6 R2/R3)"*
   **unconditionally.** A not-found marker alone is contradictory input alongside an unconditional
   compliance claim — and the assertion wins. So the compliance assertion MUST become **conditional on
   `regulatoryCount > 0`.** When there is no regulatory grounding, the prompt must not assert compliance
   for that section (fall back to the existing CRITICAL RULES: flag with `[PLACEHOLDER]`, never
   fabricate). This is the difference between the model *knowing it is ungrounded* and the model being
   told two opposite things.

### Deploy note
This is a client↔edge contract change: `useProposalGeneration.ts` (client) and
`generate-proposal-section` (edge) must ship together. `generate-proposal-section` was NOT touched in
14.5 — it needs an explicit deploy (`npx supabase functions deploy generate-proposal-section
--project-ref fuuvdcvbliijffogjnwg`). `retrieve-context` needs NO change (it already returns the split).

### Why this bottoms out legitimately
With the (third) starter set seeded R3-only for `{US,EU,UK}`, a **Japan** GCP section will correctly
retrieve zero regulatory chunks (geography filter excludes R3; graded relaxation correctly keeps the
geography filter). That legitimate zero MUST be visible, not swallowed — this is the concrete case the
fix protects.

## (a) SIBLING — Ingest supersession hardening

Today `ingest_regulatory_document` (`supabase/migrations/20260708000005_ingest_regulatory_rpc.sql`)
**silently no-ops** when `--supersedes` is passed but the target doesn't resolve — the
`IF v_supersedes_id IS NOT NULL THEN … END IF;` simply falls through.

**Required:** RAISE instead. New migration (`CREATE OR REPLACE` the function), applied via Supabase MCP
`apply_migration` (NOT `db push`). The supersession block becomes:

```sql
IF p_supersedes_document_key IS NOT NULL THEN
  SELECT id INTO v_supersedes_id FROM regulatory_documents
    WHERE document_key = p_supersedes_document_key AND status = 'active' AND id <> v_id;
  IF v_supersedes_id IS NULL THEN
    RAISE EXCEPTION 'supersedes target % not found among active regulatory_documents',
      p_supersedes_document_key;
  END IF;
  -- ... existing flip (set predecessor superseded/superseded_by; set new supersedes) ...
END IF;
```

**Raise condition (state precisely — do not get this wrong):** raise iff **`p_supersedes_document_key
IS NOT NULL` AND the lookup found nothing**. When `--supersedes` was NOT passed
(`p_supersedes_document_key IS NULL`), the branch is skipped entirely and the ingest proceeds normally —
that no-op is CORRECT. **Do NOT implement as "raise whenever `v_supersedes_id IS NULL`"** — that would
fire on every non-superseding ingest, including all GLOBAL starter docs, and break seeding.

The error message is "you asked to supersede something that isn't there," not "you didn't supersede
anything." DB-only change — no edge deploy for (a).

## (third) — Starter-corpus seeder (Approach A: manifest + folder convention)

### Shape
- **Manifest** (`scripts/regulatory-starter-manifest.ts`) exports typed entries:
  `{ documentKey, title, agency, geography: string[], phase?: string[], therapeuticArea?, effectiveDate?, status?, supersedes?, folder? }`.
  `folder` defaults to `documentKey`. Inline COMMENTS carry rationale (esp. the E6 non-GLOBAL note).
- **Folders:** PDFs live in `regulatory-docs/<documentKey>/*.pdf` (curated, not committed as binaries;
  `.gitignore` the PDFs, keep the folder structure documented). Each folder's PDFs = one logical doc.
- **Command:** `npm run seed:regulatory` → `scripts/seed-regulatory.ts`, reusing the ported ingest path
  (`embedBatch` + `chunkDocument` + the `ingest_regulatory_document` RPC — do not re-implement embedding).

### Structural requirement #1 — supersession ordering independent of manifest order
Either topologically sort entries by their `supersedes` links before running, or validate up front that
every `supersedes` target appears earlier in the run order — hard-fail with a clear message if a target
is missing or the graph is cyclic. This pairs with (a): the RPC now RAISES on an unresolved supersedes,
and the seeder must never depend on lucky manifest ordering to avoid that raise.

### Structural requirement #2 — batch pre-validation before any write
A validation pass that runs **before any DB write or embedding call** and confirms, across the whole
manifest: every referenced folder exists with ≥1 PDF; every `supersedes` target is present in the
manifest; no duplicate `documentKey`s; supersedes graph acyclic. Aggregate all failures into one clear
report and exit non-zero **without spending a single embedding call.** Seeding is all-or-nothing at the
batch level. Provide a `--validate-only` mode that runs just this pass.

### Geography / E6 decision (locked — launching without Japan)
- **Starter set is R3-only.** No R2 in the pack. No `--supersedes` on the E6 pair.
- **`ICH-E6R3` geography = `{US,EU,UK}`, NOT `GLOBAL`.** The non-GLOBAL scoping is deliberate: it keeps
  E6 from answering a Japan query and citing R3, which PMDA has not adopted. A manifest COMMENT MUST
  state this so nobody later "fixes" it to GLOBAL for consistency with its siblings.
- **Everything else** (E8, E9, E3, M3, etc.) → `GLOBAL` canon (`org_id` NULL).
- **Intended, documented consequence:** a Japan proposal gets no ICH E6 from the starter set — a
  coverage gap the operator fills (add R2 for JP) when Japan comes into scope. This is exactly the
  legitimate zero-retrieval that (b) makes visible.

### Default manifest — PROPOSED, pending clinical-domain review
Draft a sensible default (core ICH E-series + select FDA/EMA) as a PROPOSAL for domain review before
locking — treat the list as a proposal, not a spec. It needs one clinical-domain pass.

## OUT OF SCOPE — DO NOT IMPLEMENT THIS PHASE

- **Per-geography / regional supersession status** — the real fix for staggered regional adoption
  (e.g. E6 R3 in US/EU/UK vs R2 in JP). Deferred to **Backlog 999.2**; this phase deliberately works
  around it via disjoint-geography unlinked docs.
- Auto-download / auto-fetch of regulatory PDFs (no `--fetch` option). Files are operator-supplied.
- Locking the default manifest contents (requires clinical-domain review).
- Modality column/filter; recency/time-decay ranking; LLM/HyDE query synthesis; any 14.5 out-of-scope item.

## VERIFICATION

1. **(b) tier separation:** a section generated with `regulatoryCount=0` but proposal chunks present
   does NOT emit proposal chunks under `[REGULATORY CONTEXT]`; the prompt contains the "no regulatory
   grounding" marker and does NOT assert ICH-GCP compliance for that section. A section with
   `regulatoryCount>0` retains the compliance assertion and a correctly-populated `[REGULATORY CONTEXT]`.
   (Unit-test the prompt-assembly branch on `regulatoryCount`; live-smoke a Japan-scoped section after
   seeding.)
2. **(b) deploy:** `generate-proposal-section` redeployed; client + edge payload contract match (no
   silent shape drift).
3. **(a) raise:** calling `ingest_regulatory_document` with `p_supersedes_document_key` set to a
   non-existent/inactive key RAISES; calling with `p_supersedes_document_key = NULL` succeeds normally
   (regression guard for the GLOBAL-doc path).
4. **(third) pre-validation:** running the seeder against a manifest with a missing folder / missing
   supersedes target / duplicate key fails BEFORE any embedding call, with an aggregated message.
5. **(third) end-to-end:** `npm run seed:regulatory` populates the corpus in dependency order; a US
   Phase-2 oncology "Study Design" section retrieves the seeded E6(R3); a JP-scoped section legitimately
   retrieves none and surfaces the (b) marker.

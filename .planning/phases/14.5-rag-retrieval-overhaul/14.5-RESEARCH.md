## Summary

This phase touches a small, well-bounded set of already-shipped Phase 04/05/07 artifacts. Every
file and RPC named in the BRIEF was located and read in full. The schema, RPCs, edge function, and
wizard code all match the BRIEF's "current-state facts" section exactly — no surprises there.

The one material discovery beyond the BRIEF's stated facts: **the wizard does not persist
`regions`/`countries` as a real column today.** `ProposalCreationWizard.tsx` JSON-stringifies
`{ services, regions }` into `proposals.description` (a repurposed free-text column), and
`ProposalDetail.tsx`'s `buildProposalInput()` parses that JSON back out at generation time to
populate `studyInfo.countries`. Adding `proposals.geography text[]` is therefore not just a
migration — it requires rewiring three call sites (wizard create, wizard update-on-generate,
`buildProposalInput`) plus the `ProposalsContext` camelCase↔snake_case mapper and the `Proposal`
type, none of which currently know about geography/regions as a first-class field.

The second material discovery: **`scripts/ingest-regulatory.ts` is a Deno-only CLI, and Deno is not
installed in this dev environment** `[VERIFIED: command -v deno → not found]`. The BRIEF's
verification protocol requires running this CLI twice (ICH E6R2, then E6R3 with `--supersedes`).
As written today (`Deno.args`, `Deno.env`, `Deno.readFile`, `jsr:`/`npm:` specifiers), it cannot run
in this shell. The sibling script `scripts/backfill-proposal-chunks.ts` already proves the working
alternative pattern in this repo: a plain Node/tsx script using `@supabase/supabase-js` + raw
`fetch()` to the OpenAI embeddings endpoint (no `openai` npm package, no Deno). The planner must
decide: rewrite `ingest-regulatory.ts` to the tsx pattern (recommended, low risk, mirrors proven
code) or require the user to install Deno before this phase's verification can run.

**Primary recommendation:** Treat this as three independent-but-sequenced units of work: (1) SQL
migrations (regulatory_documents + chunks alterations + RPC rewrites + RLS), applied via Supabase
MCP `apply_migration`; (2) ingest CLI rewrite/extension to tsx + new flags; (3) TS/edge wiring
(`fetchRagChunks`, `retrieve-context`, wizard geography field) + edge redeploy. Sequence SQL before
CLI before TS wiring, since the CLI and retrieval RPCs both depend on the new schema existing first.

## Common Pitfalls

### Pitfall 1: Deno CLI cannot run in this dev environment
**What goes wrong:** Planner writes a task like "run `deno run ... scripts/ingest-regulatory.ts
--document-key=ICH-E6R2 ...`" for the BRIEF's verification protocol, and it fails immediately with
"deno: command not found."
**Why it happens:** `ingest-regulatory.ts` was written Deno-first in Phase 04 and has never been
run outside that assumption; this dev machine has no Deno install `[VERIFIED]`.
**How to avoid:** Either (a) add a task to install Deno first (`irm https://deno.land/install.ps1 |
iex` on Windows, or via a package manager) and keep the CLI Deno-only, or (b) port
`ingest-regulatory.ts` to a `tsx`-runnable Node script following `backfill-proposal-chunks.ts`'s
exact pattern (raw `fetch()` for OpenAI, `@supabase/supabase-js` service-role client,
`process.argv`-based flag parsing instead of `jsr:@std/cli/parse-args`, `node:fs`/`node:path`
instead of `Deno.readFile`/`jsr:@std/fs/walk`, plain PDF file reads via `node:fs.readFileSync` +
`pdf-parse` from npm — already a real dependency per REQUIREMENTS.md). Option (b) is recommended:
it removes an environment dependency entirely and mirrors code already proven in this exact repo.
Either way, this decision must be made explicitly in the plan, not discovered mid-execution.
**Warning signs:** Any task description that assumes `deno run` works without a preceding
install/verify step.

### Pitfall 2: RPC signature change breaks the caller without a matching edge deploy
**What goes wrong:** `match_chunks_vector`/`match_chunks_fts` get `CREATE OR REPLACE FUNCTION` with
new parameters (`phases_filter`, `geographies_filter`), but the deployed `retrieve-context` edge
function still calls them with the old parameter list (or vice versa — new edge code deployed
before the migration lands) — RPC calls fail with a Postgres "function does not exist for this
argument list" error, and per the existing non-blocking pattern (`console.warn` + empty array
fallback in `retrieve-context/index.ts` lines 229-244), **this fails silently** — RAG just returns
empty regulatory chunks with no visible error to the end user.
**Why it happens:** SQL migrations (via Supabase MCP `apply_migration`) and edge function deploys
(via `npx supabase functions deploy`) are two independent, manually-triggered steps in this repo —
"committed ≠ live" applies to both, and they don't have to land in the same action.
**How to avoid:** Sequence tasks so the migration (new RPC signatures) is applied and confirmed
*before* the edge function code that calls the new signature is deployed. Use
`scripts/verify-retrieve-context.ts` (already exists, hits the deployed edge function via the
internal service-role path) as a post-deploy smoke check — but note this script currently only
checks HTTP 200 + chunk counts, not filter correctness, so it may need light extension for this
phase's regulatory-specific budget/relaxation behavior.
**Warning signs:** `retrieve-context` logs `console.warn` for regulatory vector/FTS errors but
still returns HTTP 200 — a "successful" response with `regulatoryChunks: []` looks identical
whether the corpus is genuinely empty or the RPC call is silently erroring.

### Pitfall 3: `document_key` re-ingest must UPDATE the existing parent row, not upsert-by-unique-constraint naively
**What goes wrong:** A naive `INSERT ... ON CONFLICT (document_key) DO UPDATE SET ...` that
includes `document_key` in the `SET` clause (even redundantly, `document_key = EXCLUDED.document_key`)
risks the immutability trigger firing on a value that's technically unchanged but structurally
present in the SET list — and more importantly, an `INSERT ... ON CONFLICT DO UPDATE` changes `id`
semantics if not done carefully (Postgres `ON CONFLICT DO UPDATE` does preserve the existing row's
`id` since it's an UPDATE under the hood, so this is actually safe *if* `document_key` is excluded
from the SET clause — but the BRIEF is explicit: "UPDATE the parent row in place by its `id`" and
"`document_key` is never in the SET clause"). The safer implementation matching the BRIEF exactly is
two explicit statements: `SELECT id FROM regulatory_documents WHERE document_key = $1`, then either
`INSERT` (no match) or `UPDATE ... WHERE id = $found_id` (match, omitting `document_key` from the
SET list) — not a single `ON CONFLICT` clause, so the trigger's `NEW.document_key <> OLD.document_key`
check is trivially always false for the update path.
**Why it happens:** `ON CONFLICT DO UPDATE` is the idiomatic Postgres upsert pattern, but the BRIEF's
guardrail language ("document_key is never in the SET clause") reads as a deliberate steer away from
a single blended upsert statement, toward an explicit select-then-branch, to keep the immutability
invariant visually obvious in the ingest code itself (defense in depth alongside the trigger).
**How to avoid:** Write the ingest CLI's upsert as explicit SELECT-then-INSERT-or-UPDATE, matching
BRIEF language literally.
**Warning signs:** A single SQL statement doing both insert and update paths for
`regulatory_documents` — worth a second look during plan-checking.

### Pitfall 4: CASCADE delete on re-ingest must be scoped by `regulatory_document_id`, not `source`/`agency`
**What goes wrong:** Re-ingest logic deletes existing chunks by `WHERE source = $filename` (the old
`ingest-regulatory.ts` mental model) instead of `WHERE regulatory_document_id = $parent_id` — if a
single logical document is split across multiple source filenames, or if `source` free text ever
collides across documents, the wrong chunk set gets deleted/kept.
**Why it happens:** The current CLI's only identity concept is `source` (filename) + `agency`; the
new `document_key`-keyed identity is a structurally different key and it's easy to reach for the old
`source`-based delete pattern out of habit.
**How to avoid:** Scope every re-ingest delete to `chunks WHERE regulatory_document_id = <resolved
parent id>` exactly as the BRIEF states; never delete by `source` or `agency`.

### Pitfall 5: `proposals.geography` column added but old `description`-JSON `regions` path left as the only writer
**What goes wrong:** Migration adds the column, `Step1StudyInfo.tsx` UI is left unchanged, but
nobody rewires `ProposalCreationWizard.tsx`'s two `createProposal(...)` call sites to also pass
`geography: studyInfo.regions` — the column exists but is always NULL, and `buildProposalInput` in
`ProposalDetail.tsx` (if switched to read `proposal.geography`) silently gets `[]` forever, worse off
than today's working-but-hacky JSON-in-description path.
**Why it happens:** The BRIEF's schema section and the wizard-wiring section are easy to plan as
separate tasks; the actual call sites are spread across 4 files (see item 7/8 above) and none of
them is named "geography" anywhere yet, so a grep for "geography" during planning would find
nothing to anchor on — the planner must know to grep for `regions` instead.
**How to avoid:** Plan explicit tasks for all 4 touch points found above: (1) migration, (2)
`Proposal` type + `ProposalsContext` create/update/mapRow, (3) `ProposalCreationWizard.tsx` both
call sites, (4) `ProposalDetail.tsx` `buildProposalInput`.
**Warning signs:** A plan that only mentions `Step1StudyInfo.tsx` and the migration for the
geography requirement, with no `ProposalsContext.tsx`/`ProposalCreationWizard.tsx`/`ProposalDetail.tsx`
tasks.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|----------------------|
| Cross-tenant regulatory-tier confusion (a crafted `org_id_filter` or malformed geography filter accidentally exposing another org's *proposal* chunks) | Information Disclosure | Keep the `_proposals` RPCs completely untouched (BRIEF's explicit instruction) and unit/integration-test that the regulatory RPC's `OR org_id IS NULL` clause is scoped to `doc_type='regulatory'` rows only (already true via the existing `AND doc_type = 'regulatory'` clause — must be preserved verbatim when the functions are replaced) |
| RPC signature drift causing silent empty results (see Pitfall 2) | — (not strictly STRIDE, but a correctness/availability concern) | Sequence migration-then-deploy; add a live smoke check post-deploy |
| Supersession state corruption (a failed mid-ingest crash leaves two `active` documents with the same `document_key`, or a dangling `supersedes`/`superseded_by` pointer) | Tampering / Integrity | The immutability trigger + FK constraints (`ON DELETE CASCADE` on `chunks.regulatory_document_id`, not on `regulatory_documents` self-FKs) already close most of this; the ingest CLI should wrap the parent upsert + supersession flip + chunk delete/reinsert in a single transaction if the Supabase JS client supports it, or clearly document the multi-step non-transactional risk if it doesn't (the `@supabase/supabase-js` client does not expose multi-statement transactions directly — this may require a Postgres function (`RPC`) wrapping the whole ingest-write sequence to get atomicity, which is a real design decision the planner should make explicit rather than leaving as several independent `.insert()`/`.update()` calls) |

**Flag for planner:** the transactionality of the ingest CLI's multi-step write (parent upsert +
supersession flip + chunk delete + chunk reinsert) is NOT addressed by the BRIEF and is a genuine
open design gap — `@supabase/supabase-js` does not support ad-hoc multi-statement transactions from
a script; the safe options are (a) a single `SECURITY DEFINER` Postgres function that the CLI calls
via one `supabase.rpc(...)`, wrapping all writes in one transaction, or (b) accept non-atomic
multi-step writes with a documented partial-failure risk. Given this phase already writes several
new RPCs, wrapping the ingest write path as its own RPC is the more consistent choice architecturally
but is Claude's discretion per CONTEXT.md ("internal function/param naming not dictated by the
BRIEF").

## Summary

Phase 14.2.4 is a targeted wiring change on an already-functional system. The walkthrough engine, ghost-accept flow, and `resolved_items` write machinery all exist and work. The phase has three load-bearing sub-problems: (1) add a new `cta_tool` value and sync both enum sites; (2) make the forced `ask_user` dispatch also write `active_task` with the originating-finding snapshot embedded (D-01 + Risk B); (3) add a defer/skip affordance to `AskUserCard`. Everything else reuses existing machinery unchanged.

**Primary recommendation:** Implement in three waves — (Wave 1) enum widening + analyzer detection rule; (Wave 2) edge `ask_user` dispatch with mirrored `active_task` write + snapshot survival; (Wave 3) client CTA routing, label, focus, attribution read, and `AskUserCard` skip button.

## Priority 1: Partial-Resolution / acceptance_summary Machinery (D-08 watch-item 3)

### How `acceptance_summary` is computed today

`computeTerminalWrites` (verified: `src/hooks/useResolvedItemsWriteOnTerminal.ts:90-157`) iterates all `pending_edits` for a message. Once ALL edits for that message are in terminal state (`accepted | rejected | auto_rejected_stale`), it builds:

```
resolutionSummary = {
  accepted: count of 'accepted' edits,
  rejected: count of 'rejected' edits,
  stale:    count of 'auto_rejected_stale' edits,
}
```

`buildResolvedItemEntry` (`src/chat/resolved-items.ts:96-124`) sets `user_action: 'fixed'` when `accepted >= 1`, otherwise `'dismissed'`. The `acceptance_summary` field is always written with the exact counts.

### Does it support partial resolution already?

**Yes — by design.** The machinery is paragraph-level, not finding-level. A single `propose_edit` message produces N paragraph edits; the user can accept some and reject others. `resolutionSummary` captures the exact split. `user_action` is `'fixed'` as long as at least one edit was accepted.

**For the ask-then-fill case:** one `propose_edit` fills the placeholder values the model could map confidently. Any unmapped values stay as placeholder text in the accepted HTML. On the next analysis run, those remaining placeholders will re-surface as a finding because:
- The `section_content_hash_at_action` in the resolved_items entry reflects the post-accept HTML.
- `rebuildFilterSet` (`resolved-items.ts:136-155`) only hard-suppresses `dismissed` items — `fixed` items are NOT filtered client-side (14.2.3 fix). The edge prompt receives the resolved_items block as dedup hints only, and its rule is "do not re-emit if UNCHANGED" — if placeholders remain, content is effectively the same type of issue and Haiku will re-surface it.

**Conclusion:** No change needed to `acceptance_summary` machinery for partial resolution. The existing per-paragraph accept/reject model already handles it. What matters is that remaining placeholders appear in the accepted HTML so the next analysis detects them. `[VERIFIED: src/hooks/useResolvedItemsWriteOnTerminal.ts, src/chat/resolved-items.ts]`

## Priority 4: Enum Sync + Analyzer cta_tool Change (D-02, D-06, D-07)

### Two enum sites (verified)

**Edge** (`supabase/functions/analyze-proposal-gaps/index.ts:27`):
```typescript

```

**Client** (`src/types/chat.ts:190`):
```typescript

```

**Change required:** Add `'ask_user'` to both. They must widen together.

### Analyzer few-shot outputs — all hardcode `'propose_edit'` (verified: lines 121-136)

All four families (bracket, descriptive-noun, contact/address, TBD/marker) emit `cta_tool: 'propose_edit'` and `cta_label: 'Fix it'` or `'Draft it'`. Under D-06, all placeholder + missing findings must emit `cta_tool: 'ask_user'` and a label matching D-03 ("Provide info" / "Fill in").

**Four few-shot outputs to update:**
- Family 1 (gap, bracket): `cta_tool: 'propose_edit'` → `'ask_user'`; label → "Provide info"
- Family 2 (gap, descriptive-noun): same change
- Family 3 (missing, contact): same change; label → "Fill in"  
- Family 4 (missing, TBD/marker): same change; label → "Fill in"

**System prompt instruction lines to update:** The system prompt lists valid `cta_label` and `cta_tool` values on lines 97-98. Both must include the new values.

**D-07 description threading — threading mechanism (watch-item 2):**

The ask turn currently receives `[Action: ask_user] {title}` as the message text (`AIChatPanel.tsx:718`). The `cta_payload` is also sent in the request body (`:435`). The edge reads `cta_payload` to set `tool_choice` but does NOT inject the payload content into the model's prompt at ask time — it forces the tool and lets the model see the message history. The description therefore threads most effectively **via the message text**, not via payload, because the message text IS in the conversation history that the model reads. Recommended approach: at CTA-click time, send `[Action: ask_user] {title}: {description}` (append description to the message text). This requires no new edge wiring — the description rides the existing history-based context. Alternative (payload threading) requires wiring payload→prompt injection on the ask turn, which is net-new and risks the "specified-but-unwired" pattern D-05 guards against. `[VERIFIED: AIChatPanel.tsx:718, chat-with-jamo/index.ts:112-115]`

**D-06 detection rule placement:** Add a single `isNeedsValue(finding)` helper in the analyzer that returns `true` when `type === 'gap' || type === 'missing'` (v1 simplification). Needs-expansion (thin-but-present `gap` with substantive content) — the distinction between "gap with placeholder" vs "gap with thin content" must be made in the prompt/few-shots, not in a separate code branch, since Haiku classifies at emit time. The cleanest v1 implementation: instruct Haiku in the system prompt to emit `cta_tool: 'ask_user'` for all `gap` and `missing` types, and `propose_edit` only for `conflict` and `compliance`. This collapses the ask/draft decision into the type taxonomy Haiku already uses. `[VERIFIED: analyze-proposal-gaps/index.ts:86-137]`

## Common Pitfalls

### Pitfall 1: Snapshot Key Mismatch (Risk B — confirmed)
**What goes wrong:** `captureSnapshot` stores under `section_key:ask_user`; `takeSnapshot` at `propose_edit` arrival hardcodes `section_key:propose_edit`. Keys never match. `originating_action` is null. `resolved_items` has no attribution. Finding re-surfaces (violates AC-7).
**Root cause:** `ctaSnapshotMap.ts:19` uses `cta_tool` as part of the key; the fill tool differs from the click tool.
**How to avoid:** Do NOT rely on the in-memory Map for ask-then-fill attribution. Read the snapshot from `active_task.originating_snapshot` at `propose_edit` arrival instead. The in-memory Map path is still correct for direct `propose_edit` CTAs.
**Warning sign:** `resolved_items` entry has `originating_action_id: null` after an ask-then-fill cycle.

### Pitfall 2: Fire-and-Forget active_task Write (D-01 condition 3)
**What goes wrong:** Inheriting `set_focus`'s `void` (fire-and-forget) write pattern means the active_task may not exist when the user answers immediately (fast typist closes the race).
**Root cause:** The write is load-bearing for durable resume; fire-and-forget was acceptable for `set_focus` because the user must navigate, then type — the gap is wide. For `ask_user`, the card renders immediately and the user can answer before the write lands.
**How to avoid:** `await` the `supabase.from('chat_sessions').update(...)` in the needs-value `ask_user` dispatch block. `set_focus` stays fire-and-forget (do not change it).

### Pitfall 3: Auto-dismiss on ask_user CTA (D-09)
**What goes wrong:** The `propose_edit` auto-dismiss at `AIChatPanel:553-557` dismisses all `propose_edit`-tool actions for the section when an edit arrives. The equivalent block must NOT fire for `ask_user` CTAs — the finding must remain visible during the walkthrough so it re-surfaces if deferred.
**Root cause:** The existing code already guards this correctly (`a.cta_tool === 'propose_edit'` predicate, verified at `:554`). The risk is a future developer copying the auto-dismiss block for `ask_user`.
**How to avoid:** Verify the auto-dismiss predicate explicitly in Wave 0 tests. Never add `ask_user` to the auto-dismiss block.

### Pitfall 4: Enum Out-of-Sync Deployment
**What goes wrong:** Edge `PendingActionSchema` widened but client `ActionItemCtaTool` not (or vice versa). Findings with `cta_tool:'ask_user'` arrive on the client as `unknown`, breaking the CTA click handler.
**Root cause:** Two separate files, two separate deploy steps (edge functions must be deployed explicitly — not auto-deployed by GSD commit).
**How to avoid:** Widen both enums in the same plan. Add the Wave 0 enum-sync test. After deployment, verify with a live finding.

### Pitfall 5: Description Threading via Payload (D-07 watch-item 2)
**What goes wrong:** Analyst stores the enumerative description in `cta_payload`, but the edge does not inject payload content into the model's prompt context at the ask turn — it only uses payload to set `tool_choice`. The model asks a vague question.
**Root cause:** "Specified but unwired" — payload is passed but not read for prompt context.
**How to avoid:** Thread description via message text (append to `[Action: ask_user] {title}: {description}` at CTA-click). No edge wiring needed — message text is in conversation history the model reads.

## Open Questions

1. **`isNeedsValue` boundary for `gap` type.** D-06 routes all `gap` and `missing` to ask. But a `gap` finding can be "thin section with weak content" (needs-expansion, AI can fill) or "section-with-placeholders" (needs-value, only user can fill). In v1, the system prompt few-shots drive which type Haiku emits — the code-level `isNeedsValue` check just reads `type`. If Haiku mis-classifies a thin-content section as `gap` (it currently does, per existing few-shots), it will route to ask when `propose_edit` would be better. **Mitigation:** update the system prompt to distinguish the two gap subtypes explicitly, or accept that v1 asks for everything (D-06 rationale: wrong ask is minor annoyance; wrong draft is the bug being fixed).

2. **`originating_snapshot` field on `ActiveTask` type.** Adding this optional field to the `ActiveTask` interface requires a type change. The field is JSONB-stored and the migration does not need updating (it's already a JSONB column). The TypeScript interface change is the only required step. Confirm no TypeScript strict-mode issues with `OriginatingActionSnapshot` imported into the types file.

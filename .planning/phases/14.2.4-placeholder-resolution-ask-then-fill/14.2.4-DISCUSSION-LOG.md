## Detection rule — needs-value vs needs-expansion

| Option | Description | Selected |
|--------|-------------|----------|
| Per-finding semantic judgment | Haiku judges draftable-from-regulatory vs user-only per finding | |
| Placeholder-family → ask, missing/thin → draft | Per-type map | |
| **All placeholder + missing → ask; no AI-draft branch (v1)** | Collapse the decision; needs-expansion keeps propose_edit | ✓ |

**Decision (D-06):** Route ALL placeholder + missing findings to ask. **Why:** verified fact —
the fill path (`chat-with-jamo`) has NO access to RFP/protocol/assumptions (only section content
+ regulatory RAG; the `[PROPOSAL HISTORY]` channel is wired but never fed). The AI can't draft
study-specific content, so the draftable slice is narrow and the risk is asymmetric (wrongly
asking = annoyance; wrongly drafting = the silent-rewrite no-op this phase kills). Forward-compat:
single-place rule, `cta_tool` as routing primitive, don't bake a permanent ask-or-draft binary.

## Ask-flow mechanism — how the CTA reaches the ask while keeping durable resume

| Option | Description | Selected |
|--------|-------------|----------|
| **Force `ask_user` + mirror the `active_task` write** | One forced turn asks AND persists durable state | ✓ |
| `set_focus` + new client auto-continuation turn | Two round-trips, net-new continuation wiring | |

**Decision (D-01, amended from "route via set_focus"):** Force `ask_user`; mirror `set_focus`'s
`active_task` write into that dispatch. **Why:** verified — forcing `set_focus` stalls (forced
single tool can't also ask; no continuation wiring exists). The answer/resume path is
provenance-agnostic (edge re-reads `active_task` from the column), so a mirrored write resumes
identically. Four conditions locked: identical active_task shape (hard verify), client focus-set
at click, await the write (load-bearing state), `collected_inputs` is dead (feeds batching choice).
Risk B (snapshot orphan) composes into the same write — "one write, both jobs."

## Ask construction — what the ask carries (Area 2) + batched vs sequential (Area 3)

| Option (Area 2) | Description | Selected |

| Option (Area 3) | Description | Selected |
|--------|-------------|----------|
| **One batched `ask_user` per section** | One question lists all values → one answer → one fill | ✓ |
| Sequential one-at-a-time asks | Multi-turn; depends on dead `collected_inputs` | |

**Decisions (D-07, D-08):** Thread the existing description (Option C); one batched ask per
section. **Key realization:** the analyzer already enumerates needed values in the description —
this is wiring existing work to the ask turn, not new extraction. Batching sidesteps the dead
`collected_inputs` problem AND is better UX. Watch-items recorded: enumerative-description prompt
quality; threading via message-vs-payload must be read by the edge; robust partial-answer mapping;
readable numbered question; partial-fill writes partial `resolved_items` (remaining re-surface).

## Defer / abandon semantics (Area 4)

| Option | Description | Selected |
|--------|-------------|----------|
| **Defer via existing stop-walkthrough; defer ≠ dismiss** | No resolved write → re-surfaces; dismiss stays separate | ✓ |
| Map skip → dismiss | Collapses the two intents | |

**Decision (D-09):** Abandoning an ask defers (re-surfaces), never writes `'fixed'`. Reuses
`onStopWalkthrough` (already discards active_task, no resolved write). Skip affordance added to
`AskUserCard` in v1, labeled as defer ("I don't have this yet"), not dismiss. No bundled
"dismiss instead" at stop time. Load-bearing invariant: abandon never marks fixed.

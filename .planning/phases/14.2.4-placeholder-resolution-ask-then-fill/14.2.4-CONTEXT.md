# Phase 14.2.4: Placeholder Resolution (Ask-Then-Fill) - Context

**Gathered:** 2026-06-11
**Status:** Decisions locked — open questions remain for interactive discuss before planning

<domain>
## Phase Boundary

Fix the placeholder no-op. Findings that flag unfilled placeholder text ("CRO legal entity
name", "investigational product name", "Name and title of RFP contact at…") currently route
to a forced `propose_edit`, which makes the AI rewrite the section and reproduce the same
placeholder — because the AI has no source for a value only the user knows. This phase routes
**needs-value** findings through the existing walkthrough machinery (`set_focus` → `ask_user`
→ `active_task` → `propose_edit` → ghost-accept) so Jamo asks the user for the value, then
fills it.

This is the **resolution** layer. The **detection** layer (Phase 14.2.3) is done and out of
scope. The walkthrough engine (Phase 14.2 Part B) already exists and is out of scope to
rebuild — this phase only re-routes findings into it.

**In scope:** the needs-value `cta_tool` tag, both-enum widening, CTA routing + labeling,
originating-snapshot survival across the ask hop, reuse of the existing walkthrough /
`ask_user` / `active_task` / ghost-accept machinery.

**Out of scope:** auto-fill (blocked on a future org-profile data phase — design must not
preclude it, but build nothing); any new conversational/walkthrough engine (the existing one
works); changes to needs-expansion "Fix it" behavior (works, leave it); changes to the
`tool_choice` forcing logic (works — only the emitted `cta_tool` value changes).

</domain>

<verified_facts>
## Verified Code Facts (ground truth — build on these, do not re-investigate)

Confirmed against the code on 2026-06-11. These are the foundation of the locked decisions.

1. **The needs-value/needs-expansion distinction does not exist yet.** Finding schema is
   `type | section_key | title | description | priority | cta_label | cta_tool | cta_payload`
   (`supabase/functions/analyze-proposal-gaps/index.ts:19-29`). `type` is
   `gap | missing | conflict | compliance`. A placeholder finding tags as `gap`/`missing` —
   but so does a thin-section finding, so `type` cannot carry the distinction. Every
   placeholder family hardcodes `cta_tool: 'propose_edit'`. The tag is net-new; cheapest home
   is a new `cta_tool` value.

2. **CTA routing is forced and the mechanism already supports the fix.** Analyzer assigns
   `cta_tool` → client `onCtaClick` passes it as `forcedTool`
   (`src/components/AIChatPanel.tsx:713-718` → request body `:435`) → edge sets
   `tool_choice: {type:'tool', name: forced_tool}`
   (`supabase/functions/chat-with-jamo/index.ts:112-115`). `ask_user` and `set_focus` are
   already registered tools (`index.ts:16-22`), so forcing one of them already works
   mechanically. Fix = analyzer emits a different `cta_tool` for needs-value findings + the
   two enums widen. No change to the forcing logic.

3. **The walkthrough machinery works end-to-end.** `set_focus` writes
   `active_task{stage:'gathering_inputs'}` (`chat-with-jamo/index.ts:203-230`); `ask_user`
   returns the question; `propose_edit` advances `gathering_inputs → drafting` (`:177-184`);
   `active_task` is injected into the prompt (`:90`) and read with 7-day expiry (`:50-82`).
   Client renders `AskUserCard` (`AIChatPanel.tsx:932-963`); answering calls
   `handleSendMessage(text)` (`:960`) → edge re-reads `active_task` → model continues.
   Hydrated on mount + Realtime (`:243, :292`); `ResumeTaskBanner` exists (`:780`). It is
   wired and functional — today's CTA bypasses it (forces `propose_edit` directly), it is not
   broken.

4. **`organizations` has no auto-fill source.** Columns are
   `id, name, slug, plan, is_active, feature_flags, created_at, updated_at`
   (`supabase/migrations/20260305000002_organizations.sql`). `name` is a display name. No
   legal entity name, no address, no contacts. The placeholders that dominate (Family-2 "CRO
   legal entity name", Family-3 address/contact) have no source in the table.

5. **Resolution write + accept flow is automatic and reused.** A fill is a normal
   `propose_edit`: arrival → `materializePendingEdits` → ghost decorations + `EditSummaryCard`
   Accept/Reject (`AIChatPanel.tsx:528-547, :840-869`). User accepts (not auto-applied).
   `resolved_items` is written automatically by `useResolvedItemsWriteOnTerminal`
   (`AIChatPanel.tsx:179-192`; `src/hooks/useResolvedItemsWriteOnTerminal.ts`) once all edits
   hit terminal state. The only new wiring needed: the originating-finding snapshot
   (`captureSnapshot`, `ctaSnapshotRef`, `AIChatPanel.tsx:717`) must survive the
   ask→answer→propose_edit hop.

</verified_facts>

<decisions>
## Implementation Decisions (Locked)

### Routing & detection
- **D-01: Ask-then-fill via `set_focus`, NOT bare `ask_user`.** Needs-value findings route to
  `set_focus`, which starts the walkthrough and writes durable `active_task` state; Jamo asks
  for the value, the user answers, Jamo `propose_edit`s with the real value, the user accepts
  the ghost edits. A bare `ask_user` creates no `active_task`, so resume-after-reload would
  lean only on chat history — the fragile, stateless behavior the resume-on-reload design
  explicitly rejected. `set_focus` feeds the resume machinery the durable state it was built
  to consume.
- **D-02: The needs-value tag is a new `cta_tool` value, widened in BOTH enum locations.** The
  analyzer emits `cta_tool: 'set_focus'` for needs-value findings. The enum is defined in two
  places that MUST stay in sync: edge `PendingActionSchema`
  (`analyze-proposal-gaps/index.ts:27`) and client `ActionItemCtaTool` (`src/types/chat.ts:190`).
  Both widen together. (Primary risk surface — see Risks.)
- **D-05: No model-decides routing.** Do not implement `tool_choice: auto` + a prompt rule.
  That reintroduces the nondeterminism the forced-tool code exists to prevent, and its failure
  mode is the exact bug being fixed (model rewrites with the placeholder intact). The
  ask-vs-fill decision is made deterministically at detection time via the `cta_tool` tag.

### UX
- **D-03: CTA label differs by actor.** Needs-expansion findings keep "Fix it" (the AI fixes
  it). Needs-value findings use a verb signaling the user supplies the value — "Provide info" /
  "Fill in". Exact copy is a discuss detail; the principle (different verb because different
  actor) is locked.

### Scope guard
- **D-04: Auto-fill is OUT for v1 and is NOT a quick follow-on.** `organizations` has no legal
  entity name, address, or contact data (fact #4). Auto-fill is **not deferred-but-easy — it is
  blocked on net-new data infrastructure** (an org-profile table with legal name / address /
  contacts). It is a separate future phase with a data-modeling prerequisite, not a polish
  layer. **Design constraint:** the fill stage must be built so it *could* accept a looked-up
  value through the same path later — i.e., the fill step takes a value regardless of whether it
  came from the user or a future lookup — but no lookup is built now.

### Claude's Discretion
- Exact CTA copy ("Provide info" vs "Fill in") — within D-03's principle.
- Whether to fix the cosmetic `set_focus` `section_title = section_key` TODO
  (`chat-with-jamo/index.ts:216`) in this phase (recommended, since the phase already touches
  this path) — see open questions.

</decisions>

<risks>
## The Real Risk Surface

The routing change itself is small (fact #2 — forcing `set_focus` already works). The phase
earns its keep in two places:

### A. Two-place enum sync (D-02)
The `cta_tool` enum must widen in both `PendingActionSchema` (edge `:27`) and
`ActionItemCtaTool` (client `chat.ts:190`). If only one is updated, findings with the new
`cta_tool` fail validation on the unsynced side. **Explicit verification:** a finding carrying
the new needs-value `cta_tool` must validate on BOTH the edge and the client.

### B. Originating-finding snapshot survival across the hop (highest risk)
In a normal `propose_edit`, the snapshot is captured at CTA-click (`ctaSnapshotRef`, `:717`)
and the `propose_edit` arrives directly, so `useResolvedItemsWriteOnTerminal` attributes the
terminal write to the right finding. In ask-then-fill there is an `ask_user` round-trip in
between: CTA-click → `set_focus` → `ask_user` question → user answer → `propose_edit` fill. The
snapshot must persist across that detour so the terminal `resolved_items` write attributes to
the correct placeholder finding.

If the snapshot does not survive the hop, the fill works but `resolved_items` either doesn't
write or attributes to the wrong finding — resurrecting the re-surfacing bug for placeholders
specifically (the finding comes back after the user addressed it). Needs explicit design
attention and its own test: complete a full ask-then-fill cycle and assert the `resolved_items`
entry exists and references the originating placeholder finding.

</risks>

<deliverables>
## Deliverables (for planning to scope)

- **Analyzer:** emit `cta_tool: 'set_focus'` for needs-value findings (placeholder +
  missing-scaffolding); keep `propose_edit` for needs-expansion (thin section, weak rationale).
- **Enums:** widen `cta_tool` in both `PendingActionSchema` and `ActionItemCtaTool`.
- **CTA label:** needs-value findings render "Provide info" / "Fill in".
- **Snapshot persistence:** ensure `ctaSnapshotRef` (or equivalent) survives CTA-click →
  `set_focus` → `ask_user` → answer → `propose_edit`, so the terminal `resolved_items` write
  attributes correctly.
- **Verification:** confirm the end-to-end flow uses the existing `set_focus` / `ask_user` /
  `active_task` / ghost-accept machinery without modification (it should, per facts #3 and #5).

</deliverables>

<acceptance_criteria>
## Acceptance Criteria

1. A placeholder finding's CTA initiates an ask-then-fill walkthrough (asks for the value)
   rather than a no-op rewrite.
2. The user provides the value; Jamo `propose_edit`s with the real value; the user accepts
   ghost edits; the placeholder is replaced with the user's actual content.
3. A finding carrying the new needs-value `cta_tool` validates on both the edge
   (`PendingActionSchema`) and the client (`ActionItemCtaTool`).
4. Completing an ask-then-fill cycle writes a `resolved_items` entry that references the
   originating placeholder finding (snapshot survived the hop).
5. A half-completed ask-then-fill walkthrough survives reload via `active_task` /
   `ResumeTaskBanner` and can be continued (durable resume, not chat-history-only).
6. Needs-expansion findings (thin section) still route to `propose_edit` and behave exactly as
   before.
7. The placeholder finding does not re-surface after being addressed via ask-then-fill
   (resolved_items attribution correct — guards against the re-surfacing bug for placeholders).

</acceptance_criteria>

<open_questions>
## Open Questions for Discuss (resolve before planning)

- **Which finding types get `set_focus` routing?** Placeholder findings clearly. Does `missing`
  (scaffolding / section-not-started) also route to ask-then-fill, or is some `missing` content
  the AI can draft from RFP/protocol context (needs-expansion)? The analyzer needs a clear rule
  for needs-value vs needs-expansion — this may require reasoning per-finding rather than
  per-type.
- **What does the analyzer pass into the ask flow?** When a section has multiple placeholders,
  does the finding carry the specific values needed ("legal entity name", "corporate address",
  "RFP contact name") so the ask is targeted rather than generic? Pre-extracting these at
  detection time makes the ask far better. Confirm scope.
- **One ask per value vs batched multi-field ask.** A section with five placeholders — five
  questions or one multi-field prompt? Determined by what `ask_user` / `AskUserCard` currently
  support. Lean batched; confirm feasibility against the existing card.
- **The `set_focus` `section_title = section_key` TODO (`chat-with-jamo/index.ts:216`).**
  Cosmetic (snake_case title in one spot). Fix in this phase for quality, or leave the TODO?
  Recommend fixing since this phase already touches the walkthrough path.
- **User doesn't know the value either.** User clicks "Provide info", is asked, doesn't have the
  value handy. Can they defer/skip without the finding being marked resolved? Should map to the
  existing dismiss-vs-resolve distinction.

</open_questions>

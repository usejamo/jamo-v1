# Phase 14.2.4: Placeholder Resolution (Ask-Then-Fill) - Context

**Gathered:** 2026-06-11
**Status:** Decisions locked — open questions remain for interactive discuss before planning

<domain>
## Phase Boundary

Fix the placeholder no-op. Findings that flag unfilled placeholder text ("CRO legal entity
name", "investigational product name", "Name and title of RFP contact at…") currently route
to a forced `propose_edit`, which makes the AI rewrite the section and reproduce the same
placeholder — because the AI has no source for a value only the user knows. This phase routes
**needs-value** findings through the existing walkthrough machinery (`set_focus` → `ask_user`
→ `active_task` → `propose_edit` → ghost-accept) so Jamo asks the user for the value, then
fills it.

This is the **resolution** layer. The **detection** layer (Phase 14.2.3) is done and out of
scope. The walkthrough engine (Phase 14.2 Part B) already exists and is out of scope to
rebuild — this phase only re-routes findings into it.

**In scope:** the needs-value `cta_tool` tag, both-enum widening, CTA routing + labeling,
originating-snapshot survival across the ask hop, reuse of the existing walkthrough /
`ask_user` / `active_task` / ghost-accept machinery.

**Out of scope:** auto-fill (blocked on a future org-profile data phase — design must not
preclude it, but build nothing); any new conversational/walkthrough engine (the existing one
works); changes to needs-expansion "Fix it" behavior (works, leave it); changes to the
`tool_choice` forcing logic (works — only the emitted `cta_tool` value changes).

</domain>

<verified_facts>
## Verified Code Facts (ground truth — build on these, do not re-investigate)

Confirmed against the code on 2026-06-11. These are the foundation of the locked decisions.

1. **The needs-value/needs-expansion distinction does not exist yet.** Finding schema is
   `type | section_key | title | description | priority | cta_label | cta_tool | cta_payload`
   (`supabase/functions/analyze-proposal-gaps/index.ts:19-29`). `type` is
   `gap | missing | conflict | compliance`. A placeholder finding tags as `gap`/`missing` —
   but so does a thin-section finding, so `type` cannot carry the distinction. Every
   placeholder family hardcodes `cta_tool: 'propose_edit'`. The tag is net-new; cheapest home
   is a new `cta_tool` value.

2. **CTA routing is forced and the mechanism already supports the fix.** Analyzer assigns
   `cta_tool` → client `onCtaClick` passes it as `forcedTool`
   (`src/components/AIChatPanel.tsx:713-718` → request body `:435`) → edge sets
   `tool_choice: {type:'tool', name: forced_tool}`
   (`supabase/functions/chat-with-jamo/index.ts:112-115`). `ask_user` and `set_focus` are
   already registered tools (`index.ts:16-22`), so forcing one of them already works
   mechanically. Fix = analyzer emits a different `cta_tool` for needs-value findings + the
   two enums widen. No change to the forcing logic.

3. **The walkthrough machinery works end-to-end.** `set_focus` writes
   `active_task{stage:'gathering_inputs'}` (`chat-with-jamo/index.ts:203-230`); `ask_user`
   returns the question; `propose_edit` advances `gathering_inputs → drafting` (`:177-184`);
   `active_task` is injected into the prompt (`:90`) and read with 7-day expiry (`:50-82`).
   Client renders `AskUserCard` (`AIChatPanel.tsx:932-963`); answering calls
   `handleSendMessage(text)` (`:960`) → edge re-reads `active_task` → model continues.
   Hydrated on mount + Realtime (`:243, :292`); `ResumeTaskBanner` exists (`:780`). It is
   wired and functional — today's CTA bypasses it (forces `propose_edit` directly), it is not
   broken.

4. **`organizations` has no auto-fill source.** Columns are
   `id, name, slug, plan, is_active, feature_flags, created_at, updated_at`
   (`supabase/migrations/20260305000002_organizations.sql`). `name` is a display name. No
   legal entity name, no address, no contacts. The placeholders that dominate (Family-2 "CRO
   legal entity name", Family-3 address/contact) have no source in the table.

5. **Resolution write + accept flow is automatic and reused.** A fill is a normal
   `propose_edit`: arrival → `materializePendingEdits` → ghost decorations + `EditSummaryCard`
   Accept/Reject (`AIChatPanel.tsx:528-547, :840-869`). User accepts (not auto-applied).
   `resolved_items` is written automatically by `useResolvedItemsWriteOnTerminal`
   (`AIChatPanel.tsx:179-192`; `src/hooks/useResolvedItemsWriteOnTerminal.ts`) once all edits
   hit terminal state. The only new wiring needed: the originating-finding snapshot
   (`captureSnapshot`, `ctaSnapshotRef`, `AIChatPanel.tsx:717`) must survive the
   ask→answer→propose_edit hop.

6. **The fill-time context is weak — the AI cannot see this study's source documents.** At
   `propose_edit` time, `chat-with-jamo` assembles only: (1) the current section content
   (placeholder-laden HTML), (2) other sections in this proposal (`context.ts:27-29`), (3) RAG
   `[REGULATORY CONTEXT]` — top-5 chunks from the org's regulatory KB (ICH/FDA),
   `doc_type='regulatory'`, (4) RAG `[PROPOSAL HISTORY]` — wired to read `doc_type='proposal'`
   chunks but **never fed** (the only writer to `chunks` is `scripts/ingest-regulatory.ts`, so
   this block is always `"(No relevant proposal history found)"`), (5) chat history +
   `active_task.collected_inputs`. It does **NOT** read the uploaded RFP or protocol
   (`document_extracts` — never embedded, never read by chat; grep: zero hits) nor the extracted
   assumptions (those feed `generate-proposal-section`, not chat). RAG K-values per tool live in
   `chat-with-jamo/rag.ts:8-16`. Consequence: at fill time the AI can produce generic regulatory
   boilerplate but has zero source for anything study-specific (eligibility, endpoints, dosing,
   indication, names, contacts, dates) — it would hallucinate or re-emit the placeholder. This is
   the basis for D-06.

7. **Forcing `set_focus` stalls; the typed walkthrough works only under auto tool-choice.**
   Under forced `tool_choice: {type:'tool', name:'set_focus'}` the model emits ONLY `set_focus`
   on that turn — it cannot also call `ask_user`. After the `set_focus` tool_result the client
   appends a `tool-set-focus` message and stops; nothing watches `tool-set-focus`/`active_task`
   to fire a follow-on turn (`onContinueWalkthrough`, `AIChatPanel.tsx:780`, only *scrolls* to an
   existing ask). So fact #3's "walkthrough works end-to-end" holds under **auto** tool-choice
   (the typed path naturally chains `set_focus`→`ask_user` across turns); **forcing** a single
   tool for the CTA defeats that chain. This is why D-01 forces `ask_user` (not `set_focus`).

8. **The CTA snapshot Map orphans across a tool change (Risk B, confirmed cause).**
   `captureSnapshot` stores under `makeCtaKey({section_key, cta_tool})`
   (`src/chat/ctaSnapshotMap.ts:19,34`); `takeSnapshot` at `propose_edit` arrival looks up
   `section_key + 'propose_edit'` (`AIChatPanel.tsx:503-506`). For a needs-value finding the
   click tool is `ask_user`, so the snapshot is stored under `…:ask_user` and never retrieved by
   the `…:propose_edit` lookup → `originating_action` null → resolved_items mis-attributes →
   finding re-surfaces (violates AC-7). The in-memory Map also would not survive a
   mid-walkthrough reload. Fix: persist the snapshot in `active_task` (see Risk B).

<decisions>
## Implementation Decisions (Locked)

### Routing & detection
- **D-01 (AMENDED): Ask-flow mechanism — force `ask_user` + mirror the `active_task` write.**
  A needs-value CTA forces `ask_user` directly, AND the needs-value `ask_user` dispatch mirrors
  the `active_task` write that `set_focus` performs today (`chat-with-jamo/index.ts:211-229`).
  One forced turn both asks the question and establishes durable walkthrough state — one
  round-trip, no continuation wiring.
  - **Why amended (was: route via `set_focus`):** forcing `set_focus` is broken under forced
    tool-choice — the model can emit only `set_focus` on that turn (cannot also call `ask_user`),
    and no continuation wiring exists to fire the follow-on ask, so the flow dead-ends at "focus
    changed, silence" (verified fact #7). The original decision's *intent* — durable resume, not
    chat-history-only — is preserved; only the mechanism changes.
  - **Why this works:** the answer/resume path is provenance-agnostic. The answer click calls
    `handleSendMessage(text)` with no forced tool → `tool_choice: auto`; the edge re-reads
    `active_task` from the `chat_sessions` column independent of the client
    (`index.ts:50-82`) and cannot distinguish a row written by the typed `set_focus → ask_user`
    chain from one written by a forced `ask_user` with a mirrored write. `[ACTIVE WALKTHROUGH]`
    is injected, the model sees the answer in history, calls `propose_edit` to fill, and the edge
    advances `gathering_inputs → drafting` (`:177-184`) — identical to the typed path.
  - **Rejected alternative:** keep `set_focus` + build a client auto-continuation turn — two
    round-trips and net-new continuation wiring of the same specified-but-unwired class that has
    caused defects here before (the `triggerAnalysis` stub). Spending effort building a mechanism
    to defend a routing choice whose only purpose was durability — when durability is achievable
    in one turn — is the wrong trade.

  **Four conditions (all required):**
  1. **Identical `active_task` shape — hard verification requirement.** The forced-`ask_user`
     write MUST produce a structurally identical `active_task` object to `set_focus`'s
     (`index.ts:212-224` — `type, status, section_key, section_title, stage, collected_inputs`,
     and all other fields). The provenance-agnostic property only holds if the shape matches;
     client hydration (`AIChatPanel.tsx:243`) and `ResumeTaskBanner` key off `status:'active'`
     and the structure. **Verification check:** the `active_task` written by the needs-value
     `ask_user` path is structurally identical to the `set_focus` path's write. This single
     condition is what makes the whole mechanism work.
  2. **Client focus-set at CTA-click.** `set_focus` switched the working section; a bare forced
     `ask_user` does not. The model still targets the right section via `active_task.section_key`
     (`propose_edit` can target any `section_key`; all sections are in `[OTHER SECTIONS]`), so
     attribution/filling work without it — but for correct `[CURRENT SECTION]` context and
     coherent UX, the CTA-click handler must also set `activeSectionKey = action.section_key`
     client-side. Trivial; include it.
  3. **Await the `active_task` write in the needs-value path.** `set_focus`'s write is
     fire-and-forget today; do NOT inherit that here. This is load-bearing resume state for a
     flow whose entire value is durable resume — await the write to eliminate the race rather
     than relying on the human read-then-type gap. Same stance as the flush-then-hash decision
     (14.2.3 D-6): when state is load-bearing for a durability guarantee, make the window not
     exist rather than tolerating a usually-safe race.
  4. **`collected_inputs` is dead — feeds the Area 3 decision.** It is initialized to `{}` and
     nothing ever writes answers into it; resume leans entirely on chat history (the answer is a
     persisted `proposal_chats` row reloaded on mount). Fine for a single-field ask. For a
     batched multi-field ask the model tracks answered-vs-pending via history, not structured
     state — history-dependent and more fragile. **Real input to Area 3:** batched multi-field
     asks rely on history-based progress tracking unless `collected_inputs` population is wired
     (net-new). May tilt Area 3 toward single-field for v1, or toward wiring `collected_inputs`
     if batched matters.
- **D-02: The needs-value tag is a new `cta_tool` value, widened in BOTH enum locations.** The
  analyzer emits `cta_tool: 'set_focus'` for needs-value findings. The enum is defined in two
  places that MUST stay in sync: edge `PendingActionSchema`
  (`analyze-proposal-gaps/index.ts:27`) and client `ActionItemCtaTool` (`src/types/chat.ts:190`).
  Both widen together. (Primary risk surface — see Risks.)
- **D-05: No model-decides routing.** Do not implement `tool_choice: auto` + a prompt rule.
  That reintroduces the nondeterminism the forced-tool code exists to prevent, and its failure
  mode is the exact bug being fixed (model rewrites with the placeholder intact). The
  ask-vs-fill decision is made deterministically at detection time via the `cta_tool` tag.
- **D-06: Detection rule — ALL placeholder + missing findings route to ask; no AI-drafting
  branch in v1.** The analyzer emits `cta_tool: 'set_focus'` for *all* placeholder and missing
  findings. Needs-expansion findings (thin-but-present sections with weak content the AI can
  strengthen from regulatory context + sibling sections) keep `propose_edit`. Everything that
  flags an unfilled placeholder or unstarted/scaffolding content routes to ask.
  - **Why:** fill-time context is weak (fact #6) — the AI can't see this study's RFP/protocol,
    so it cannot draft study-specific content. The only findings it can fill well are the narrow
    slice needing generic boilerplate.
  - **Why route ALL rather than per-finding judgment:** the risk is asymmetric. Wrongly asking is
    a minor annoyance; wrongly drafting reproduces the exact silent-rewrite no-op this phase
    exists to kill. With the draftable slice this narrow and the downside this lopsided, collapse
    the decision — route everything placeholder/missing to ask.
  - **Forward-compatibility constraint (critical):** this is a v1 simplification gated on weak
    fill-time context, NOT permanent. (a) The v1 rule must live in ONE clearly-scoped place in the
    analyzer — a single "is this needs-value?" determination that currently returns true for all
    placeholder/missing findings; do not scatter the logic. (b) The `cta_tool` tag is the routing
    primitive — when document context is later wired in, the only change is which findings emit
    `set_focus` vs `propose_edit`; the walkthrough, ask-then-fill flow, snapshot survival, and
    resolved_items attribution all stay. (c) Do NOT design the tag as a permanent binary that
    assumes a finding is either ask-or-draft forever — a future "draft-with-embedded-asks" hybrid
    (AI drafts from the protocol but asks for study-specific holes within one walkthrough) must be
    able to layer on without re-architecting the tag.

### Ask construction (Areas 2 & 3)
- **D-07: Targeted ask via the analyzer's existing description (Option C) — do NOT add a
  structured field schema.** The analyzer already enumerates the specific needed values in the
  finding `description` (e.g. *"uses descriptive-noun placeholders ('investigational product
  name', 'CRO legal entity name')"*). Thread that description through to the `ask_user` turn so
  the question is targeted. Rejected: Option A (new structured `needed_values[]` schema —
  re-derives what the description already contains) and Option B (pass only `section_key`, let
  the model re-spot placeholders — discards the analyzer's work and is weak for exactly the prose
  Family-2 cases). The ask quality *inherits directly from the description*.
  - **Watch-item 1 (prompt quality):** confirm needs-value descriptions are consistently
    *enumerative* (list the specific values), not vague ("this section has placeholders"). A
    vague description yields a vague ask. Flag any non-enumerative descriptions as an analyzer
    prompt-quality fix (`analyze-proposal-gaps`).
  - **Watch-item 2 (threading mechanism — must verify, not assume):** decide explicitly whether
    the description threads via the **message text** or **`cta_payload`**, and verify the edge
    actually reads it into the model's context at the ask turn. Payload is cleaner, but today the
    ask turn receives `[Action: ask_user] {title}` (title only — `AIChatPanel.tsx:718`); if the
    edge reads only message text, payload-threading needs that read wired too — otherwise the
    description sits in a payload nobody reads (the specified-but-unwired pattern to avoid).
- **D-08: One batched `ask_user` question per section (Area 3).** A section with N placeholders
  produces ONE `ask_user` question listing all needed values → user answers in one free-text
  message (`AskUserCard` is a single free-text input, `AIChatPanel.tsx:940`) → ONE `propose_edit`
  fills them all. Batching wins for **two** reasons: (a) it sidesteps the dead `collected_inputs`
  problem entirely (no multi-turn progress to track, so the fragility never arises — avoids both
  wiring `collected_inputs` and accepting history-based fragility), and (b) better UX (user sees
  all holes at once, fills in one pass vs drip-fed one field at a time).
  - **Watch-item 1 (robust answer→value mapping):** the model maps the free-text answer back to
    values from context. Handle partial / out-of-order / ambiguous answers gracefully — fill what
    maps confidently, leave the rest as placeholders (which correctly re-surface as a finding next
    analysis). Never let a partial answer produce a confident-but-wrong fill.
  - **Watch-item 2 (question formatting):** format the batched question as a numbered/bulleted
    list of needed values (more answerable than a run-on sentence) for the realistic max N.
  - **Watch-item 3 (partial resolution → resolved_items):** confirm the
    `acceptance_summary`/partial-resolution machinery from earlier decisions applies to the
    batched-ask fill, not just the per-paragraph `propose_edit` case it was designed for. If the
    user provides 3 of 5 values and `propose_edit` fills those three, the finding is *partially*
    addressed and the remaining two must re-surface.

### UX
- **D-03: CTA label differs by actor.** Needs-expansion findings keep "Fix it" (the AI fixes
  it). Needs-value findings use a verb signaling the user supplies the value — "Provide info" /
  "Fill in". Exact copy is a discuss detail; the principle (different verb because different
  actor) is locked.

### Scope guard
- **D-04: Auto-fill is OUT for v1 and is NOT a quick follow-on.** `organizations` has no legal
  entity name, address, or contact data (fact #4). Auto-fill is **not deferred-but-easy — it is
  blocked on net-new data infrastructure** (an org-profile table with legal name / address /
  contacts). It is a separate future phase with a data-modeling prerequisite, not a polish
  layer. **Design constraint:** the fill stage must be built so it *could* accept a looked-up
  value through the same path later — i.e., the fill step takes a value regardless of whether it
  came from the user or a future lookup — but no lookup is built now.

<risks>
## The Real Risk Surface

The routing change itself is small (fact #2 — forcing `set_focus` already works). The phase
earns its keep in two places:

### A. Two-place enum sync (D-02)
The `cta_tool` enum must widen in both `PendingActionSchema` (edge `:27`) and
`ActionItemCtaTool` (client `chat.ts:190`). If only one is updated, findings with the new
`cta_tool` fail validation on the unsynced side. **Explicit verification:** a finding carrying
the new needs-value `cta_tool` must validate on BOTH the edge and the client.

### B. Originating-finding snapshot survival across the hop (highest risk)
In a normal `propose_edit`, the snapshot is captured at CTA-click (`ctaSnapshotRef`, `:717`)
and the `propose_edit` arrives directly, so `useResolvedItemsWriteOnTerminal` attributes the
terminal write to the right finding. In ask-then-fill there is an `ask_user` round-trip in
between: CTA-click → forced `ask_user` → question → user answer → `propose_edit` fill. The
snapshot must persist across that detour.

**Confirmed cause (fact #8):** the in-memory snapshot Map keys by `section_key:cta_tool`. The
needs-value click tool is `ask_user`, but `takeSnapshot` at `propose_edit` arrival looks up
`section_key:propose_edit` — the keys don't match, so the snapshot is orphaned,
`originating_action` is null, `resolved_items` mis-attributes, and the placeholder finding
re-surfaces (violates AC-7). The in-memory Map also wouldn't survive a mid-walkthrough reload.

**Fix (composes with D-01 — "one write, both jobs"):** persist the originating snapshot inside
`active_task` — the same write that D-01 mirrors for durable resume also carries the snapshot.
It then survives both the ask→answer→fill hop and a mid-walkthrough reload; the terminal
`resolved_items` write reads attribution from `active_task` rather than the ephemeral Map. One
`active_task` write does both jobs (durable resume state + attribution).

**Test:** complete a full ask-then-fill cycle (including a mid-walkthrough reload) and assert the
`resolved_items` entry exists and references the originating placeholder finding.

</risks>

<acceptance_criteria>
## Acceptance Criteria

1. A placeholder finding's CTA initiates an ask-then-fill walkthrough (asks for the value)
   rather than a no-op rewrite.
2. The user provides the value; Jamo `propose_edit`s with the real value; the user accepts
   ghost edits; the placeholder is replaced with the user's actual content.
3. A finding carrying the new needs-value `cta_tool` validates on both the edge
   (`PendingActionSchema`) and the client (`ActionItemCtaTool`).
4. Completing an ask-then-fill cycle writes a `resolved_items` entry that references the
   originating placeholder finding (snapshot survived the hop).
5. A half-completed ask-then-fill walkthrough survives reload via `active_task` /
   `ResumeTaskBanner` and can be continued (durable resume, not chat-history-only).
6. Needs-expansion findings (thin section) still route to `propose_edit` and behave exactly as
   before.
7. The placeholder finding does not re-surface after being addressed via ask-then-fill
   (resolved_items attribution correct — guards against the re-surfacing bug for placeholders).
8. A batched ask is one `ask_user` question listing all needed values; the user's single answer
   fills the mapped values via one `propose_edit`. A **partial** answer (e.g. 3 of 5 values) fills
   only what maps confidently, leaves the rest as placeholders, and those remaining values
   re-surface as a finding on the next analysis (partial-resolution `acceptance_summary` applies).

</acceptance_criteria>

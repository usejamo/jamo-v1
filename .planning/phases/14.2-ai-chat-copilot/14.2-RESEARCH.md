## Summary

Phase 14.2 extends the 14.1 AI chat foundation in two sequential parts. Part A migrates diff review from the chat panel into the section editor using ProseMirror Decorations, eliminating three structural bugs (cramped surface, scroll corruption, insertion order corruption). Part B activates proactive co-pilot behavior: a server-generated action queue, Haiku-powered gap/conflict detection, multi-turn walkthroughs, and resume-on-reload persistence.

The core technical challenge in Part A is implementing a ProseMirror plugin that holds state external to the document, renders visual overlays (widget + node decorations), maps those overlays correctly through user edits, and dispatches back to a React context reducer — all without creating a render loop. The existing `PlaceholderMark` extension in this codebase already demonstrates the `addProseMirrorPlugins` + `appendTransaction` pattern and serves as the direct reference implementation.

Part B is primarily Supabase Realtime subscription management, a new Deno edge function, and UI state orchestration. The existing `chat-with-jamo` edge function structure provides the blueprint; `analyze-proposal-gaps` follows the same non-streaming `messages.create()` pattern from the AI-SPEC.

**Primary recommendation:** Build Part A's `PendingEditsPlugin` using the same `Plugin` + `PluginKey` from `@tiptap/pm/state` pattern already used in `PlaceholderMark.ts`, with `addProseMirrorPlugins()` in a standalone `Extension.create()`. Use extension `options` to pass the `dispatch` function and workspace state into plugin scope. Map decorations via `DecorationSet.map(tr.mapping, tr.doc)` in the plugin's `state.apply` method.

## Pattern 1: TipTap Extension with ProseMirror Plugin (VERIFIED against PlaceholderMark.ts)

The existing `PlaceholderMark.ts` is the canonical reference. The pattern for `PendingEditsPlugin`:

```typescript
// src/editor/plugins/pendingEdits/PendingEditsPlugin.ts
import { Extension } from '@tiptap/core'
import { Plugin, PluginKey } from '@tiptap/pm/state'
import { DecorationSet } from '@tiptap/pm/view'
import type { PendingEdit } from '../../types/workspace'
import type { WorkspaceDispatch } from '../../context/SectionWorkspaceContext'
import { buildDecorations } from './decorations'

export const PendingEditsPluginKey = new PluginKey('pendingEdits')

export interface PendingEditsOptions {
  sectionKey: string
  getState: () => PendingEdit[]         // reads workspace reducer state
  dispatch: WorkspaceDispatch           // dispatches back to reducer
}

export const PendingEditsPlugin = Extension.create<PendingEditsOptions>({
  name: 'pendingEdits',

  addOptions() {
    return {
      sectionKey: '',
      getState: () => [],
      dispatch: () => {},
    }
  },

  addProseMirrorPlugins() {
    const { sectionKey, getState, dispatch } = this.options

    return [
      new Plugin({
        key: PendingEditsPluginKey,

        state: {
          init(_, editorState) {
            const pending = getState()
            return buildDecorations(pending, editorState.doc, dispatch, sectionKey)
          },
          apply(tr, oldDecoSet, _oldState, newState) {
            // Map existing decorations through transaction (keeps anchors alive)
            const mapped = oldDecoSet.map(tr.mapping, newState.doc)

            // If workspace state changed (signaled by meta), rebuild from scratch
            if (tr.getMeta(PendingEditsPluginKey) === 'refresh') {
              return buildDecorations(getState(), newState.doc, dispatch, sectionKey)
            }

            return mapped
          },
        },

        props: {
          decorations(state) {
            return PendingEditsPluginKey.getState(state)
          },
        },
      }),
    ]
  },
})
```

**How to wire in SectionEditorBlock:** Pass `getState` and `dispatch` as extension options. To trigger a `refresh` when workspace state changes, call `editor.view.dispatch(editor.state.tr.setMeta(PendingEditsPluginKey, 'refresh'))` from a `useEffect` that watches `workspaceState.sections[sectionKey].pending_edits`.

## Pattern 2: Decoration Construction (MEDIUM confidence — ProseMirror API)

```typescript
// src/editor/plugins/pendingEdits/decorations.tsx
import { Decoration, DecorationSet } from '@tiptap/pm/view'
import type { Node as PMNode } from '@tiptap/pm/model'
import type { PendingEdit, WorkspaceDispatch } from '../../types/workspace'

export function buildDecorations(
  pending: PendingEdit[],
  doc: PMNode,
  dispatch: WorkspaceDispatch,
  sectionKey: string,
): DecorationSet {
  const decorations: Decoration[] = []

  for (const change of pending) {
    if (change.operation === 'replace') {
      // Find anchor paragraph by data-id
      let anchorPos: number | null = null
      let anchorEnd: number | null = null
      doc.descendants((node, pos) => {
        if (node.attrs?.id === change.paragraph_id) {
          anchorPos = pos
          anchorEnd = pos + node.nodeSize
          return false
        }
      })
      if (anchorPos === null) continue

      // Node decoration: amber left-border on source paragraph
      decorations.push(
        Decoration.node(anchorPos, anchorEnd!, {
          class: 'pending-edit-source pending-edit-modify',
        })
      )

      // Widget decoration: ghost content immediately below source
      decorations.push(
        Decoration.widget(anchorEnd!, (view, getPos) => {
          return buildGhostWidget(change, view, dispatch, sectionKey)
        }, { side: 1, key: `ghost-${change.paragraph_id}` })
      )
    }

    if (change.operation === 'delete') {
      // Node decoration: red left-border
      decorations.push(
        Decoration.node(anchorPos, anchorEnd!, {
          class: 'pending-edit-source pending-edit-delete',
        })
      )
      // Widget: Accept/Reject affordance below
    }

    if (change.operation === 'insert_after') {
      // Widget at position after anchor — no node decoration on source
    }
  }

  return DecorationSet.create(doc, decorations)
}
```

**Key API facts:**
- `Decoration.node(from, to, attrs)` — wraps an existing node, adds CSS classes without touching content
- `Decoration.widget(pos, toDOM, options)` — inserts a DOM element not in the real document; `side: 1` places it after the position
- `DecorationSet.create(doc, decorations[])` — builds the initial set
- `decorationSet.map(mapping, doc)` — maps all decoration positions through a transaction mapping
- Widget `key` option prevents redundant re-renders when the set is rebuilt

[CITED: prosemirror.net/docs/ref/#view.Decoration]

## Pattern 3: Decoration Position Mapping Through Transactions (CRITICAL)

The `state.apply` method receives every transaction. The standard pattern:

```typescript
apply(tr, oldDecoSet, _oldState, newState) {
  // Step 1: always map through the transaction
  const mapped = oldDecoSet.map(tr.mapping, newState.doc)

  // Step 2: rebuild only when workspace state changes
  if (tr.getMeta(PendingEditsPluginKey) === 'refresh') {
    return buildDecorations(getState(), newState.doc, dispatch, sectionKey)
  }

  return mapped
}
```

**What `map()` does:** When the user types before a decoration, the mapping shifts the decoration's position forward/backward to stay anchored to the same logical location. When the user deletes the anchor paragraph, the decoration may map to a degenerate range — this is the staleness signal.

**Staleness detection:** After mapping, check whether the anchor paragraph still exists:

```typescript
apply(tr, oldDecoSet, _oldState, newState) {
  const mapped = oldDecoSet.map(tr.mapping, newState.doc)

  if (tr.docChanged) {
    // Check each pending change — is its anchor still in the doc?
    const pending = getState()
    const staleIds: string[] = []
    for (const change of pending) {
      if (!change.paragraph_id) continue
      let found = false
      newState.doc.descendants((node) => {
        if (node.attrs?.id === change.paragraph_id) { found = true; return false }
      })
      if (!found) staleIds.push(change.paragraph_id)
    }

    if (staleIds.length > 0) {
      // Dispatch auto-reject for stale changes
      dispatch({ type: 'AUTO_REJECT_STALE_EDITS', payload: { section_key: sectionKey, stale_ids: staleIds } })
      // Rebuild without stale items
      return buildDecorations(
        pending.filter(c => !staleIds.includes(c.paragraph_id ?? '')),
        newState.doc, dispatch, sectionKey
      )
    }
  }

  if (tr.getMeta(PendingEditsPluginKey) === 'refresh') {
    return buildDecorations(getState(), newState.doc, dispatch, sectionKey)
  }

  return mapped
}
```

**Walking the doc on every transaction has a cost.** Only do the staleness walk when `tr.docChanged` is true AND pending edits exist. For typical proposals (5–20 paragraphs), this is negligible.

[CITED: prosemirror.net/docs/ref/#view.DecorationSet.map; MEDIUM — derived from ProseMirror reference + community patterns]

## Pattern 4: Workspace Reducer ↔ ProseMirror Plugin Two-Way Sync (Avoiding Infinite Loops)

**The problem:** React renders asynchronously. ProseMirror's `dispatchTransaction` is synchronous. If the plugin dispatches a React action during a ProseMirror transaction, and the React re-render triggers a new transaction, you get a loop.

**The safe pattern — used by PlaceholderMark.ts:**

`appendTransaction` (used by PlaceholderMark) fires after the transaction is committed, in a separate microtask. For `PendingEditsPlugin`, the pattern is different — Accept/Reject are user-initiated button clicks, not transaction side effects. Button click handlers:

1. Dispatch the ProseMirror transaction (content replacement or no-op)
2. In the button's `onClick`, also call `dispatch({ type: 'ACCEPT_PENDING_EDIT', ... })` on the React reducer

These are two separate dispatches. The ProseMirror transaction does NOT call `dispatch` — the React `onClick` does both:

```typescript
// In the widget DOM element's onClick:
onClick={() => {
  // 1. ProseMirror: apply content replacement
  view.dispatch(
    view.state.tr
      .replaceWith(from, to, newContent)
      .setMeta('aiApplied', true)
      .setMeta('addToHistory', true)
  )
  // 2. React: update workspace state (no ProseMirror side effect)
  reactDispatch({ type: 'ACCEPT_PENDING_EDIT', payload: { section_key, change_id } })
}
```

The React `useEffect` that triggers the plugin `refresh` fires after the state update — but since the ProseMirror tr already committed the content, the `refresh` transaction only updates decorations (removes the ghost), not document content. No loop.

**The one genuine risk:** The `useEffect` watching `pending_edits` must not dispatch a `refresh` transaction if `pending_edits` reference equality hasn't changed (React shallow compare). Use `useMemo` or compare `pending.length` + IDs to gate the `editor.view.dispatch(refresh)` call.

[ASSUMED: Pattern derived from PlaceholderMark.ts analysis + ProseMirror documentation. The specific `setMeta('refresh')` gating approach was not found in official TipTap v3 docs but is the standard community pattern.]

## Pattern 5: Supabase Realtime for pending_actions Updates

The `chat_sessions` table already has RLS and Realtime can subscribe to row-level UPDATE events filtered by `proposal_id`:

```typescript
// In AIChatPanel.tsx — subscribe to pending_actions changes
useEffect(() => {
  if (!proposalId) return

  const channel = supabase
    .channel(`chat_sessions:${proposalId}`)
    .on(
      'postgres_changes',
      {
        event: 'UPDATE',
        schema: 'public',
        table: 'chat_sessions',
        filter: `proposal_id=eq.${proposalId}`,
      },
      (payload) => {
        const newRow = payload.new as { pending_actions: PendingAction[]; active_task: ActiveTask | null }
        setPendingActions(newRow.pending_actions ?? [])
        setActiveTask(newRow.active_task ?? null)
      }
    )
    .subscribe()

  return () => { supabase.removeChannel(channel) }
}, [proposalId])
```

**Requirement:** The `chat_sessions` table must be added to the `supabase_realtime` publication. Verify with:

If not present: `ALTER PUBLICATION supabase_realtime ADD TABLE chat_sessions;`

**JSONB column caveat:** Supabase Realtime Postgres Changes sends the full row on UPDATE, including all JSONB columns. `pending_actions` and `active_task` will be present in `payload.new`. No special handling needed — deserialize directly.

## Pattern 6: analyze-proposal-gaps Edge Function Structure

```typescript
// supabase/functions/analyze-proposal-gaps/index.ts
import Anthropic from "npm:@anthropic-ai/sdk"
import { createClient } from "npm:@supabase/supabase-js@2"
import { z } from "npm:zod@^3"
import { PendingActionSchema } from "./schema.ts"

Deno.serve(async (req) => {
  if (req.method === "OPTIONS") return new Response("ok", { headers: corsHeaders })

  const { proposal_id, org_id, sections } = await req.json()

  // Rate limit: reject if last call for this (proposal_id) was < 3 seconds ago
  const supabase = createClient(...)
  const { data: session } = await supabase
    .from('chat_sessions')
    .select('last_updated')
    .eq('proposal_id', proposal_id)
    .single()

  if (session?.last_updated) {
    const age = Date.now() - new Date(session.last_updated).getTime()
    if (age < 3000) {
      return new Response(null, { status: 429, headers: corsHeaders })
    }
  }

  // Build truncated section summaries (300 chars max per section)
  const summaries = sections.map((s: any) => ({
    key: s.key,
    title: s.title,
    excerpt: s.content.replace(/<[^>]*>/g, '').slice(0, 300),
  }))

  const anthropic = new Anthropic({ apiKey: Deno.env.get("ANTHROPIC_API_KEY")! })

  const response = await anthropic.messages.create({
    model: "claude-haiku-4-5-20251001",
    max_tokens: 1024,
    system: ANALYSIS_SYSTEM_PROMPT,  // instructs Haiku to return JSON array
    messages: [{ role: "user", content: JSON.stringify(summaries) }],
  })

  const textBlock = response.content.find((b) => b.type === "text")
  let pendingActions: any[] = []
  try {
    const raw = JSON.parse(textBlock?.text ?? "[]")
    pendingActions = z.array(PendingActionSchema).parse(raw)
  } catch {
    // Validation failure: return empty queue, do not surface error to user
    pendingActions = []
  }

  // Upsert to chat_sessions
  await supabase
    .from('chat_sessions')
    .upsert({
      proposal_id,
      org_id,
      pending_actions: pendingActions,
      last_updated: new Date().toISOString(),
    }, { onConflict: 'proposal_id' })

  return new Response(JSON.stringify({ ok: true }), {
    headers: { ...corsHeaders, 'Content-Type': 'application/json' }
  })
})
```

**Fire-and-forget from client:** The frontend posts and does NOT await the response in the render path:
```typescript
// After section save — no await, no error surface
supabase.functions.invoke('analyze-proposal-gaps', {
  body: { proposal_id, org_id, sections: sectionSummaries }
}).catch(() => {}) // swallow — Realtime will update UI when complete
```

## Pattern 7: Accept Transaction — aiApplied Meta Integration

`PlaceholderMark.ts` already skips its resolution plugin when `tr.getMeta('aiApplied')` is true. The `PendingEditsPlugin` Accept action must set this meta so PlaceholderMark doesn't resolve any placeholder spans in the accepted content:

```typescript
// In the Accept widget button onClick:
view.dispatch(
  view.state.tr
    .replaceWith(from, to, parsedNewContent)
    .setMeta('aiApplied', true)      // skip PlaceholderMark resolution plugin
    .setMeta('addToHistory', true)   // include in undo history
    .setMeta(PendingEditsPluginKey, 'skip-refresh')  // don't trigger decoration rebuild during accept tr
)
```

After the transaction commits, the React `onClick` handler calls the workspace `dispatch` — this causes a new `refresh` meta transaction that rebuilds decorations without the now-accepted change.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Decoration position tracking across edits | Custom position store | `DecorationSet.map(tr.mapping, tr.doc)` | ProseMirror's mapping already handles all step types correctly |
| Ghost paragraph isolation | Filter in `editor.getHTML()` | Decorations (widget/node) — never in document | Decorations are view-only; `getHTML()` returns the doc, which has no ghost content |
| Walkthrough state machine | Custom FSM | `chat_sessions.active_task` JSONB + `ask_user` tool | State already persists; AI drives transitions via tool calls |
| Action queue priority ordering | Client-side heuristic | Haiku-generated `priority` field | Server analysis has full proposal context |
| Per-paragraph UUID generation on Accept | Custom UUID logic | `UniqueID` extension auto-assigns UUIDs on `insertContentAt` | Already deployed, already handles new paragraphs |
| Detecting anchor paragraph deletion | Walking entire doc always | Map first, then check only changed ranges | `tr.docChanged` + `tr.mapping` narrows the search space |

## Common Pitfalls

### Pitfall 1: Ghost Content in `editor.getHTML()`
**What goes wrong:** A widget decoration's DOM node is mistakenly inserted into the document tree rather than the view overlay. `editor.getHTML()` returns it. Autosave writes it to the DB.
**Why it happens:** Using `editor.commands.insertContentAt()` instead of `Decoration.widget()`. Or rendering the ghost as a TipTap Node extension (real document node) rather than a decoration.
**How to avoid:** Only use `Decoration.widget()` and `Decoration.node()` from `@tiptap/pm/view`. Never call `editor.commands.*` to create ghost content. The AI-SPEC's ghost isolation guardrail validates this before every `SET_PENDING_EDITS` dispatch.
**Warning signs:** `editor.getHTML()` contains strings from `changes[].after_html` while pending edits exist.

### Pitfall 2: Decoration Refresh Loop
**What goes wrong:** The `useEffect` watching `pending_edits` calls `editor.view.dispatch(refreshTr)` → ProseMirror re-renders → `onUpdate` fires → React state update → `useEffect` fires again.
**Why it happens:** `onUpdate` calls `dispatch({ type: 'UPDATE_CONTENT', ... })` which triggers re-render, which re-evaluates `useEffect` dependencies.
**How to avoid:** The `refresh` transaction does NOT change document content — it only changes plugin state (DecorationSet). ProseMirror's `onUpdate` only fires when `tr.docChanged` is true. A refresh transaction with no content change will not trigger `onUpdate`. Gate the `useEffect` on `pending_edits` reference identity (or length + IDs) to prevent unnecessary dispatches.
**Warning signs:** Browser performance profiler shows hundreds of `UPDATE_CONTENT` dispatches per second without user input.

### Pitfall 3: insertChainRef Position Corruption (The Bug Being Fixed)
**What goes wrong:** When accepting `insert_after` changes out of order in the chat panel, `insertChainRef` maps the anchor ID to the last-inserted paragraph ID — but this only works when accepted in sequence. Out-of-order acceptance chains to the wrong anchor.
**Why it happens:** `insertChainRef` is a client-side position emulation. `insert_after` positions are not pre-resolved.
**How to avoid:** In Part A, all insertions materialize as decorations at their computed positions when the tool result arrives. Positions are pre-resolved before any user interaction. `insertChainRef` is deleted.
**Warning signs:** Multi-paragraph inserts appearing in reversed order or in the wrong section.

### Pitfall 4: Supabase Realtime not Receiving JSONB Column Updates
**What goes wrong:** The Realtime subscription fires but `payload.new.pending_actions` is null or missing.
**Why it happens:** `chat_sessions` table not included in the `supabase_realtime` publication. Or Realtime is configured to omit JSONB columns for payload size reasons.
**How to avoid:** Verify `ALTER PUBLICATION supabase_realtime ADD TABLE chat_sessions;` is in a migration. Test the subscription in the Supabase dashboard before building the UI.
**Warning signs:** `payload.new` has the row's non-JSONB columns (id, proposal_id) but JSONB columns are null.

### Pitfall 5: Widget Decoration `toDOM` Called During Transaction
**What goes wrong:** The `toDOM` function passed to `Decoration.widget()` is called synchronously during the ProseMirror update cycle. If it calls React state setters or references stale closures, behavior is undefined.
**Why it happens:** Widget `toDOM` runs in ProseMirror's view update, which happens inside `dispatchTransaction`. React state updates here are synchronous but trigger deferred re-renders.
**How to avoid:** The `toDOM` function should create a plain DOM element (not a React component). Attach `addEventListener` for click. Do NOT call React `dispatch` inside `toDOM` — only inside the event listener. Use closure over the `reactDispatch` function captured at construction time.
**Warning signs:** `Cannot update a component while rendering a different component` React warnings. Or double-dispatch of actions.

### Pitfall 6: Haiku Flooding Without Debounce Guard
**What goes wrong:** `analyze-proposal-gaps` fires on every keystroke if the debounce is on the section save but not on the function invocation side.
**Why it happens:** Autosave has a 1500ms debounce (`useAutosave`). If gap analysis fires after every autosave, a fast typist triggers it every 1.5s. Multiple sections compound this.
**How to avoid:** Server-side rate limit (3s per proposal_id, enforced in edge function via `last_updated` check). Client-side additional debounce of 3s after section save before invoking the function.
**Warning signs:** Haiku call count alert (>20 calls/session) in Arize Phoenix.

### Pitfall 7: Table Cell Ghost Row
**What goes wrong:** A widget decoration inserted after a table cell paragraph appears as a stray row or breaks the table rendering.
**Why it happens:** ProseMirror's table schema expects specific node structure. A widget at a position inside a table can render outside the table's DOM container.
**How to avoid:** Detect parent node type before creating decorations. If `change.paragraph_id` resolves to a node whose parent is `table_cell`, dispatch `inline-replace` decoration type instead of ghost-below. The plugin checks parent node type during `buildDecorations`.
**Warning signs:** Decorations appearing outside the table border, or table column alignment breaking when pending edits are present.

## Open Questions

1. **Is `chat_sessions` in the `supabase_realtime` publication?**
   - What we know: The migration creates the table and enables RLS but does not add it to the publication.
   - What's unclear: Whether a prior manual step or another migration added it.
   - Recommendation: Add `ALTER PUBLICATION supabase_realtime ADD TABLE chat_sessions;` as a Wave 0 migration task. Verify first with `SELECT tablename FROM pg_publication_tables WHERE pubname = 'supabase_realtime';`.

2. **TipTap v3 new Decorations API vs. raw ProseMirror Plugin**
   - What we know: TipTap v3 introduced a "new Decorations API" (from tiptap.dev/tiptap-editor-v3 release notes). Details are not fully documented yet.
   - What's unclear: Whether this API wraps `DecorationSet`/`Plugin` or replaces them. The existing `PlaceholderMark.ts` uses raw `Plugin` + `PluginKey` from `@tiptap/pm/state` and it works in the v3 runtime.
   - Recommendation: Use the raw ProseMirror `Plugin` approach (identical to PlaceholderMark) — it is verified to work. Investigate the new Decorations API only if the raw approach encounters v3-specific breakage. [LOW confidence on v3 new API specifics]

3. **action queue render location: above history vs. separate tab**
   - What we know: Both are architecturally viable. Above-history keeps context; tab separates concerns.
   - What's unclear: User preference — this is marked as Claude's discretion.
   - Recommendation: Default to above-history (simpler, single scroll surface). Tab adds complexity with no clear user benefit for this use case. Keep as a configurable prop.

4. **Widget decoration React rendering**
   - What we know: `Decoration.widget(pos, toDOM)` takes a function returning a DOM element. For styled React components (with Tailwind), this requires either `ReactDOM.createRoot` within the DOM element or plain DOM manipulation.
   - What's unclear: Whether TipTap v3's new Decorations API has a React-native widget API.
   - Recommendation: Use `ReactDOM.createRoot(el)` inside the `toDOM` function for complex affordances. For simple Accept/Reject buttons, plain DOM is acceptable. [MEDIUM — based on community pattern, not verified against v3 API]

## Codex Review

### Plan 01 — Wave 0 Stubs + Realtime Migration

#### Summary
The plan correctly scopes Wave 0 to stubs and the Realtime migration. The Realtime change from broadcast to `postgres_changes` is a load-bearing security decision — users should only receive events for their own sessions — but the plan does not spell out the RLS policy structure or provide a migration verification query. Dead code removal (gap props) is correctly sequenced here.

#### Strengths
- Correctly defers all logic to later waves; stubs prevent blocking downstream plans.
- Removing `gapCount`/`onGapsConsumed` dead code at Wave 0 avoids drift.
- Realtime migration at Wave 0 ensures Part B wiring (Wave 4) has a stable subscription channel.

#### Concerns
- **HIGH:** The migration changes Realtime security model (broadcast → postgres_changes with user_id filter). There is no RLS policy for Realtime isolation (`USING (auth.uid() = user_id)`) verified in the plan.
- **HIGH:** `chat_sessions` identity (per proposal? per user+proposal? per browser session?) is not explicitly defined. Resume-on-reload in Plan 07 depends on a stable session identity contract.
- **MEDIUM:** Dead code removal (prop passthrough in `ProposalDetail.tsx`) must not leave dangling TypeScript errors. Plan should include `npx tsc --noEmit` as a verification step.
- **MEDIUM:** Migration `20260515000040` adds `user_id` column — need to confirm existing rows are backfilled and not left NULL if the column is NOT NULL.

#### Suggestions
- Add RLS policies with both `USING` and `WITH CHECK` for the Realtime filter.
- Include a migration verification query and local Supabase test for Realtime visibility.
- Define explicitly: one `chat_session` per (user_id, proposal_id) or per session UUID? This contract blocks Plans 06 and 07.
- Keep the Realtime migration separate from cosmetic prop cleanup if possible.

#### Risk Assessment
**HIGH.** This plan changes the security and session identity model. If wrong, Part B resume and action queue behavior will be unreliable or leak-prone.

### Plan 02 — Type Contracts

#### Summary
Good sequencing — types before runtime code. The plan covers most of the conceptual entities needed for pending edits, action queue items, and walkthroughs. The main gap is under-specification of identity and persistence fields, which will propagate as cascading ambiguity into Plans 03–07.

#### Strengths
- Good sequencing: type contracts before runtime code.
- Covers most conceptual entities needed for pending edits, queue items, and walkthroughs.
- `ComplianceIssue.changes` optional field enables reuse of edit-review UI for compliance fixes.

#### Concerns
- **HIGH:** `PendingEdit` lacks stable identity and persistence linkage. Needs at minimum: `id`, `message_id` (or `tool_message_id`), and `change_index`.
- **HIGH:** Current tool payload uses `operation`, `before_html`, and `after_html`; plan introduces `change_type` and `ghost_content`. The mapping contract between old and new field names must be explicit to avoid runtime mismatches.
- **MEDIUM:** `anchorFrom`/`anchorTo` are ProseMirror runtime positions. They should not be treated as durable persisted state — mark them as runtime-only.
- **MEDIUM:** `ActiveTask` needs: `status`, `started_at` timestamp, `completed`/`dismissed` state, and `source_action_item_id`.
- **MEDIUM:** `PendingActionItem` needs persistence/de-dupe fields: `proposal_id`, `run_id`, `created_at`, `rationale`, `confidence`, `updated_at`.
- **LOW:** `CHANGE_TYPE_LABELS` should align with (or explicitly rename) existing `operation` field naming to avoid confusion during migration.

#### Suggestions
- Add `PendingEdit.id`, `tool_message_id`, `change_index`, `section_key`, and `created_at`.
- Mark `anchorFrom`/`anchorTo` as `/** Runtime only — not persisted */`.
- Extend `ToolName`, `ChatMessageType`, and `ToolDataEnvelope` if `analyze_proposal_gaps` is stored as a tool result.
- Define a versioned schema for `chat_sessions.active_task` and `pending_actions`.

#### Risk Assessment
**MEDIUM.** Under-specifies identity and persistence; will cause cascading problems in Plans 03–07 if not tightened.

### Plan 03 — PendingEditsPlugin + decorations.tsx

#### Summary
Correct architectural direction: ghost content stays external to the ProseMirror document. Position mapping through transactions and staleness detection via anchor hash are both necessary. The main risks are ProseMirror-specific: decoration type conflation, direct workspace dispatch from plugin state, and ambiguous anchoring for `insert_after` changes.

#### Strengths
- Correct approach: keep ghost content out of the actual document.
- Position mapping through transactions is the right mechanism.
- Staleness detection via anchor hash is a necessary guard.
- `ghostContentLeakDetected` as a last-resort defensive guard is well-motivated.

#### Concerns
- **HIGH:** Plan describes "NodeDecoration with widget overlays" — ProseMirror has `Decoration.node`, `Decoration.inline`, and `Decoration.widget` as separate types; conflating them leads to incorrect rendering or DOM corruption.
- **HIGH:** Dispatching workspace actions directly from plugin `apply()` can create lifecycle loops. Plugin state should surface metadata/events via `PluginKey.getState()`, not dispatch to external stores.
- **HIGH:** Accept/reject transaction construction must handle: stale/missing anchors, editor not mounted, cross-section edits, and partial application failure.
- **MEDIUM:** Staleness hash normalization is undefined. HTML, whitespace, smart quotes, and TipTap serialization differences can all produce false stale results.
- **MEDIUM:** `insert_after` anchoring is ambiguous — existing tool schema says `paragraph_id` may be omitted for new paragraphs, but insertion still needs a stable anchor.
- **MEDIUM:** `ghostContentLeakDetected` can false-positive if proposed text already exists in the document naturally.
- **LOW:** `PlaceholderMark.ts` pattern only partially applies — pending edits are decorations, not marks.

#### Suggestions
- Use separate decoration types: `Decoration.inline` for anchor range highlight, `Decoration.widget` for accept/reject buttons near the affected paragraph.
- Define `PendingEditPluginMeta` protocol for `set`, `clear`, `accept`, `reject`, and `stale` events exposed via PluginKey.
- Keep staleness detection deterministic: hash normalized paragraph text + paragraph ID + original HTML.
- Add unit tests for: replace, delete, insert-after, user edits before anchor, user edits inside anchor, missing paragraph ID.
- Treat `ghostContentLeakDetected` as a last-resort guard, not the primary source of truth.

#### Risk Assessment
**HIGH.** Technically the hardest plan. Small ProseMirror mistakes can corrupt content, break undo, or produce permanent stale decorations.

### Plan 04 — Workspace Reducer

#### Summary
Centralizing pending edit state in the workspace reducer is reasonable. The batch-accept action matching the one-PM-transaction requirement is correct. The main architectural concern is `persistResolutions` inside a reducer — React reducers must be pure; Supabase writes should happen in a hook/effect layer.

#### Strengths
- Centralizing pending edit state in the workspace is the right pattern.
- Batch accept as one reducer action matches the one-transaction requirement (D-03).
- Initializing `pending_edits: []` on `SET_SECTIONS` is necessary.

#### Concerns
- **HIGH:** `persistResolutions` inside a reducer is an anti-pattern. React reducers must be pure; side effects (Supabase writes) should happen in a `useEffect` hook or middleware layer triggered by state change.
- **HIGH:** Updating `proposal_chats.tool_data` fire-and-forget can overwrite concurrent state changes unless it merges the latest envelope (read-modify-write, not blind overwrite).
- **MEDIUM:** `AUTO_REJECT_STALE_EDITS` should be triggered by the plugin's staleness detection, not manually. The trigger path should be explicit.
- **MEDIUM:** `BATCH_ACCEPT_PENDING_EDITS` filters to `resolution === 'pending'` — plan should document what happens if some edits were already resolved (silent skip vs. error).
- **LOW:** `buildResolutionMap` helper needs tests for empty input, mixed resolutions, and duplicate IDs.

#### Suggestions
- Move `persistResolutions` to a `useEffect` or custom hook that fires after reducer state update.
- Use optimistic merge: read current `tool_data`, merge resolution map, then write.
- Define the trigger path for `AUTO_REJECT_STALE_EDITS` (plugin event → dispatch).
- Document BATCH_ACCEPT_PENDING_EDITS partial-resolution behavior explicitly.

#### Risk Assessment
**MEDIUM-HIGH.** Pure reducer + side effects anti-pattern is a correctness risk under concurrent updates.

### Plan 05 — SectionEditorBlock Wiring + EditSummaryCard + AIChatPanel Part A

#### Summary
Good locked decision: `materializePendingEdits` as the single entry point for both propose_edit paths. Replacing DiffPreview with EditSummaryCard aligns the UI with editor-first review. Batch accept as one PM transaction is the right UX. Main risk is the breadth of Plan 05: wiring, new component, refactor, and deletion all in one wave.

#### Strengths
- `materializePendingEdits` as single entry point is well-motivated and correctly prevents double-application.
- Replacing `DiffPreview` with `EditSummaryCard` unifies the diff surface.
- Batch accept as one ProseMirror transaction is the right user experience.
- Removing `insertChainRef` addresses the known insertion-order bug.

#### Concerns

- **HIGH:** Accept All must be atomic or clearly partial. A half-applied batch (some paragraphs accepted, PM transaction throws) leaves the editor in undefined state.
- **MEDIUM:** Deleting `DiffPreview.tsx` requires updating/deleting its tests and all import sites in the same wave; plan does not enumerate them.
- **MEDIUM:** `EditSummaryCard` props do not include `message_id` — required for `persistResolutions` to target the correct `proposal_chats` row unless `payload` carries it.
- **MEDIUM:** Double-click on "Review in editor →" behavior is undefined — `materializePendingEdits` should be idempotent by edit ID.
- **LOW:** Accessibility attributes for decoration buttons and EditSummaryCard controls should be specified.

#### Suggestions
- Make `materializePendingEdits` idempotent by edit ID (re-calling with same message_id is a no-op).
- Add disabled/error state for `EditSummaryCard` when target editor is not mounted.
- Enumerate DiffPreview import sites before deletion wave.
- Add `message_id` to `EditSummaryCardProps` for persistence identity.

#### Risk Assessment
**MEDIUM-HIGH.** Broad wave scope. ProseMirror transaction atomicity needs explicit error recovery path.

### Plan 06 — analyze-proposal-gaps Edge Function + chat-with-jamo Integration

#### Summary
The walkthrough context in `chat-with-jamo` is a clean extension point. The `analyze-proposal-gaps` function concept is correct. The main concerns are: (1) this plan is too large for one autonomous wave, (2) security — never trust `user_id` from the client, (3) action queue store canonical location is unresolved.

#### Strengths
- Walkthrough context injection into `chat-with-jamo` is a clean, minimal extension.
- SSE `task_complete` event for UI state transitions is well-designed.
- Supabase Edge Function as the analysis layer keeps client thin.

#### Concerns
- **HIGH:** Plan is too large for one autonomous wave: new Edge Function + LLM analysis + DB writes + auth/RLS + rate limiting + streaming changes = too many failure modes in one pass.
- **HIGH:** `{ proposal_id, user_id }` input — NEVER trust `user_id` from the client. The function must derive identity from the JWT (`req.headers.get('Authorization')`).
- **HIGH:** "RLS only callable by authenticated user who owns proposal" must be enforced in function code or via user-scoped Supabase client. Service role key bypasses RLS entirely.
- **MEDIUM:** Schema mismatch: current `chat_sessions` stores `pending_actions`; plan says upsert to `proposal_chats`. The canonical action queue store is unresolved.
- **MEDIUM:** Rate limit/debounce needs a durable store (DB timestamp or Redis). Client debounce alone is bypassed by page reload.
- **MEDIUM:** LLM output (`PendingActionItem[]`) needs strict JSON schema validation and a defined fallback (empty array, not crash).
- **LOW:** Model name `claude-sonnet-4-6` should be verified against Anthropic's current available model IDs before implementation.

#### Suggestions
- Split: first implement deterministic function contract and persistence; then add LLM analysis in a follow-up plan.
- Derive user identity from auth token; verify proposal ownership from DB, not client claim.
- Choose one canonical action queue store: `chat_sessions.pending_actions`, `proposal_chats.tool_data`, or a normalized table.
- Add Zod/JSON schema validation for `PendingActionItem[]` output.
- Preserve SSE behavior with regression tests for normal chat, tool call, and task completion flows.

#### Risk Assessment
**HIGH.** Security-sensitive backend work combined with LLM schema reliability and streaming behavior changes — too much for one autonomous wave.

### Plan 07 — ActionQueue + Resume UI + AIChatPanel Part B

#### Summary
Component breakdown is sensible and the resume-on-reload concept maps well to `chat_sessions.active_task`. Feature-flagging `detectGaps()` retirement is pragmatic. The main blockers are the missing Realtime subscription contract and a schema mismatch (`metadata` column vs. direct `active_task` column).

#### Strengths
- Component breakdown (ActionQueue, ActionItem, ResumeTaskBanner, WalkthroughProgress) is sensible and testable independently.
- Resume-on-reload maps naturally to existing `chat_sessions.active_task` column.
- Feature-flagging `detectGaps()` retirement behind `VITE_ENABLE_CLIENT_GAPS` is pragmatic.
- Queue cap of 5 items avoids overwhelming the chat panel.

#### Concerns
- **HIGH:** Realtime subscription for ActionQueue is missing key details: which table, which filter column, event type (INSERT/UPDATE/DELETE), auth behavior, cleanup on unmount, reconnect strategy, and stale initial data merge.
- **HIGH:** `active_task` persistence target is `chat_sessions.metadata` per the plan — but the current schema has `active_task` as a direct column, not inside a `metadata` JSONB. Schema mismatch will cause silent runtime failures.
- **MEDIUM:** Last-writer-wins for `active_task` is acceptable only if the UX makes it visible — two browser tabs can silently stomp each other's walkthrough state.
- **MEDIUM:** `analyze-proposal-gaps` triggered after section save needs in-flight run protection, not just debounce — overlapping concurrent runs will produce duplicate action items.
- **MEDIUM:** `detectGaps()` retirement spans `AIChatPanel`, `ProposalDetail`, tests, and badge behavior — scope is likely larger than the listed files.
- **LOW:** Queue item dismissal/resolution semantics (dismissed vs. completed vs. skipped) are not defined.

#### Suggestions
- Document the Realtime subscription contract: table, filter, event handling, cleanup, and reconnect.
- Verify `chat_sessions` schema before writing `active_task` — use the correct column path.
- Add an in-flight run guard to `analyze-proposal-gaps` trigger (server-side lock or idempotency key).
- Enumerate all `detectGaps` call sites before removal.
- Define queue item terminal states (dismissed, completed, skipped) before implementation.

#### Risk Assessment
**HIGH.** Schema mismatch and missing Realtime contract details are blocking risks for Part B.

## Consensus Summary

> Single reviewer (Codex) — consensus summary reflects its overall assessment.

### Top Concerns (HIGH severity, repeated across plans)

1. **`chat_sessions` identity and security contract undefined (Plans 01, 07)** — Session identity (per user+proposal? per browser?) is assumed but never defined. The Realtime postgres_changes filter and resume-on-reload both depend on it.

2. **`PendingEdit` lacks stable identity fields (Plans 02, 03)** — Missing `id`, `message_id`, `change_index` causes every downstream plan (persistence, accept/reject, staleness) to operate on unstable references.

3. **ProseMirror decoration type conflation (Plan 03)** — `Decoration.node` vs `Decoration.inline` vs `Decoration.widget` conflated in the plan description. Wrong choice corrupts DOM rendering.

4. **Side effects in pure reducer (Plan 04)** — `persistResolutions` inside `workspaceReducer` violates React's pure reducer contract; must move to effect layer.

5. **`user_id` trusted from client in edge function (Plan 06)** — Security vulnerability: the function must derive identity from JWT, not accept `user_id` as a client-supplied parameter.

6. **`active_task` schema mismatch (Plan 07)** — Plan says `chat_sessions.metadata` but current schema has `active_task` as a direct column. Silent runtime failure.

### Agreed Strengths

- Wave ordering (types → plugin → reducer → wiring → edge function → UI → verify) is logical and minimizes blocking dependencies.
- `materializePendingEdits` as the single entry point for both propose_edit paths is the right guardrail design.
- Feature-flagging `detectGaps()` retirement is pragmatic risk management.
- Batch-accept as a single ProseMirror transaction is the correct UX (one undo step).
- Stub-first approach at Wave 0 prevents downstream blocking.

### Key Divergences / Investigation Items

- **Action queue canonical store:** Plan 06 says `proposal_chats.tool_data`; current `chat_sessions` has a `pending_actions` column. Needs an explicit decision before Plan 06 is executed.
- **Plan 06 scope:** Codex flagged it as too large for one autonomous wave. Consider splitting: (a) function contract + persistence, then (b) LLM analysis + SSE integration.
- **`insert_after` anchor ambiguity:** When `paragraph_id` is omitted in the existing tool schema, `insert_after` needs an explicit anchoring strategy for the ProseMirror plugin.

## Overall Assessment

**Overall risk: HIGH.**

The phase goal is achievable and the wave ordering is mostly sensible. The highest risks are contract and integration risks, not conceptual ones:

- `chat_sessions` identity and Realtime security must be resolved before Part B execution.
- Pending edit identity and persistence need sharper contracts before Part A execution.
- ProseMirror decoration type selection requires careful verification.
- Plan 06 should be split to avoid combining auth, LLM validation, persistence, and SSE changes in one autonomous wave.

**Recommendation:** Tighten Plans 01, 02, 03, 04, 06, and 07 around the flagged contracts before proceeding to execution.

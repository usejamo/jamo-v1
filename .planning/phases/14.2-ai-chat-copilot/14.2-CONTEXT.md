# Phase 14.2: AI Chat Co-pilot — Context

**Gathered:** 2026-05-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 14.2 delivers two sequenced parts:

**Part A — Inline Editor Diffs.** Moves paragraph-level diff review from the chat panel into the section editor via ProseMirror Decorations. Prerequisite for Part B. Removes `DiffPreview.tsx` and `insertChainRef`. Fixes scroll bug scoped to all tool result cards.

**Part B — Proactive Co-pilot.** Activates proactive behavior: prioritized action queue on panel open, server-side gap/conflict detection via a new `analyze-proposal-gaps` edge function, multi-turn section walkthroughs, and resume-on-reload. Retires client-side `detectGaps()`.

The architectural decisions in the phase brief (ProseMirror Decorations for ghosts, `chat_sessions` as state store, Haiku 4.5 for proactive analysis, `ask_user` as multi-turn primitive, unidirectional state flow) are **locked — do not reopen**.

<decisions>
## Implementation Decisions

### Part A: Accept/Reject Affordances

- **D-01:** Individual Accept/Reject affordances on each ghost decoration (no floating action bar). No focus tracking in plugin state required.
- **D-02:** Batch **Accept All** and **Reject All** actions live in the `EditSummaryCard` (chat side), not the editor. Mental model: editor = individual decisions, card = set-level decisions and history.
- **D-03:** Batch Accept fires a **single ProseMirror transaction** wrapping all ghost commits — one undo step, not five. Batch Reject clears all decorations atomically.

### Part A: Ghost Anchor Staleness

- **D-04:** When a user edits or deletes a paragraph that has a pending ghost **before resolving it**, the ghost is **auto-rejected** with an `auto_rejected_stale` resolution enum value. No disabled UI, no stale state left on screen.
- **D-05:** Definition of "anchor edited": edits **inside** the anchor paragraph's content trigger staleness. Edits to surrounding paragraphs do not (ProseMirror's transaction mapping handles position tracking). Deletion of the anchor paragraph triggers staleness.
- **D-06:** Content-hash the anchor paragraph at materialization time. Compare on every transaction. Staleness fires when hash differs.
- **D-07:** The `EditSummaryCard` tally distinguishes `accepted / rejected / stale` — never collapses `auto_rejected_stale` into `rejected`. Example tally: "2 accepted, 1 rejected, 1 stale."

### Part A: Decoration Accessibility

- **D-08:** Each ghost decoration shows a **text label badge** — "Edit" / "Insert" / "Delete" — as a visible chip positioned top-left of the widget decoration. Muted, small, uppercase tracking, low-contrast in the border color family (amber/neutral-green/red).
- **D-09:** Decoration wrapper carries a full-sentence `aria-label`: "Proposed edit replacing the following paragraph" / "Proposed new paragraph to insert here" / "Proposed deletion of the following paragraph."
- **D-10:** Both badge text and aria-label live in a single typed mapping: `CHANGE_TYPE_LABELS: Record<ChangeType, { badge: string; aria: string }>`. Defined in the same file as `TOOL_STATUS_LABELS` from Phase 14.1. Same convention.

### Part A: EditSummaryCard Terminal State

- **D-11:** Once all changes in a set are resolved, the card shows the tally and **hides** the "Review in editor →" affordance. The card is a history record, not an action surface in its terminal state.
- **D-12:** Terminal state is visually distinct via slight desaturation of card chrome and section title shifting from active-link to plain text. Layout and information density do not change.
- **D-13:** Per-paragraph drill-down (expand card to see individual changes with their resolution) remains available in both active and terminal states. Terminal drill-down shows `accepted`, `rejected`, `stale` per paragraph.

### Part A: Resolution Write Granularity

- **D-14:** One DB write per Accept/Reject via the existing `persistToolDataState` mechanism. No debounce, no batching.
- **D-15:** Writes are **fire-and-forget**. ProseMirror transaction commits immediately, decorations clear immediately, tally updates optimistically — none await the DB write. If the write fails: surface a toast or add to retry queue. Does not block review flow. Matches existing autosave pattern.

### Part B: Action Queue Placement

- **D-16:** Queue renders **above chat history** in the message list area. Collapses (does not disappear) when a walkthrough task starts. Collapsed state shows a small header "N items in queue" with an expand affordance.
- **D-17:** Empty queue state shows a low-key message: "No suggestions right now. Ask me anything below." No missing UI — intentional empty state.

### Part B: Action Queue Ordering

- **D-18:** Fixed type priority: **compliance > conflict > gap > missing**. No Haiku scoring for ordering — fixed hierarchy is predictable and debuggable.
- **D-19:** Within each tier, order by **section position in the proposal** (document flow, top-to-bottom). Not by detection time.
- **D-20:** Terminology precision required in the plan: **gap** = section exists but is incomplete/thin; **missing** = a required section that hasn't been started. The detection function must output these as distinct types. Planner to verify the four categories map cleanly to detection output.

### Part B: Queue Dismissibility

- **D-21:** Users can dismiss queue items without acting. Dismissed items move to a `dismissed` state (not deleted from `pending_actions`). Re-surface when the content that triggered the detection changes materially.
- **D-22:** **Content-hash anchor at dismiss time.** Capture a hash of the relevant content (section content or cross-section content) when the user dismisses. Re-surface fires when that content changes beyond a threshold.
- **D-23:** Dismissal requires no reason. Single click, no confirmation prompt. Telemetry captured implicitly (item type, section, queue dwell time).
- **D-24:** Dismissed items are visible on demand — collapsed by default, expandable inline. Supports undo-of-dismiss and auditability.
- **D-25:** When an item re-surfaces, label it: "Re-surfaced — section content changed since you dismissed this."

### Part B: Queue Item Cap

- **D-26:** Cap visible items at **8 total**, with per-tier distribution to guarantee coverage: max 4 compliance, max 2 conflict, max 2 gap, max 2 missing. Items below the cap are sorted by section position within their tier.
- **D-27:** Footer reads: "+N more — focus on these first." Clickable — expands queue inline (not a separate view). Collapses automatically when queue drops back to ≤8 items.
- **D-28:** Cap values (8, per-tier maxes) live in a **single constants file**, not hardcoded in rendering logic. Treat as tunable.
- **D-29:** Action queue items display the **section name visibly** in the item text (not in a tooltip). Example: "Inclusion Criteria — missing primary endpoint definition."

### Part B: Proactive Detection Trigger

- **D-30:** Gap analysis fires **fire-and-forget after each section save**, debounced ~3 seconds after last keystroke (following the existing 1.5s autosave debounce, so analysis reads stable persisted content).
- **D-31:** **Content-hash skip guard:** if the section's content hash hasn't changed since the last analysis, skip the call. No new analysis for unchanged content.
- **D-32:** **30-second per-proposal cooldown:** if an analysis already ran within 30s for the same proposal, skip. Prevents rapid multi-section saves from firing multiple analyses. Cooldown is per-proposal, not per-section.
- **D-33:** Analysis uses the **full proposal as input** (not just the changed section). Cross-section conflict detection (budget vs. timeline) requires comparing across sections.
- **D-34:** **Race condition handling:** tag each analysis run with a run ID. When results arrive, only the latest run ID's results replace `pending_actions`. Stale responses are discarded.
- **D-35:** Initial population: plan to decide between (a) fire analysis on proposal open when no prior analysis exists, or (b) accept empty queue until first section save. Decision affects first-time user experience.

### Part B: Resume-on-Reload

- **D-36:** "Continue" **re-renders from DB state** — re-displays the last `ask_user` card from `proposal_chats`. No new edge function call. Deterministic, offline-safe, no AI latency cost on resume.
- **D-37:** Before showing "Continue," verify the walkthrough premise is still valid: `active_task` must be non-null and not marked discarded, and the target section must still exist.
- **D-38:** **Content-hash drift detection:** store a content hash of the target section in `active_task` at walkthrough start. If the section content has drifted materially on resume, show: "Content has changed since this walkthrough started — restart or discard?" rather than silently continuing.
- **D-39:** Active walkthrough surfaces as a **high-priority queue item**: "Continue [section_title] walkthrough." Visible in the action queue, not just in chat history.

### Part B: Walkthrough Cancel UX

- **D-40:** "Cancel" leaves all previously accepted paragraph edits **in place**. The user made explicit per-paragraph decisions; stop means stop the AI-guided flow, not undo those decisions.
- **D-41:** Button label: **"Stop walkthrough"** (not "Cancel"). Pair with inline clarification: "Accepted changes will stay in your document."
- **D-42:** Summary card terminal state for a cancelled walkthrough: "Walkthrough stopped — N changes kept, M not reviewed." Paragraphs not reached use a `not_reached` resolution enum value (distinct from `rejected` and `auto_rejected_stale`).
- **D-43:** `active_task` clears **optimistically** on Stop click (in-memory immediately, then DB write). If DB write fails, retry. The stop signal is not held hostage by network conditions.

### Part B: Concurrent User Sessions

- **D-44:** **Per-user `chat_sessions`** with a composite primary key on `(proposal_id, user_id)`. Each user has their own action queue state, walkthrough state, and dismissals. The shared resource is proposal content; AI session state is per-user.
- **D-45:** Migration: backfill `user_id` on existing `chat_sessions` rows from the most recent chat author in `proposal_chats`.
- **D-46:** `pending_actions` rows are **global per proposal** (detection output, not personalized). Each user's rendered queue is the global set minus their personal dismissals. Dismissal state is per-user (separate `pending_action_dismissals` or user-scoped flag on `pending_actions`). Planner to design the schema explicitly.
- **D-47:** Two users running walkthroughs on the same section simultaneously is allowed. Ghost decorations are UI-state (not persisted). If both accept conflicting changes, last-write-wins via autosave — same model as rest of editor. No coordination layer needed.

### Part B: Section-Scoped Thread Filter

- **D-48:** **Deferred.** Do not build the filter chip row in 14.2. Build when usage data shows user pain (scroll fatigue, lost threads).
- **D-49:** `section_target_id` **must be captured reliably** on every message in 14.2 — including walkthrough-driven messages and queue-triggered messages. Audit during implementation. This data enables the deferred filter to be built without a schema migration.

### Claude's Discretion

- Schema design for per-user dismissal state (`pending_action_dismissals` table vs. user-scoped field on `pending_actions`) — planner to decide based on query patterns
- Initial population strategy for first-time proposals: fire analysis on open vs. wait for first save (D-35 decision left to planner with awareness of both options)
- Content-hash algorithm and "material drift" threshold values for staleness detection (D-06, D-22, D-38) — planner to choose consistent approach across all three uses
- Autosave cooldown alignment details (exact timing to follow existing autosave path)
- RLS policy updates for the new per-user `chat_sessions` schema

</decisions>

<specifics>
## Specific Ideas from Discussion

- **`auto_rejected_stale` enum value** — a new resolution enum value distinct from `rejected`. Used when a ghost's anchor paragraph content changes before the user resolves the ghost. Tally shows this separately.
- **`not_reached` enum value** — for paragraphs in a cancelled walkthrough that were never reviewed. Distinct from `rejected` and `auto_rejected_stale`. Tally reads "N changes kept, M not reviewed."
- **Batch Accept transaction grouping** — single ProseMirror transaction for all changes in a set. Undo is a single step. Planner to use `setMeta` / transaction grouping (consistent with per-paragraph undo in 14.1 Specific Ideas).
- **`CHANGE_TYPE_LABELS` placement** — same file as `TOOL_STATUS_LABELS`. Typed `Record<ChangeType, { badge: string; aria: string }>`. Full-sentence aria strings, not bare badge labels.
- **Queue item section name** — visible in item text, not tooltip. "Inclusion Criteria — missing primary endpoint definition" format.
- **Dismissed items list** — collapsed by default, expandable inline in the panel. Supports undo-of-dismiss. Re-surfaced items labeled explicitly.
- **Queue constants file** — cap (8), per-tier maxes (4/2/2/2), cooldown (30s), analysis debounce (3s) all in one tunable constants file.
- **Gap vs. missing distinction** — gap = section exists but incomplete/thin; missing = required section not started. Detection function must output these as distinct `type` values in the `pending_actions` schema.
- **Active walkthrough in queue** — "Continue [section_title] walkthrough" appears as a high-priority queue item. Wired from `active_task` state, not only from chat message stream.
- **"Stop walkthrough" copy** — not "Cancel." Adjacent copy: "Accepted changes will stay in your document."
- **Per-user `chat_sessions` migration** — backfill `user_id` from most recent `proposal_chats` author. Composite PK on `(proposal_id, user_id)`. RLS update needed.
- **`section_target_id` on all messages** — walkthrough messages, queue-triggered messages, and proactive gap messages must all record `section_target_id`. Audit during implementation.

</specifics>

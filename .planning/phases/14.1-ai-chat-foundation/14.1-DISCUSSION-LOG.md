## Paragraph Diff Strategy

### Paragraph identification method

| Option | Description | Selected |
|--------|-------------|----------|
| @tiptap/extension-unique-id | ProseMirror node attributes that survive all transforms | ✓ |
| data-paragraph-id in HTML | Custom serializer injects attributes on save | |
| Position-based patching | AI returns index, no IDs needed | |

**User's choice:** `@tiptap/extension-unique-id`
**Notes:** Rejected position-based due to race conditions when user edits during streaming or accepts stale indices. Rejected data-attributes because silent ID loss on any HTML roundtrip without the custom serializer (paste, copy, AI tools returning clean HTML, future imports). ProseMirror node attributes survive everything by design. User specified: AI must never supply IDs for additions — fresh UUIDs minted client-side.

---

### Retroactive ID assignment

| Option | Description | Selected |
|--------|-------------|----------|
| Lazy assignment on editor mount | UniqueID auto-assigns on first open | ✓ |
| One-time migration via headless TipTap | Migration script adds IDs to all sections in DB | |

**User's choice:** Lazy on mount
**Notes:** Headless migration adds real complexity for a problem that mostly isn't real — proactive 14.2 features operate on sections the user engages with, not unopened ones. User called out three specific watch-outs: (1) first-open write must persist/trigger autosave, (2) ID-only saves must not pollute version history, (3) concurrent tabs are fine with last-write-wins.

---

### Diff application mechanics

| Option | Description | Selected |
|--------|-------------|----------|
| ProseMirror transaction by ID, immediate per-paragraph | Accept fires immediately, each paragraph independent | ✓ |
| Staged apply — atomic on "Apply all" | Hold in memory, apply when user commits | |

**User's choice:** Immediate per-paragraph ProseMirror transaction
**Notes:** Staged apply creates a worse review loop — user can't see how accepted changes read in context until committing everything. User specified five watch-outs: locate by ID at click time (not cached reference), `before` snapshot is display-only, three apply paths needed (replace/insert/delete by ID), each accept = own undo step, partial-accept state survives panel collapse.

## Tool Result Streaming UX

### What user sees during tool generation

| Option | Description | Selected |
|--------|-------------|----------|
| Thinking dots throughout | Generic indicator until result arrives | |
| Status label naming the action | Replace dots with "Drafting your edit...", etc. | ✓ |
| Progressive text from partial JSON | Extract readable text as JSON accumulates | |

**User's choice:** Status label
**Notes:** Generic dots leave the "I know what I'm doing" signal on the table — this is the main perceived-intelligence win of structured tool use. Option 3 rejected as fragile (incomplete JSON heuristics misfire). User specified: label fires on `content_block_start`, multi-tool chains update label per tool, fast tools just show dots→result, must handle plain-text fallback path.

### TOOL_STATUS_LABELS location

| Option | Description | Selected |
|--------|-------------|----------|
| Client-side constant | Record<ToolName, string> in frontend | ✓ |
| Server-sent in SSE | Edge function emits label string | |

**User's choice:** Client-side constant
**Notes:** UI copy belongs in frontend. Iterating on wording shouldn't require edge function redeploy. User specified: type as `Record<ToolName, string>`, fallback `?? 'Working...'` for unknown tools, present-progressive tone convention documented next to constant.

## Tool Result Persistence Design

### How to persist tool results across reload

| Option | Description | Selected |
|--------|-------------|----------|
| tool_data jsonb column on proposal_chats | Nullable JSONB on existing table | ✓ |
| New proposal_chat_tools table | Normalized, join on every load | |
| Serialize in content with new message_type | JSON stringified in content column | |

**User's choice:** `tool_data jsonb` column
**Notes:** Normalized table adds a join for a query use case that doesn't exist. Serialized-in-content poisons the content column with mixed markdown/JSON. User specified the full envelope schema with `tool`, `version`, `payload`, `state` fields. `version` field called non-negotiable. Mutable state (per-paragraph accept/reject) mutates `tool_data.state` in place for 14.1. Six specific watch-outs including size management for resolved diffs.

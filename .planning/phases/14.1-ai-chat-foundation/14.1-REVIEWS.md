# Cross-AI Plan Review — Phase 14.1

## Claude Code Self-Review

> **Note:** External reviewers unavailable (Codex CLI requires OpenAI API key, not ChatGPT login). This is a self-review by Claude Code. Treat as a thorough adversarial audit, not an independent perspective.

---

### 1. Summary

Phase 14.1 is a well-structured, thoughtfully decomposed migration from keyword-intent chat to Claude tool-use. The wave ordering is sound, the type system is thorough, and the security threat model covers the right surfaces. However, there are **two production-breaking bugs** that will cause silent failures regardless of test results: a client/server UUID mismatch that makes all tool-data state mutations no-ops, and an AskUserCard answer path that never actually submits the answer to the AI. A third significant issue — RAG always running at default K regardless of tool selection — inflates costs for every `set_focus` and `ask_user` call. These are fixable with targeted changes and do not require replanning the phase.

---

### 2. Strengths

- **Wave decomposition is clean.** The 4-wave structure correctly identifies the blocking chain (DB → types → edge function → client → components → persistence). No circular dependencies.
- **Dead code removal is atomic.** Doing all removals in one pass per plan (Plans 03, 05) prevents half-states that break tests mid-phase.
- **`version: 1` on `ToolDataEnvelope` is non-negotiable and enforced.** The loader guard (`td.version !== 1 → undefined`) prevents crashes on future schema changes. Good forward-compat.
- **Fabrication guardrail on citations.** Stripping citations whose `chunk_id` is not in `retrievedChunkIds` is an important correctness control that prevents hallucinated sources.
- **Compliance confidence guardrail.** Overriding `passes → null` when retrieval returns nothing prevents false-positive "passes" from model training data alone.
- **Paragraph ID resolved at click time, not cache.** Finding the ProseMirror node at `onAccept` time (not at diff delivery time) correctly handles the user-edits-between-diff-and-accept race condition.
- **Each accepted paragraph = its own undo step.** `tr.setMeta('addToHistory', true)` per change is the right granularity for a word processor-style UX.
- **sectionTitles built with useMemo keyed on sections array.** Avoids object identity churn on every render. Correct.
- **`chat_sessions` table design.** Using `proposal_id` as a unique index rather than a composite key is the right call given one session per proposal.

---

### 3. Concerns

#### HIGH — Production-Breaking Bugs

**H-01: client UUID vs server UUID mismatch breaks all tool_data state mutations**

*Affects: Plans 05, 06, 07, 08*

In Plan 05, tool-result messages are added to local state with `id: crypto.randomUUID()` (client-generated). In Plan 08, the tool result is saved to `proposal_chats` — but the DB generates its own UUID via `gen_random_uuid()` (the `id PRIMARY KEY DEFAULT gen_random_uuid()` pattern). The `persistToolDataState(msg.id, newState)` helper then runs `.update(...).eq('id', msg.id)` using the **client-generated UUID**, which does not exist in the DB. The UPDATE silently finds 0 rows. Every accept/reject/dismiss/answer mutation is a no-op against the DB. Users will see their state preserved in-memory during the session but lose it completely on reload.

**Fix:** Either (a) insert with an explicit client-generated UUID as the primary key (`INSERT INTO proposal_chats (id, ...) VALUES (clientUUID, ...)`), or (b) capture the DB-returned `id` from the insert response and update the local message state with the real DB ID before any mutations are attempted.

Option (a) is simpler: pass the client UUID as the DB id. Supabase `gen_random_uuid()` default only fires when no id is supplied.

---

**H-02: AskUserCard answer never reaches the AI**

*Affects: Plan 07*

`AskUserCard.onAnswer` calls `setMessages(prev => [...updatedPrev, { role: 'user', content: text, ... }])` to inject the answer as a user message. The plan comment says "Auto-submit the answer as a new user message (handleSubmit will be triggered by the user message injection above)." **React state updates do not trigger `handleSubmit`.** The answer appears as a user bubble in the chat but is never sent to the edge function. The AI never sees the user's response and the ask_user flow produces a dead end.

**Fix:** After `setMessages`, call `handleSubmit` programmatically with the answer text. Or, instead of injecting into state and expecting auto-fire, call `handleSubmit(text)` directly from `onAnswer`, passing the answer text as the prompt. Plan 08 should also persist the `answered` state before the submit fires so the card renders in answered state on reload.

---

#### MEDIUM — Cost/Performance Issues

**M-01: RAG always runs at DEFAULT_RAG_K regardless of which tool the model will select**

*Affects: Plan 03*

The per-tool K config in `rag.ts` (`ask_user: {regulatory: 0, proposal: 0}`, `set_focus: {regulatory: 0, proposal: 0}`) is never used. `index.ts` calls `fetchRagContext(org_id, user_message, DEFAULT_RAG_K)` — always K=5+5. The model hasn't selected a tool yet at this point. `ask_user` and `set_focus` are designed to skip retrieval entirely (K=0), but every "switch focus to the budget section" message still runs a full vector search. For high-frequency sessions this doubles the RAG cost.

**Mitigation options:**
- (a) Use a lightweight heuristic to predict tool before RAG (partial intent detection — reintroduces the problem we're removing).
- (b) Run RAG lazily inside each tool handler rather than upfront (changes the streaming architecture).
- (c) Accept the cost for 14.1 and revisit in 14.2 once usage patterns are known. (Simplest — document as known limitation.)

Option (c) is likely the right call for this phase since the architecture change is the goal, not the cost optimization. But it should be documented explicitly rather than silently broken.

---

**M-02: Compliance DB write blocks SSE tool_result delivery**

*Affects: Plan 09*

`handleCheckCompliance` is made async for the DB write. `index.ts` `await`s it. This means the `tool_result` SSE event is blocked by the Supabase round-trip (add ~100–500ms). For a compliance check that already takes 2–4s, adding DB latency before the result reaches the user is noticeable. The silent-fail is there but the latency is not.

**Fix:** Fire the DB write in the background, don't await it. Return the result immediately:
```typescript
// Don't await — fire and forget
void writeComplianceFlagsToDb(flagsForDB, proposalId, orgId)
return { section_key: ..., passes: effectivePasses, ... }
```

---

#### MEDIUM — Logic Errors

**M-03: compliance flags always written, even when issues array is empty**

*Affects: Plan 09*

```typescript
if (proposalId && orgId && flagsForDB.length >= 0) {
```

`Array.length >= 0` is **always true**. When the compliance check returns zero issues (section passes cleanly), this writes an empty array `[]` to `proposal_sections.compliance_flags`, clearing any flags previously set by `useComplianceCheck.ts`. A passing compliance check from the AI tool would silently erase rule-based flags from the existing hook.

**Fix:** `flagsForDB.length > 0` — only write when there are flags to write.

---

**M-04: `buildSlidingWindow` stops at first message that doesn't fit**

*Affects: Plan 04*

```typescript
if (used + cost > budgetChars) break
```

If message N (say, a long AI response with a full document excerpt) exceeds the budget, the loop breaks and excludes N-1, N-2, etc. even if those earlier messages would fit. This can exclude most of the chat history when one large message early in the window consumes the budget. A skip-and-continue approach (skip the oversized message, keep collecting smaller ones) would give Claude more history context.

This is a behavioral regression from the old 8000-char window: the old window had the same break logic but at a much lower budget, so it was less likely to strand large chunks of context. At 42000 chars the break-on-first-miss can leave the AI with 0 messages of history if the most recent message is a large diff payload.

**Fix:** Change `break` to `continue` so that smaller messages later in the loop (earlier in history) can still be included.

---

#### LOW — Minor Issues

**L-01: `chat_sessions` schema carries 14.2-specific columns**

*Affects: Plan 01*

`active_task jsonb`, `pending_actions jsonb`, `resolved_items jsonb` are listed as 14.2 non-goals (action queue UI, multi-turn walkthroughs). Including them in the 14.1 migration adds schema debt. The columns are nullable so they don't break anything, but they create implicit coupling with 14.2 scope.

**Recommendation:** Either create these in 14.2 migration or document explicitly that they're pre-provisioned for 14.2.

---

**L-02: `Promise.all([fetchRagContext(...)])` wraps a single item**

*Affects: Plan 03*

```typescript
const [ragContext] = await Promise.all([
  fetchRagContext(org_id, user_message, DEFAULT_RAG_K),
])
```

`Promise.all` with a single-element array is functionally identical to `await fetchRagContext(...)`. The comment "RAG retrieval runs in parallel with message assembly" implies a second concurrent operation was planned but not included. Either add the intended concurrent operation or simplify to a direct await.

---

**L-03: `retrieve-context` K-cap not implemented despite being in threat model**

*Affects: Plan 02*

Threat T-14.1-04 specifies: "Cap effective K values: `Math.min(k_regulatory ?? RETRIEVAL_K_REGULATORY, 20)`" to prevent DoS via large K values. The task action does not include this cap. The threat is documented but the mitigation is not implemented.

**Fix:** Add `Math.min(k_regulatory ?? RETRIEVAL_K_REGULATORY, 20)` when computing `effectiveKRegulatory`.

---

**L-04: Stale paragraph state survives panel close but the stale detection fires at apply-time**

*Affects: Plans 04, 06*

`applyParagraphPatch` returns a `stale: string[]` result. Plan 06 logs stale IDs as a console warning and comments "will be persisted in Plan 08." But Plan 08 never adds stale ID persistence to the state mutation wiring — the `stale_ids` field from `ToolDataEnvelope.state` is used in `DiffPreview` props (`staleIds={state.stale_ids ?? []}`) but is only populated if the caller explicitly writes to `state.stale_ids` after calling `applyParagraphPatch`. In the Plan 06 onAccept handler, stale IDs are logged but not written back to `msg.toolData.state.stale_ids`. DiffPreview's stale row UI will never render.

**Fix:** After `applyParagraphPatch`, if `result.stale.length > 0`, merge them into `msg.toolData.state.stale_ids` in the same `setMessages` update.

---

**L-05: `model: "claude-sonnet-4-6"` hardcoded in edge function**

*Affects: Plan 03*

Model ID is hardcoded as a string literal. When Anthropic updates model versions, this requires an edge function redeploy. Extract as a constant:
```typescript
const CHAT_MODEL = Deno.env.get("CHAT_MODEL") ?? "claude-sonnet-4-6"
```

---

### 4. Suggestions

- **H-01 fix (UUID):** Pass the client-generated UUID as the DB `id` when inserting tool-result messages. Add to the insert: `id: localMsg.id`. This makes `persistToolDataState` work without needing to reconcile server-returned IDs.

- **H-02 fix (AskUserCard):** Expose `handleSubmit` or a `submitMessage(text: string)` helper from `AIChatPanel`. Pass it as `onAnswer` prop to `AskUserCard`. The handler should call `submitMessage(text)` after updating the answered state.

- **M-02 fix (compliance DB latency):** Extract the DB write into a fire-and-forget function. The `async/await` refactor in index.ts is unnecessary if the DB write doesn't block the return.

- **M-03 fix (empty flags guard):** Change `>= 0` to `> 0` on the compliance flags write condition.

- **M-04 fix (sliding window):** Change the `break` in `buildSlidingWindow` to `continue` so oversized messages are skipped rather than truncating the entire history walk.

- **L-03 fix (K cap):** Add `Math.min(..., 20)` cap when computing effective K values in retrieve-context.

- **L-04 fix (stale IDs):** In the `onAccept` handler in Plan 06, after getting `result.stale`, merge them: `stale_ids: [...(prevState.stale_ids ?? []), ...result.stale]` in the same `setMessages` call.

- **General:** Add a stream timeout to the Anthropic `messages.stream()` call in the edge function. If the model hangs (rare but possible), the SSE connection stays open indefinitely. A 60s timeout with a `stream_interrupted` error event closes the loop gracefully.

---

### 5. Risk Assessment

**Overall: MEDIUM**

The wave structure, type system, and security threat model are production-quality. The phase will compile and tests will pass as written. However, two silent production bugs (H-01 UUID mismatch, H-02 AskUserCard submit) will make the accept/reject and ask_user features non-functional in production despite passing all automated checks. These require targeted fixes before execution, not a replan. The other issues (M-01 RAG cost, M-02 latency, M-03 empty flags, M-04 sliding window) are behavioral but not crashes.

**Recommended path:**
1. Fix H-01 (UUID) in Plan 05 and Plan 08 before execution
2. Fix H-02 (AskUserCard submit) in Plan 07 before execution
3. Fix M-03 (`>= 0` → `> 0`) in Plan 09 before execution
4. Document M-01 (RAG K optimization) as a known 14.2 improvement
5. Apply remaining fixes (M-02, M-04, L-03, L-04) as part of execution

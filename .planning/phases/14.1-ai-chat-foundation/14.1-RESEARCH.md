## Executive Summary

The codebase is well-positioned for this migration. The edge function is small (154 lines) and the dead code is clearly isolated. The biggest risk is the paragraph-ID strategy: `@tiptap/extension-unique-id` exists on npm up to v3.23.2 — matching the project's TipTap v3.20–3.22 range — but it is **not currently installed**. The PlaceholderMark custom extension proves the team can write TipTap Node extensions with custom attributes and ProseMirror plugins, which is exactly the skill needed if UniqueID requires any project-specific configuration. The `retrieve-context` edge function does **not** currently accept per-tool K values — it uses hardcoded constants (`RETRIEVAL_K_REGULATORY = 5`, `RETRIEVAL_K_PROPOSALS = 5`) and returns a combined `systemPromptBlock` string. This must be extended to accept `k_regulatory` / `k_proposal` params and return raw chunk arrays so `chat-with-jamo` can assemble tool-specific context. The `proposal_chats` table has no `tool_data` column yet. The `chat_sessions` table does not exist yet. Both require migrations. The Anthropic SDK in the edge function is already at `npm:@anthropic-ai/sdk` (v0.78.x in package.json for client — the Deno edge function imports `npm:@anthropic-ai/sdk` directly and will pick up latest unless pinned).

**Primary recommendation:** Implement in this order: (1) DB migrations, (2) retrieve-context extension, (3) tool schemas, (4) edge function rewrite, (5) TipTap UniqueID + ProseMirror apply-patch, (6) AIChatPanel new message types, (7) new UI components.

### How UniqueID Works [ASSUMED — based on TipTap v2 docs and v3 npm package existence; behavior not verified against v3 source]

The extension assigns a UUID to each node (paragraph, heading, etc.) as a **node attribute** named `id`. Key properties:

- IDs survive content edits — the attribute is on the node wrapper, not the content.
- IDs are serialized to HTML as `data-id="<uuid>"` attributes when `renderHTML` is configured.
- On `setContent()` or `insertContent()`, nodes without existing IDs get new UUIDs assigned automatically via a ProseMirror plugin.
- **Autosave watch-out (D-02):** The ID assignment plugin fires a transaction on editor mount (to assign IDs to loaded content). This transaction will trigger `onUpdate`, which triggers `triggerAutosave`. This is harmless if autosave is idempotent (same HTML with IDs added), but adds a spurious save on every load. Mitigation: compare `getHTML()` before and after the ID assignment transaction and skip autosave if only attributes changed — or accept the extra save as benign (IDs need to be persisted to DB anyway so the AI can reference them).
- **Serialization:** IDs appear in `editor.getHTML()` output as `data-id` attributes. This means the content stored in `proposal_sections.last_saved_content` (and sent to `chat-with-jamo`) will contain the IDs — exactly what is needed.
- **Retroactive assignment:** Existing sections loaded without IDs will get IDs assigned on first editor mount. No migration needed for DB content — IDs appear in the live editor state and persist on next autosave.

### Configuration Pattern [ASSUMED — based on TipTap v2 docs]

```typescript

const editor = useEditor({
  extensions: [
    StarterKit,
    // ... other extensions
```

## ProseMirror Transaction Mechanics

### Finding a Node by UniqueID Attribute [VERIFIED: ProseMirror docs pattern via project's existing PlaceholderMark implementation]

The PlaceholderMark extension already uses `editor.state.doc.descendants()` to walk the doc and find nodes by mark attribute. The same pattern works for node attributes:

```typescript
function findNodePosByParagraphId(
  doc: ProseMirrorNode,
  paragraphId: string
): { node: ProseMirrorNode; pos: number } | null {
  let result: { node: ProseMirrorNode; pos: number } | null = null
  doc.descendants((node, pos) => {
    if (result) return false  // stop traversal once found
    if (node.attrs?.id === paragraphId) {
      result = { node, pos }
      return false
    }
  })
  return result
}
```

### Replacing Node Content (Targeted Transaction) [VERIFIED: ProseMirror API — used in PlaceholderMark resolution plugin]

```typescript
function applyParagraphReplace(
  editor: Editor,
  paragraphId: string,
  afterHtml: string
): boolean {
  const found = findNodePosByParagraphId(editor.state.doc, paragraphId)
  if (!found) return false  // stale ID — reject this change

  const { node, pos } = found
  const newNode = editor.schema.nodeFromJSON(
    // Parse afterHtml into a ProseMirror node
    // Use DOMParser or editor.commands.insertContentAt internals
  )

  // Each accepted paragraph gets its own transaction (separate undo step)
  const tr = editor.state.tr.replaceWith(
    pos,
    pos + node.nodeSize,
    newNode
  )
  tr.setMeta('addToHistory', true)   // ensures undo step
  editor.view.dispatch(tr)
  return true
}
```

**Key decisions:**
- Each paragraph acceptance dispatches its own transaction with `addToHistory: true` → each accepted paragraph is its own undo step. [ASSUMED — standard ProseMirror pattern; verify behavior]
- Parse `afterHtml` using `editor.view.dom` DOMParser or `editor.commands.insertContentAt` with a position offset. The safest approach is using TipTap's `generateJSON` utility (from `@tiptap/core`) to convert HTML → ProseMirror JSON, then `schema.nodeFromJSON`. [ASSUMED]
- For `delete` operations: `tr.delete(pos, pos + node.nodeSize)`.
- For `insert_after` operations: `tr.insert(pos + node.nodeSize, newNode)`.

### Validating Paragraph IDs Before Applying [VERIFIED: pattern from PlaceholderMark]

Before accepting a `propose_edit` tool result, the client must validate all `paragraph_id` values in `changes`:

```typescript
function validateParagraphIds(
  doc: ProseMirrorNode,
  changes: ProposeEditChange[]
): { valid: ProposeEditChange[]; stale: ProposeEditChange[] } {
  const valid: ProposeEditChange[] = []
  const stale: ProposeEditChange[] = []
  for (const change of changes) {
    if (!change.paragraph_id) { valid.push(change); continue }  // insert_after new
    const found = findNodePosByParagraphId(doc, change.paragraph_id)
    found ? valid.push(change) : stale.push(change)
  }
  return { valid, stale }
}
```

Stale IDs go into `tool_data.state.stale_ids` and render as a warning chip ("This paragraph was removed — discard suggestion?").

## Anthropic Tool-Use Streaming — SSE Event Forwarding

### What the Edge Function Currently Does

Line 133: `controller.enqueue(encoder.encode(`data: ${JSON.stringify(event)}\n\n`))` — forwards ALL Anthropic SDK events raw. [VERIFIED: codebase read]

This means `content_block_start` events ARE currently forwarded, but the client ignores them. The new architecture needs the edge function to:
1. Intercept `content_block_start` events where `content_block.type === 'tool_use'`
2. Send a custom `{ type: 'tool_start', tool: name, tool_use_id: id }` SSE event
3. Accumulate `input_json_delta` in a server-side buffer (never forward partial JSON)
4. On `content_block_stop`, parse and dispatch the tool handler, then send `{ type: 'tool_result', tool: name, result: toolData }`
5. Continue forwarding `text_delta` events for any plain-text content blocks

### Multi-Tool Turn Handling [VERIFIED: AI-SPEC.md pattern]

Buffer reset pattern for multi-tool turns (e.g., `set_focus` + `propose_edit` in one response):

```typescript
let currentToolName: string | null = null
let currentToolId: string | null = null
let jsonBuffer = ''

for await (const event of stream) {
  if (event.type === 'content_block_start') {
    if (event.content_block.type === 'tool_use') {
      currentToolName = event.content_block.name
      currentToolId = event.content_block.id   // needed for multi-turn tool results
      jsonBuffer = ''
      sendSSE({ type: 'tool_start', tool: currentToolName })
    }
  }

  if (event.type === 'content_block_delta') {
    if (event.delta.type === 'text_delta') {
      sendSSE({ type: 'text_delta', text: event.delta.text })
    } else if (event.delta.type === 'input_json_delta') {
      jsonBuffer += event.delta.partial_json   // accumulate — never forward partial
    }
  }

  if (event.type === 'content_block_stop' && currentToolName) {
    const toolInput = JSON.parse(jsonBuffer)   // safe — only parse on stop
    const toolResult = await handleToolCall(currentToolName, toolInput, ctx)
    sendSSE({ type: 'tool_result', tool: currentToolName, result: toolResult })
    // Reset for next potential tool block
    currentToolName = null
    currentToolId = null
    jsonBuffer = ''
  }
}
```

**Critical:** `await` inside the SSE loop for `handleToolCall` is unavoidable — tool handlers need to make DB writes (e.g., `set_focus` writes to `chat_sessions`). This is acceptable because the Deno runtime supports it, but means the stream is paused during tool handling. For Sonnet 4.6 the model completes the full tool input before `content_block_stop` fires, so the user already sees the status label before the pause begins.

### Client-Side SSE Changes (AIChatPanel)

The client SSE event handler currently (lines 406–416) only handles `{ type: 'intent' }` and `{ type: 'content_block_delta', delta: { type: 'text_delta' } }`.

## Open Risks

### Risk 1: TipTap UniqueID Autosave Loop — HIGH

**What could go wrong:** UniqueID extension fires a transaction on editor mount to assign IDs to all existing nodes. This triggers `onUpdate` → `triggerAutosave`. Every section loads with a spurious autosave that writes the same content back with IDs added. This is not data loss, but wastes Supabase writes and may confuse the "Saved" status indicator on load.

**Mitigation:** On `onUpdate`, compare old and new HTML. If the only difference is added `data-id` attributes, skip the autosave dispatch. Alternatively, accept the extra save as necessary (IDs must be persisted to DB for the AI to reference them on the next call).

**Verification step:** Test with `console.log` in autosave to count saves on a section with 5 paragraphs — should be 1 (initial ID assignment) or 0 (if UniqueID is smart enough to suppress the transaction).

### Risk 2: `@tiptap/extension-unique-id` v3 API Differences — MEDIUM

**What could go wrong:** The v3 package exists but may have renamed exports, changed `configure()` options, or changed how IDs are stored (e.g., `attributeName` default or HTML attr name may differ from v2 docs).

**Mitigation:** After `npm install`, inspect `node_modules/@tiptap/extension-unique-id/dist/index.js` for export names and defaults before writing integration code. The PlaceholderMark pattern (custom attributes + `parseHTML`/`renderHTML`) is the fallback if UniqueID doesn't work — implement `data-paragraph-id` via a custom TipTap Node extension using the same pattern.

### Risk 3: `compliance_flags` Schema Conflict — MEDIUM

**What could go wrong:** The existing `useComplianceCheck` hook writes to `proposal_sections.compliance_flags` with a specific JSONB shape. The `check_regulatory_compliance` tool also writes to this column. If their schemas differ, either the hook or the tool result overwrites the other's data silently.

**Mitigation:** Before implementing the compliance tool handler, read `useComplianceCheck.ts` and document the exact JSONB shape it writes. The tool handler must produce the same shape (or a superset). This is a pre-implementation code audit step, not a design-time decision.

### Risk 4: `await` Inside SSE Loop — MEDIUM

**What could go wrong:** Tool handlers that make Supabase writes (set_focus → `chat_sessions`, compliance → `proposal_sections`) are `async`. Awaiting them inside the SSE forwarding loop pauses the stream. If the Deno edge function has a tight timeout and the tool handler is slow, the stream may time out before `[DONE]` is sent.

**Mitigation:** Keep tool handlers fast. `set_focus` is a single Supabase upsert — <50ms. `propose_edit` does no DB write (returns data to client). `check_regulatory_compliance` writes compliance_flags — single upsert. The only tool that could be slow is `answer_with_citations` if it does additional RAG. Since RAG runs before the Anthropic call in parallel, the tool handler itself should be lightweight.

### Risk 5: History Budget with Tool Result Blobs — MEDIUM

**What could go wrong:** A `propose_edit` result with 10 before/after HTML pairs is several KB. If stored in history as full JSON, the 8000-char sliding window will drop all prior context after a single edit exchange, leaving the AI without session context.

**Mitigation:** Tool results in history messages should be summarized: store `overall_summary` + list of accepted/rejected paragraph IDs, not full before/after HTML. The `buildSlidingWindow` upgrade to `chars / 3.5` token estimation helps, but the summarization is the key lever. Full `tool_data` is stored in the DB column for UI reconstruction — it does not need to be in the history window.

### Risk 6: `retrieve-context` Parallel Call for All Tools — LOW

**What could go wrong:** For `propose_edit`, the pre-tool RAG retrieval runs before the model call (parallel with message assembly). But the tool selection is determined by the model during the call — we don't know which tool will be selected before the call starts. So we either (a) always retrieve at max K (wasteful for `set_focus`/`ask_user`) or (b) pre-classify with a Haiku call to decide K before retrieval.

**Recommendation:** Option (a) — always retrieve at `propose_edit` K values (5+5). Skip retrieval only if the client sends a signal that the message is clearly a `set_focus` (e.g., clicking a section title chip). The latency overhead of unnecessary retrieval for `ask_user` messages is small compared to the complexity of a Haiku pre-classification call.

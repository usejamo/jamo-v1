# Phase 14.1: AI Chat Foundation — Context

**Gathered:** 2026-05-12
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the fragile keyword-based chat (`detectIntent()`, `EDIT_KEYWORDS` arrays) with a structured Claude tool-use architecture. The AI executes defined tools — paragraph-level edits, cited answers, compliance checks, section focus, user prompting — instead of parsing free-text output. Streaming logic, chat persistence, and the TipTap editor are all updated to support this. This phase ships independently and is immediately usable on its own.

**Non-goals (14.2):** Action queue UI, proactive gap surfacing, multi-turn walkthroughs, resume-on-reload UX, section-scoped thread filtering.

</domain>

<decisions>
## Implementation Decisions

### D-01 — Paragraph Identification: @tiptap/extension-unique-id

Install `@tiptap/extension-unique-id`. ProseMirror node attributes survive every transform, copy/paste, undo/redo, and serialization by design.

**Rejected:**
- Position-based patching: race conditions when user edits during streaming or accepts diffs computed against stale indices.
- `data-paragraph-id` HTML attributes: silent ID loss on any HTML roundtrip without the custom serializer (paste, copy, AI tools returning clean HTML, future imports).

**Watch-outs for planner:**
- AI-generated new or restructured paragraphs must have fresh UUIDs minted **client-side** at diff application time. The AI must never supply IDs for additions — those don't exist yet.
- Verify the extension's default serialization keeps IDs in node attributes only (no visible text, no copy-paste artifacts).
- Install and wire the extension before any diff logic is written — everything downstream depends on IDs being present.

### D-02 — Retroactive ID Assignment: Lazy on Editor Mount

When `SectionEditorBlock` initializes with existing content, the UniqueID extension auto-assigns IDs to nodes that don't have them. No migration step required.

**Rejected:** One-time headless migration — adds real complexity (headless TipTap in Deno/Node, schema parity, rollback story) to solve a problem that mostly isn't real. Proactive 14.2 features operate on sections the user is engaging with, not unopened ones.

**Watch-outs for planner:**
- **The first-open write must persist.** When the extension assigns IDs on mount, the editor must flag the doc as dirty so autosave writes the ID-bearing HTML back to DB. Verify whether UniqueID dispatches a transaction that triggers the existing autosave path or not. If not, manually trigger a silent autosave after ID assignment.
- **Guard against ID-only diffs polluting version history.** If version snapshots are taken on autosave, the first-open ID-assignment save will look like a meaningful version. Either suppress snapshotting when the only change is ID assignment, or treat the save as a silent migration write. Decide and implement explicitly.
- **Concurrent first-open across tabs:** last-write-wins, no corruption. Do not over-engineer a lock for this — document it as known-safe behavior.

### D-03 — Diff Application Mechanics: Immediate Per-Paragraph ProseMirror Transactions

When `propose_edit` arrives, render a per-paragraph diff UI. Clicking Accept on a single paragraph fires a targeted ProseMirror transaction that replaces just that node by ID — immediately, before the user acts on other paragraphs. Rejection is a no-op against the editor (just dismisses that row in the chat preview).

**Rejected:** Staged apply (hold all in memory, apply atomically) — the editor should reflect each accept immediately so the user can see how the accepted change reads in context before committing the rest.

**Watch-outs for planner:**
- **Locate by ID at click time, not from cached reference.** Between diff generation and user Accept, the user may have edited the doc. If the target paragraph no longer exists (user deleted it), fail gracefully: UI message "This paragraph was removed — discard suggestion?" with a Discard button.
- **`before` snapshot is for display only.** Never use text matching as a fallback to locate the paragraph. The ID is the only source of truth. If the ID is gone, the suggestion is stale.
- **Three apply paths needed:** `replace-by-id`, `insert-after-id` (fresh UUID minted client-side), and `delete-by-id`. All three must be implemented — edits aren't only modifications.
- **Each accepted paragraph = its own undo step.** ProseMirror transaction grouping is the lever — verify the default behavior gives one undo per accept, not one giant bundled undo for all siblings. Adjust with `setMeta` if needed.
- **Partial-accept state must survive panel collapse.** Remaining pending paragraphs (not yet accepted or rejected) must still be present in the chat with their affordances after the user collapses and reopens the panel. This is solved by the persistence design (D-07) — `tool_data.state` tracks per-paragraph resolution.

### D-04 — Tool Result Streaming UX: Status Label Naming the Action

When the first SSE event identifies which tool the model is invoking (`content_block_start`), replace the thinking-dot indicator with a labeled status: "Drafting your edit...", "Searching the protocol...", "Checking compliance...", "Finding sources...". The full tool result renders all at once when the JSON is assembled.

**Rejected:**
- Generic thinking dots throughout: wastes the "I know what I'm doing" signal that structured tool use provides. Especially relevant for `check_regulatory_compliance` and `propose_edit` which take longer.
- Progressive text from partial JSON: parsing incomplete JSON requires fragile heuristics that misfire on long-tail cases.

**Watch-outs for planner:**
- **The edge function must forward `content_block_start` events** with the tool name so the client knows which label to show before the JSON body finishes streaming. Confirm this is included in the SSE forwarding loop.
- **Fallback:** when the model returns plain text (no tool call), the label-swap never fires and the existing thinking-dots-into-streaming-text behavior continues. Both paths must be handled cleanly.
- **Multi-tool chains:** if the model calls `set_focus` then `propose_edit` in one turn, the label updates as each `content_block_start` arrives — not frozen on the first tool.
- **Fast tools:** accept dots→result as de facto behavior for tools that complete in <300ms. Don't add a minimum display time unless testing reveals it's needed.

### D-05 — TOOL_STATUS_LABELS: Client-Side Constant

A `TOOL_STATUS_LABELS: Record<ToolName, string>` constant lives in `src/constants/chatLabels.ts` (or co-located in `src/types/chat.ts`). The edge function emits the tool name; the client maps name → label at render time. UI copy belongs in the frontend, not a Deno edge function.

**Rejected:** Server-sent labels — UI copy doesn't belong in a Deno function; iterating on label wording shouldn't require an edge function redeploy.

**Watch-outs for planner:**
- `ToolName` defined as a string-literal union in `types/chat.ts`. `TOOL_STATUS_LABELS` typed as `Record<ToolName, string>` so TypeScript flags missing labels when a new tool is added.
- Fallback for unknown tool names: `?? 'Working...'` at the lookup site — never render `undefined`.
- Label tone convention: **present-progressive, implied first-person** ("Drafting your edit...", not "Edit drafted" or "Drafting edit"). Document this convention next to the constant.

### D-06 — Section Title Resolution: sectionTitles Prop from Sidebar

Add `sectionTitles: Record<string, string>` as a prop to `AIChatPanel`. `Sidebar.tsx` already has the template definition in scope and builds this map with `useMemo` keyed on the template definition. Zero DB roundtrips.

**Rejected:**
- Fetch in edge function: adds a DB roundtrip to every chat message to recover data the client already has.
- Hardcoded map: templates are data, not constants. Different orgs may have custom sections; template definitions evolve.

**Watch-outs for planner:**
- **Build with `useMemo` keyed on template definition** in Sidebar — not per-render object literal.
- **Fallback for missing keys:** if a `section_key` isn't in the map (template transition, ad-hoc section), humanize the key: replace underscores with spaces and title-case. One utility function, used at every title-lookup site.
- **Audit every surface where `section_key` currently appears in AI-facing or user-facing strings:** `buildContextPayload` (`target_section.title`, `other_sections[].title`), gap message formatting (`formatGapMessage`), tool inputs referencing sections, citation displays. All must resolve through the same map.
- **Assume template doesn't change mid-session** (verify this assumption — if it can change, the map needs to be reactive to template updates).

### D-07 — Tool Result Persistence: tool_data jsonb Column on proposal_chats

Add a nullable `tool_data jsonb` column to `proposal_chats`. For tool result messages: `content` holds the human-readable summary (bubble fallback text); `tool_data` holds the full structured payload.

**Rejected:**
- Normalized `proposal_chat_tools` table: adds a join on every history load, second migration, no independent query use case to justify it.
- Serialize in content with new `message_type` values: poisons `content` with a mix of markdown and JSON, breaks future full-text search, compounds with every new tool.

**`tool_data` envelope schema:**
```jsonc
{
  "tool": "propose_edit" | "answer_with_citations" | "ask_user" | "set_focus" | "check_regulatory_compliance",
  "version": 1,
  "payload": { /* tool-specific, immutable */ },
  "state": { /* mutable: per-paragraph accept/reject, dismissed issues, answered prompts */ }
}
```

**Watch-outs for planner:**
- **`version` field is non-negotiable.** When tool schemas evolve, rows from old versions must degrade gracefully. Loader must check `version` and handle ≥ 1 variants without crashing.
- **Mutable state in `tool_data.state`.** Per-paragraph accept/reject, dismissed compliance issues, answered `ask_user` prompts all mutate after the message is created. For 14.1: mutate `tool_data.state` in place (single source of truth, atomic with the row). Each accept/reject triggers an UPDATE on `proposal_chats`. Revisit if 14.2 session state makes a cleaner separation natural.
- **RLS is inherited** from the existing `proposal_chats` row-level policy (org-scoped). Confirm the existing policy covers SELECT/INSERT/UPDATE — no new RLS work needed.
- **Loader reconstruction:** the new loader reads `tool_data.tool` and `tool_data.state` to decide what to render. The `edit-proposal → chat` hack on history load is removed. Backward compatibility: `tool_data IS NULL` = legacy plain-text message, render as today. No backfill needed.
- **Size concern:** diff patches with full before/after HTML for a 10-paragraph section can be 20–50 KB of JSON. JSONB handles this. Consider truncating `tool_data.payload.before/after` once all paragraphs in a diff are resolved (replacing with a compact resolution record) to manage long-running proposal chat sizes.

### D-08 — Compliance Flags Integration (Carried from Phase 999.1)

`check_regulatory_compliance` tool writes results to `proposal_sections.compliance_flags JSONB` via upsert on the existing row. The `ComplianceFlag` interface in `src/types/workspace.ts` is the source of truth for the flag shape. The tool does NOT create a parallel mechanism.

`useComplianceCheck.ts` already dispatches `SET_COMPLIANCE_FLAGS` and runs Haiku checks — the new tool extends this pattern rather than replacing it.

### Claude's Discretion

- Exact schema for each tool's `payload` shape within `tool_data` (beyond the envelope) — planner can design these based on the tool definitions
- Whether `TOOL_STATUS_LABELS` is co-located in `types/chat.ts` or in a new `src/constants/chatLabels.ts` file
- Whether the first-open autosave for ID assignment uses a "silent save" flag to suppress version history, or defers to existing autosave path if the extension dispatches a transaction automatically
- Error handling specifics for failed `tool_data` upserts (silent fail acceptable, same as compliance flag upserts)

</decisions>

<specifics>
## Specific Ideas (from discussion)

- **`TOOL_STATUS_LABELS` tone convention:** present-progressive, implied first-person ("Drafting your edit...", "Checking compliance...", "Finding sources..."). Document this next to the constant so future tools match.
- **`tool_data` version field:** version 1 from the start. When tool schemas evolve, the loader uses `version` to handle old rows. Non-negotiable.
- **Find-by-ID at accept time:** locate the ProseMirror node by `data-unique-id` at the moment the user clicks Accept — not from a reference cached when the diff arrived. If the node is gone, show "This paragraph was removed — discard suggestion?" prompt.
- **Three diff apply paths:** `replace-by-id`, `insert-after-id` (with fresh client-generated UUID), `delete-by-id`. All three must be implemented.
- **Undo granularity:** each accepted paragraph = its own undo step. Use ProseMirror transaction grouping / `setMeta` to prevent siblings from bundling.
- **`sectionKeyToTitle` fallback:** humanize the key (underscores → spaces, title-case) rather than passing snake_case through. One utility function used at every lookup site.
- **`tool_data` size management:** once all paragraphs in a diff are resolved, consider truncating `before/after` content and replacing with a compact resolution record to control JSONB column growth on long proposals.

</specifics>

<deferred>
## Deferred Ideas

- **Multi-tool per turn (Q5):** `set_focus` + `propose_edit` in one Claude response — the status label design (D-04/D-05) already handles this (label updates per tool). The planner should spec the client-side render ordering explicitly. No user decision needed.
- **Token-aware history window (Q9):** Upgrade `buildSlidingWindow` from 8000-char budget to a `chars / 3.5 ≈ tokens` estimate targeting ~12k token budget for history. The existing function structure supports this; it's a planner-level task.
- **Haiku for lightweight tools (Q10):** whether `set_focus` and `ask_user` calls route through Haiku rather than Sonnet — planner discretion. Cost optimization, not a behavior change.
- **K=0 for `ask_user`/`set_focus` (Q7):** retrieval skip for tools that don't need context — planner discretion based on measured latency.
- **Section-scoped thread filtering:** explicitly 14.2 territory.
- **Action queue UI:** 14.2.

</deferred>

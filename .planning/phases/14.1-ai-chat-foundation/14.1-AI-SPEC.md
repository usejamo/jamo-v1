## 1. System Classification

**System Type:** Hybrid — Conversational Assistant + Structured Tool Use + RAG

**Description:**
An AI-powered proposal writing assistant embedded inside a clinical trial proposal application. The user sends chat messages about a specific section of their proposal; Claude responds by invoking structured tools rather than returning free text. The five tools cover the complete interaction surface: paragraph-level edits (`propose_edit`), regulatory Q&A with citations (`answer_with_citations`), protocol compliance checking (`check_regulatory_compliance`), section focus declaration (`set_focus`), and mid-task user prompting (`ask_user`). Each tool call is backed by RAG retrieval from regulatory documents and the current proposal at per-tool K values tuned for cost and relevance. The system runs on Supabase Deno edge functions using the Anthropic SDK, streams `content_block_start` / `input_json_delta` events to the React client, and persists tool results in a `tool_data jsonb` column on `proposal_chats`.

**Critical Failure Modes:**
1. `propose_edit` locates the wrong paragraph or silently corrupts content — the user loses written work with no undo path and may not notice until later.
2. `check_regulatory_compliance` returns `passes: true` when real compliance issues exist — regulatory problems go undetected and enter the submission.
3. `answer_with_citations` fabricates source references not present in retrieved chunks — user acts on invented regulatory guidance.
4. Streaming failure mid-tool-call delivers partial `input_json_delta` JSON to the client — causes React parse crash or silent data corruption of `tool_data`.
5. History window drops earlier accepted edits from context — AI re-proposes changes already made or contradicts accepted work in the same session.

## 1b. Domain Context

> Researched for clinical research / regulatory submission context.

**Industry Vertical:** Clinical research / pharmaceutical (FDA/ICH regulated)

**User Population:** Proposal writers working on clinical trial submissions — medical writers, regulatory affairs specialists, scientists. Technically proficient in the domain; not necessarily technical with software. Working under deadline pressure; trust the tool's compliance signals.

**Stakes Level:** High

**Output Consequence:** Proposal text enters regulatory submissions (IND, NDA, protocol synopses). Compliance check results influence go/no-go decisions. Regulatory citations are used to justify design choices in submission documents. A false compliance pass or a fabricated citation can cause protocol deviation findings during inspection.

### What Domain Experts Evaluate Against

| Dimension | Good (expert accepts) | Bad (expert flags) | Stakes | Source |
|-----------|----------------------|--------------------|--------|--------|
| Regulatory accuracy | Cites correct ICH/FDA guideline version; clause matches actual text | Cites ICH E6(R2) when E6(R3) applies; invents clause numbers | Critical — wrong version invalidates citation | Retrieved regulatory chunks |
| Compliance specificity | Flags the exact protocol clause violated with a suggested fix | Returns generic "may not comply" without rule reference | High — vague flags are ignored | Protocol document |
| Edit coherence | Proposed paragraph fits scientific context; doesn't introduce new issues | Rewrite changes endpoint language or drops required safety language | High — submitter may not catch on review | Proposal context |
| Appropriate hedging | Qualifies uncertain regulatory interpretations with "per FDA draft guidance" | States ambiguous guidance as definitive fact | Medium — overstated confidence misleads | Retrieved context + model judgment |
| Citation traceability | `passage` quoted is verbatim from retrieved chunk; `chunk_id` resolves | Passage is paraphrased or combined from multiple sources | Critical — inspection requires original source | RAG retrieval metadata |

### Known Failure Modes in This Domain

1. **Regulatory version hallucination** — model cites ICH E6(R2) Annex 2 when E6(R3) is in force; the guideline name is correct but the version and clause reference are wrong.
2. **Protocol-document mismatch** — compliance check reads from regulatory corpus but the actual constraint is in the sponsor's protocol PDF, which may or may not be in the retrieval index.
3. **Edit introductory compliance violations** — `propose_edit` improves readability but removes a regulatory qualifier ("as defined in Section 7.3 of the protocol") that was load-bearing.
4. **Context contamination across sections** — with K=5 proposal retrieval, content from adjacent sections bleeds in and the AI produces an edit that matches the wrong section's requirements.
5. **False confidence on empty retrieval** — when no regulatory chunks are retrieved (query didn't match), the model answers from training data only; the cited regulation exists but the clause reference is wrong.

### Regulatory / Compliance Context

- **ICH E6(R3)** — Good Clinical Practice: governs protocol design language, informed consent, and safety reporting requirements. Supersedes E6(R2) as of 2025.
- **FDA 21 CFR Part 11** — Electronic records; relevant if electronic signatures or audit trails are referenced in proposals.
- **FDA Draft Guidance on Clinical Trial Protocols** — Governs protocol section structure and required content.
- **Sponsor protocol documents** — Must be in the RAG corpus; compliance checks against "the protocol" only work if the sponsor's protocol is indexed.

### Domain Expert Roles for Evaluation

| Role | Responsibility |
|------|---------------|
| Regulatory Affairs Specialist | Labels reference dataset examples; calibrates compliance check rubric; identifies false pass/fail cases from production sampling |
| Medical Writer | Labels edit quality examples; identifies coherence failures and safety-language drops |
| QA/Study Manager | Reviews citation traceability; confirms chunk_id resolves to correct source |

## 2. Framework Decision

**Selected Framework:** Anthropic SDK — TypeScript (npm: `@anthropic-ai/sdk`)

**Version:** `^0.39.0` (latest as of 2026-05 — already used in the codebase; pin to minor in `package.json` or `deno.json`)

**Rationale:**
The system already runs on Supabase Deno edge functions with direct Anthropic SDK calls. Claude tool-use (`tools[]` + `tool_choice: 'auto'`) is a first-class SDK primitive requiring zero abstraction layer. The interaction pattern is single-agent, single-turn — the user sends a message, Claude calls one or more tools, the client renders results. LangChain/LangGraph would add dependency weight, Deno compatibility surface, and a learning curve with no architectural benefit for this pattern. The 14.2 stateful session (active tasks, resume-on-reload) will be managed via Supabase `chat_sessions`, not a framework.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| LangGraph (TypeScript) | Overkill for single-agent single-turn; stateful session managed in Supabase; adds graph mental model complexity |
| LlamaIndex (TypeScript) | RAG retrieval already in a separate `retrieve-context` edge function; LlamaIndex is the retrieval layer, not what's being built here |
| Vercel AI SDK | Doesn't expose raw Anthropic `content_block_start` / `input_json_delta` events needed for tool-name status labels (D-04 in CONTEXT.md) |

**Vendor Lock-In Accepted:** Yes — Claude tool-use format and streaming event shapes are Anthropic-specific. Accepted: this is an existing Claude deployment; migration cost is a deliberate product decision.

### Entry Point Pattern — Tool-Use Streaming

```typescript
const anthropic = new Anthropic({ apiKey: Deno.env.get("ANTHROPIC_API_KEY") });

// Tool definitions (one per tool file in tools/ directory)
const tools: Tool[] = [proposeEditTool, answerWithCitationsTool, /* ... */];

// Main streaming call
const stream = anthropic.messages.stream({
  model: "claude-sonnet-4-6",
  max_tokens: 4096,
  system: buildSystemPrompt(tools),   // single unified system prompt describing tool set
  tools,
  tool_choice: { type: "auto" },
  messages: buildHistory(chatHistory, ragContext),
});

// SSE forwarding loop — handles both text and tool_use blocks
let currentToolName: string | null = null;
let jsonBuffer = "";

for await (const event of stream) {
  if (event.type === "content_block_start") {
    if (event.content_block.type === "tool_use") {
      currentToolName = event.content_block.name;
      jsonBuffer = "";
      // Forward tool name so client can show status label
      sendSSE({ type: "tool_start", tool: currentToolName });
    }
  }

  if (event.type === "content_block_delta") {
    if (event.delta.type === "text_delta") {
      sendSSE({ type: "text_delta", text: event.delta.text });
    } else if (event.delta.type === "input_json_delta") {
      jsonBuffer += event.delta.partial_json;
      // Do NOT forward partial JSON — accumulate and send complete
    }
  }

  if (event.type === "content_block_stop" && currentToolName !== null) {
    const toolInput = JSON.parse(jsonBuffer);  // safe — only parse on stop
    const toolResult = await handleToolCall(currentToolName, toolInput, context);
    sendSSE({ type: "tool_result", tool: currentToolName, result: toolResult });
    currentToolName = null;
    jsonBuffer = "";
  }
}

// Await final message (for stop_reason, usage)
const finalMessage = await stream.finalMessage();
```

### Key Abstractions

| Concept | What It Is | When You Use It |
|---------|-----------|-----------------|
| `tools[]` | Array of `Tool` objects with `name`, `description`, `input_schema` | Passed on every call; Claude decides which to invoke |
| `tool_choice: { type: "auto" }` | Let Claude decide whether/which tool to call | Default for conversational assistant; never force a tool in this phase |
| `content_block_start` (tool_use) | Stream event announcing a tool invocation — contains `name` and `id` | Fire status label update to client immediately on this event |
| `input_json_delta` | Partial JSON of the tool's input — accumulate, never parse partial | Buffer until `content_block_stop` then parse complete JSON |
| `content_block_stop` | Tool input fully received | Safe to parse buffer and call your handler |
| `stream.finalMessage()` | Awaits complete `Message` with all content, usage, stop_reason | Use after loop for usage logging and stop_reason inspection |

### Common Pitfalls

1. **Parsing `input_json_delta` before `content_block_stop`** — partial JSON throws `SyntaxError`. Always accumulate the full buffer before parsing. The stop event is your only safe parse point.
2. **Not forwarding `content_block_start` to the client** — the client has no way to show "Drafting your edit..." until it receives the tool name. The current edge function only forwards `content_block_delta` — this must be extended.
3. **Multi-tool turns with shared buffer** — if Claude calls `set_focus` then `propose_edit` in one turn, `content_block_stop` fires between them. Reset `jsonBuffer = ""` and `currentToolName = null` on each `content_block_stop`, not just at the end of the stream.
4. **`tool_choice: { type: "required" }` on initial message** — forces a tool call even when Claude would answer better as plain text. Use `"auto"` always.
5. **Forgetting `id` on tool_use blocks** — the Anthropic API requires the `tool_use_id` when sending tool results back in multi-turn flows. Capture `event.content_block.id` on `content_block_start` and store alongside the tool name.

## 4. Implementation Guidance

**Model Configuration:**
- **Primary:** `claude-sonnet-4-6` — all tool-use calls including `propose_edit`, `answer_with_citations`, `check_regulatory_compliance`
- **Optional optimization (planner discretion):** `claude-haiku-4-5` for `set_focus` and `ask_user` — these tools do not draft text and don't need Sonnet quality
- **Temperature:** `0` for `check_regulatory_compliance` (determinism critical); `0.3` for `propose_edit` and `answer_with_citations` (some creativity, not random)
- **Max tokens:** `4096` — sufficient for full diff payloads; a 10-paragraph `propose_edit` is ~2k tokens of output
- **Prompt caching:** Enable `cache_control: { type: "ephemeral" }` on the system prompt and static regulatory context blocks to reduce latency on consecutive calls

**Core Pattern:**
Single unified system prompt describing all five tools and when to use each. Claude chooses the tool via `tool_choice: "auto"`. No intent detection, no keyword matching. The system prompt is the only behavioral contract.

**Tool Use:**
Each tool lives in its own file exporting `(1) the Tool schema, (2) the handler function`. The handler receives parsed tool input + request context (proposal, org, session) and returns the `tool_data` payload directly. This keeps `index.ts` as a thin orchestrator.

**State Management:**
- `chat_sessions` table: `current_focus_section` updated on `set_focus` tool result (service role write from edge function)
- `proposal_chats` table: `tool_data jsonb` column stores full tool result payload + mutable `state` (per-paragraph accept/reject, dismissed issues)
- History is reconstructed from `proposal_chats` on each call — no in-memory session state in the edge function (stateless Deno runtime)

**Context Window Strategy:**
- Sliding window via `buildSlidingWindow()` — upgrade budget from 8000 chars to token-estimate-aware: `Math.floor(chars / 3.5)` targeting ~12k tokens for conversation history
- Tool results in history: include `tool_data.payload` summary (not full JSON) to preserve context without blowing the budget
- RAG context injected per call at per-tool K values — not cached in history (retrieved fresh each turn)

## 4b. AI Systems Best Practices

### Structured Outputs — TypeScript Tool Schema (not Pydantic — this is TypeScript/Deno)

Tool schemas are defined as `Anthropic.Tool` objects with JSON Schema `input_schema`. TypeScript types are derived from these schemas and used in handler signatures to get compile-time safety.

```typescript
// tools/propose-edit.ts
import type { Tool } from "npm:@anthropic-ai/sdk/resources/messages";

export interface ProposeEditInput {
  section_key: string;
  overall_summary: string;
  changes: Array<{
    paragraph_id: string;
    operation: "replace" | "insert_after" | "delete";
    before_html?: string;  // present for replace; absent for insert/delete
    after_html?: string;   // present for replace/insert; absent for delete
    change_summary: string;
  }>;
}

export const proposeEditTool: Tool = {
  name: "propose_edit",
  description: "Return a paragraph-level diff for a proposal section. Call when the user asks to expand, rewrite, shorten, change tone, or add content.",
  input_schema: {
    type: "object" as const,
    properties: {
      section_key: { type: "string" },
      overall_summary: { type: "string", description: "One sentence summarizing all changes" },
      changes: {
        type: "array",
        items: {
          type: "object",
          properties: {
            paragraph_id: { type: "string", description: "Existing node ID from the TipTap doc. Omit for new paragraphs." },
            operation: { type: "string", enum: ["replace", "insert_after", "delete"] },
            before_html: { type: "string" },
            after_html: { type: "string" },
            change_summary: { type: "string" }
          },
          required: ["operation", "change_summary"]
        }
      }
    },
    required: ["section_key", "overall_summary", "changes"]
  }
};

// Handler — typed against the schema
export async function handleProposeEdit(
  input: ProposeEditInput,
  ctx: RequestContext
): Promise<ToolDataPayload> { ... }
```

**Validation on handler entry:** Zod or manual check that `paragraph_id` exists in the provided section content for `replace` and `delete` operations. Reject with a structured error if stale IDs are passed — never silently apply.

### Async-First Design

The Deno edge function is already async. Key rules:
- **RAG retrieval runs in parallel with synchronous pre-processing** using `Promise.all()` — never `await` retrieval sequentially before building the message array
- **`stream.finalMessage()` is the only blocking await** after the SSE loop — call it to collect usage and stop_reason after the loop completes
- **Never `await` inside the SSE loop** — if a tool handler is async, collect tool results after `content_block_stop` and send the SSE result before continuing the stream loop (or collect all tool calls and resolve after the full stream completes)

```typescript
// Parallel RAG + message prep
const [ragContext, historyMessages] = await Promise.all([
  fetchRagContext(ragQuery, toolKValues),
  buildHistoryMessages(proposalId, orgId),
]);
```

### Prompt Engineering Discipline

- **System prompt** defines the full toolset, when to use each tool, and what the AI knows about the user's proposal. This is the only behavioral lever — no keyword-based routing.
- **User message** is the raw chat input with no pre-processing or intent injection. Remove `intentHint` from the client payload entirely.
- **Section content in context:** send `{ title, content_with_ids }` — content must include TipTap node IDs so Claude can reference them in `propose_edit`. The title must be the human-readable name (from `sectionTitles` map), not `snake_case`.
- **Token budget discipline:** regulatory context (K=5) + proposal context (K=5) + history window (~12k tokens) + system prompt (~800 tokens) targets ~16k tokens total input. Monitor `finalMessage().usage.input_tokens` for drift.
- **Few-shot in system prompt:** include 1-2 examples of correct tool invocation for `propose_edit` to anchor the `paragraph_id` usage pattern — the model needs to understand it receives IDs in the section content and must reference them, not invent new ones.

### Context Window Management

- **History budget:** `buildSlidingWindow` upgraded to estimate tokens as `chars / 3.5`, targeting 12k token budget. Tool result messages included as summaries only (not full JSON blobs).
- **RAG injection:** fresh on every call at per-tool K values. If the tool is `ask_user` or `set_focus`, skip retrieval entirely (K=0 for both dimensions).
- **Tool result history:** when a `propose_edit` result enters history on the next turn, include only the `overall_summary` and the resolved paragraph IDs (accepted/rejected) — not the full before/after HTML. This keeps the AI informed of what changed without consuming history budget on large HTML diffs.

### Cost and Latency Budget

- **Per-call estimate (Sonnet 4.6):** ~16k input tokens + ~2k output tokens ≈ $0.06–0.10 per chat message at list pricing. RAG retrieval adds ~50-100ms.
- **Caching:** `cache_control: { type: "ephemeral" }` on the system prompt and static regulatory context blocks — cache hits reduce input token cost ~90% on system prompt. High cache hit rate expected since the system prompt doesn't change per-message.
- **Model routing:** `set_focus` and `ask_user` handlers can use `claude-haiku-4-5` (planner discretion) — these tools don't draft text; Haiku is sufficient and ~25x cheaper per token.
- **Latency target:** <3s to first SSE event (status label + thinking indicator). Parallel RAG retrieval is the key lever — sequential retrieval was the primary latency source in the previous architecture.

## 5. Evaluation Strategy

### Dimensions

| Dimension | Rubric | Measurement Approach | Priority |
|-----------|--------|---------------------|----------|
| **Tool selection accuracy** | Correct tool chosen for the user's intent in ≥90% of test cases. "Expand this section" → `propose_edit`; "what does the RFP say" → `answer_with_citations`; "is this compliant" → `check_regulatory_compliance` | Code (compare selected tool to labeled intent in reference set) | Critical |
| **Edit proposal coherence** | Proposed changes are coherent with section scientific context, don't introduce new compliance issues, and target the correct paragraph IDs. Pass/fail per change. | LLM judge (Sonnet) scoring coherence 1–5; domain expert review for compliance-introducing edits | Critical |
| **Citation faithfulness** | Every `passage` in `answer_with_citations` is verbatim (±5 words) in the retrieved chunks. `chunk_id` resolves to correct source. | Code (string match passage against retrieved chunk text) | Critical |
| **Compliance check recall** | For labeled test cases with known compliance issues, `check_regulatory_compliance` identifies ≥80% of flagged issues. Zero false passes on Critical issues. | Human evaluation (regulatory specialist labels ground truth) | Critical |
| **Streaming reliability** | `tool_start` SSE event arrives before `tool_result` SSE event. No parse errors on `tool_result` JSON. Status label matches tool name. | Code (integration test: assert event order, JSON validity, label lookup) | High |
| **History coherence** | AI does not re-propose edits that are marked as accepted in `tool_data.state`. References accepted changes correctly in follow-up messages. | LLM judge (does response contradict accepted state?) | High |
| **Paragraph ID correctness** | All `paragraph_id` values in `propose_edit` responses reference IDs present in the section content sent in the request. No hallucinated IDs. | Code (compare IDs in response against IDs in request payload) | High |
| **Diff granularity** | `propose_edit` targets the minimum number of paragraphs needed. Not replacing the entire section when 1–2 paragraphs need changing. | Code (count changes / section paragraph count ratio; flag if >50% paragraphs changed for small requests) | Medium |

## 6. Guardrails

### Online (Real-Time)

| Guardrail | Trigger | Intervention |
|-----------|---------|--------------|
| **Citation fabrication guard** | `answer_with_citations` response contains a `chunk_id` not present in the retrieved context for this request | Strip citation from response; replace with "Source not found in retrieved documents" note in `tool_data.state.warning` |
| **Compliance false confidence** | `check_regulatory_compliance` returns `passes: true` AND retrieved regulatory chunks for this request is empty (K=0 or no results) | Override `passes` to `null`; inject warning: "No regulatory documents retrieved — this result is based on model training data only. Manual verification required." |
| **Stale paragraph ID** | `propose_edit` returns a `paragraph_id` for a `replace` or `delete` operation that is not present in the section content sent in the request | Reject that specific change; return it in `tool_data.state.stale_ids` for client to display "This paragraph was removed — discard suggestion?" |

### Offline (Flywheel)

| Metric | Sampling Strategy | Action on Degradation |
|--------|------------------|----------------------|
| Tool selection accuracy | Sample 5% of all `chat_sessions` weekly; human spot-check 10 examples from each tool type | Re-calibrate system prompt; add few-shot examples for misrouted intents |
| Compliance check recall | Flag all `check_regulatory_compliance` calls where `passes: true` and `issues` is empty; send to regulatory specialist review monthly | Review system prompt compliance tool description; audit retrieved regulatory corpus coverage |
| Edit coherence | Sample 10% of `propose_edit` calls with >3 changes; LLM judge coherence score | Adjust RAG K for `propose_edit`; review section context format in system prompt |

## 7. Production Monitoring

**Tracing Tool:** Arize Phoenix (open-source, self-hostable) — no dependency on LangChain ecosystem; strong RAG trace visualization; works with raw Anthropic SDK calls via OpenTelemetry spans.

Alternative: Langfuse (if team prefers hosted SaaS). Either works; Arize Phoenix preferred for its RAG eval integration.

**Key Metrics to Track:**
1. `tool_call_latency_ms` — time from request to first `tool_start` SSE event (RAG + model TTFT combined)
2. `tool_selection_distribution` — count per tool name per day (alert if `propose_edit` drops to <20% — may indicate intent routing regression)
3. `citation_fabrication_rate` — % of `answer_with_citations` calls that trigger the fabrication guardrail
4. `compliance_false_confidence_rate` — % of `check_regulatory_compliance` `passes: true` calls on empty retrieval
5. `edge_function_error_rate` — 5xx responses from `chat-with-jamo`; alert if >1%

**Alert Thresholds:**
- `citation_fabrication_rate` > 5% → immediate investigation (system prompt or retrieval regression)
- `tool_call_latency_ms` p95 > 5000ms → RAG or model latency regression
- `edge_function_error_rate` > 1% sustained over 15min → page

**Smart Sampling Strategy:**
Weight production sampling toward:
- Sessions where the user sent 3+ consecutive messages without accepting any `propose_edit` suggestion (frustration signal)
- Any `check_regulatory_compliance` call that triggered the false-confidence guardrail
- Sessions where `answer_with_citations` returned zero citations
- Any edge function call that returned a non-200 status

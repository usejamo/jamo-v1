## E1: Write ordering vs propose_edit accept transaction

| Option | Description | Selected |
|--------|-------------|----------|
| After accept commit, fire-and-forget | Editor responsiveness priority; commit not held hostage by recordkeeping. | ✓ |
| Before accept commit (sync) | Couples editor to unrelated DB call. | |
| After accept commit, awaited | Trades latency for failure visibility. | |

**User's choice:** After accept commit, fire-and-forget.
**Notes:**
- Trigger sequence: ACCEPT_PENDING_EDIT → PM transaction → "all edits terminal?" check → if yes, fire-and-forget write. Once per message, not per accept.
- Standalone module-level async function (not hook-bound effect) — in-flight promise must survive component unmount.
- Structured failure logging with `{proposal_id, user_id, action_id, attempt, error}`. Silent drops degrade co-pilot invisibly; observability must catch patterns.
- 3 in-memory retries with exponential backoff, then log and drop. No persisted retry queue — best-effort recordkeeping; tab-close loss acceptable.

## E2: Race safety for rapid double-action / cross-tab

| Option | Description | Selected |
|--------|-------------|----------|
| Postgres RPC append_resolved_item with FOR UPDATE | Atomic append + cap + roll-off; single round trip. | ✓ |
| Client-side serial queue (in-memory) | Doesn't cross tab boundaries. | |
| Read-modify-write with optimistic check | Needs retry logic; reinvents locking. | |
| Trust serialization — dismisses are slow enough | Single-tab only; cross-tab collisions lose data silently. | |

**User's choice:** Postgres RPC with FOR UPDATE.
**Notes:**
- Multi-tab same-user same-proposal treated as first-class real-world failure case, not theoretical.
- Failure mode mitigated: "tab B overwrites tab A's append → resolved_item disappears → Haiku prompt missing context → proactive co-pilot degrades invisibly" — exactly the failure class this phase exists to fix.
- RPC upserts chat_sessions row if missing — first-action might predate row creation; handle atomically.
- Cap enforcement (slice to 25 most recent) inside same FOR UPDATE transaction — no separate trim, no window where array briefly holds 26.
- Sort by entry `timestamp` before slicing, not array insertion order. Insertion order works in practice but timestamp sort is robust against any future non-append write path.

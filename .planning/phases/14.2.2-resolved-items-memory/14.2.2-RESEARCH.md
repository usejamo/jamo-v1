## Summary

Phase 14.2.2 wires the already-provisioned `chat_sessions.resolved_items jsonb` column as stateful Haiku prompt context. The implementation has three discrete surfaces: (1) a new Postgres `append_resolved_item` RPC providing atomic append + cap + timestamp-sort under `FOR UPDATE`; (2) client write paths in `AIChatPanel` for dismiss and queue-originated `propose_edit` accept-terminal events, plus an `originating_action` snapshot threaded through `tool_data`; (3) edge-function changes in `analyze-proposal-gaps` to read `resolved_items`, compute per-section content-hash deltas, and inject a structured `RESOLVED_ITEMS` block into the Haiku system prompt with worked examples.

All architectural questions are locked by CONTEXT.md (decisions 1-8 + D-9 through D-34). Research scope is narrowly focused on the seven implementation gaps the planner needs concrete answers for. No alternatives are explored — research is prescriptive.

**Primary recommendation:** Implement in this order: (1) migration with RPC + grant, (2) types + constants, (3) client writer module + retry helper, (4) AIChatPanel wire-up (dismiss + accept-terminal detection + Realtime hydration), (5) edge function read + prompt revision. Validation surfaces are unit-testable for RPC/retry/identity-key match; live-verification for Haiku evolution and multi-tab race.

## User Constraints (from CONTEXT.md)

### Locked Decisions

**Architectural decisions 1-8 (CONTEXT.md lines 28-71):**

1. `resolved_items` is stateful prompt input, not dedup state. Edge function constructs Haiku prompt with structured `resolved_items` context that instructs refine/skip/evolve — never repeat verbatim.
2. `resolved_items` is per-user per-proposal (rides on existing `chat_sessions` composite key).
3. Don't ship dismissal-persistence as a separate quick fix — do it once via `resolved_items`.
4. Entry shape: `section_key`, `finding_type` (gap|conflict|compliance|missing), `title`, `description`, `user_action` (fixed|dismissed), `applied_changes` (≤200 chars), `section_content_hash_at_action`, `timestamp`.
5. Cap to 25 most recent per user per proposal (constant: `RESOLVED_ITEMS_CAP = 25`).
6. Don't delete from `pending_actions` on user action — write to `resolved_items`, let next analyze run replace `pending_actions` cleanly.
7. Section regression handled by including current hash alongside resolved_items in prompt with `content_changed_since_action` annotation; Haiku reasons about staleness.
8. Haiku is the dedup mechanism — no client/edge title-matching or fuzzy-matching.

**Discussion-locked decisions D-9 through D-34 (CONTEXT.md lines 151-194):**

- **D-9/10/11:** `originating_action` snapshot at CTA-click time, optional on `tool_data`, shape `{ id, section_key, finding_type, title, description }`.
- **D-12 to D-17:** Single fire-and-forget write per propose_edit message at all-edits-terminal; binary `user_action` (fixed/dismissed); optional `acceptance_summary {accepted, rejected, stale}`; `auto_rejected_stale` populates `stale`; `applied_changes` required string, concat accepted `change_summary` in document order, truncate at 200 chars to word/sentence boundary; prompt references `acceptance_summary` ratio when present.
- **D-18 to D-22:** Filter Set in local AIChatPanel React state; entry shape gains `originating_action_id: string | null`; Set membership checked by id (primary) AND `(section_key, finding_type, title)` (fallback); hydrate on mount and Realtime payloads; no Set pruning across reloads.
- **D-23 to D-30:** Fire-and-forget after accept commit; survives unmount via module-level async fn; 3 retries with exp backoff then log and drop; structured logging `{proposal_id, user_id, action_id, attempt, error}`; Postgres RPC `append_resolved_item` with `FOR UPDATE`; RPC upserts row if missing; cap inside same transaction; sort by entry `timestamp` before slice.
- **D-31 to D-34:** Reuse SHA-256 from `useGapAnalysisTrigger.ts:34`; binary hash equality only; user-scoped session lookup already implemented in edge function; null/empty array treated identically as no prior context.

### Pattern 1: Postgres RPC with FOR UPDATE + atomic JSONB append/cap/sort

**What:** Server-side atomic append with cap-to-25 + timestamp sort inside one transaction.
**When to use:** Multi-writer race against the same `chat_sessions` row.

```sql
-- Source: project convention from supabase/migrations/20260515000041_chat_sessions_per_user.sql
--         + Postgres docs https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE
--         + JSONB array idioms

CREATE OR REPLACE FUNCTION append_resolved_item(
  p_proposal_id uuid,
  p_user_id     uuid,
  p_org_id      uuid,
  p_entry       jsonb
) RETURNS jsonb
LANGUAGE plpgsql
SECURITY INVOKER  -- honor RLS as the calling user
SET search_path = public
AS $$
DECLARE
  v_existing jsonb;
  v_combined jsonb;
  v_capped   jsonb;
  v_cap      int := 25;
BEGIN
  -- Step 1: lock row (or note absence) under FOR UPDATE
  SELECT resolved_items INTO v_existing
  FROM chat_sessions
  WHERE proposal_id = p_proposal_id AND user_id = p_user_id
  FOR UPDATE;

  IF NOT FOUND THEN
    -- Step 1b: upsert if row missing (D-28).
    -- INSERT … ON CONFLICT DO NOTHING handles the case where a concurrent
    -- transaction created the row between SELECT and INSERT.
    INSERT INTO chat_sessions (proposal_id, user_id, org_id, resolved_items)
    VALUES (p_proposal_id, p_user_id, p_org_id, jsonb_build_array(p_entry))
    ON CONFLICT (proposal_id, user_id) DO NOTHING;

    -- Re-fetch under lock to handle the concurrent-insert race.
    SELECT resolved_items INTO v_existing
    FROM chat_sessions
    WHERE proposal_id = p_proposal_id AND user_id = p_user_id
    FOR UPDATE;

    IF v_existing IS NULL OR jsonb_array_length(v_existing) = 0 THEN
      -- Our INSERT won. Done.
      RETURN jsonb_build_array(p_entry);
    END IF;
    -- Fall through: the concurrent insert won; append our entry to its array.
  END IF;

  -- Step 2: combine existing array with new entry. NULL-safe via COALESCE.
  v_combined := COALESCE(v_existing, '[]'::jsonb) || jsonb_build_array(p_entry);

  -- Step 3: sort by entry timestamp DESC and slice to cap (D-29, D-30).
  -- jsonb_agg respects ORDER BY in the aggregate expression.
  WITH ordered AS (
    SELECT elem
    FROM jsonb_array_elements(v_combined) AS elem
    ORDER BY (elem->>'timestamp')::timestamptz DESC NULLS LAST
    LIMIT v_cap
  )
  SELECT COALESCE(jsonb_agg(elem), '[]'::jsonb) INTO v_capped FROM ordered;

  -- Step 4: write back. SECURITY INVOKER means RLS still applies (the user owns the row).
  UPDATE chat_sessions
  SET resolved_items = v_capped,
      last_updated   = now()
  WHERE proposal_id = p_proposal_id AND user_id = p_user_id;

  RETURN v_capped;
END;
$$;

REVOKE ALL ON FUNCTION append_resolved_item(uuid, uuid, uuid, jsonb) FROM public;
GRANT EXECUTE ON FUNCTION append_resolved_item(uuid, uuid, uuid, jsonb) TO authenticated;
```

**Confidence on SQL:** HIGH [VERIFIED: codebase migration patterns + Postgres official docs]. The `jsonb_agg(... ORDER BY)` pattern is canonical; `FOR UPDATE` provides row-level exclusive lock against concurrent updates from same RLS scope.

**Note on `SECURITY INVOKER` vs `SECURITY DEFINER`:**
- `SECURITY INVOKER` (chosen): RLS applies. The user can only update their own row because policies require `user_id = auth.uid()`. This is the safest default and matches existing migration philosophy (no `SECURITY DEFINER` functions in current migrations).
- `SECURITY DEFINER` would bypass RLS — unnecessary here because we WANT RLS enforced.
- `org_id` is required by `chat_sessions` insert WITH CHECK. The RPC accepts `p_org_id` from the caller; if it doesn't match the JWT's `org_id` claim, the upsert fails via RLS. This is correct — server returns the error, client retries are bounded.

**Note on `FOR UPDATE` vs `FOR NO KEY UPDATE`:**
- `FOR UPDATE` is appropriate: we are updating the row, not just a non-key column. PK is `(proposal_id, user_id)`, and the update changes `resolved_items` + `last_updated` (neither is a key). Either lock mode works; `FOR UPDATE` is the simpler default and matches the spec wording (D-27).

### Pattern 2: Module-level fire-and-forget writer with exp-backoff retry

```typescript
// Source: src/chat/resolved-items.ts (NEW)
// Pattern derived from: usePendingEditsSync.ts (fire-and-forget) +
//                       AIChatPanel.tsx:298 (persistToolDataState silent-fail)

const RETRY_DELAYS_MS = [500, 1500, 4000] // 3 attempts; cumulative ~6s
const MODULE_NAME = '[resolved-items]'

export async function appendResolvedItem(args: {
  proposalId: string
  userId: string
  orgId: string
  entry: ResolvedItem
  client: SupabaseClient
}): Promise<void> {
  const { proposalId, userId, orgId, entry, client } = args
  for (let attempt = 0; attempt < RETRY_DELAYS_MS.length; attempt++) {
    try {
      const { error } = await client.rpc('append_resolved_item', {
        p_proposal_id: proposalId,
        p_user_id: userId,
        p_org_id: orgId,
        p_entry: entry as unknown as Json,
      })
      if (!error) return
      console.warn(`${MODULE_NAME} RPC error`, {
        proposal_id: proposalId,
        user_id: userId,
        action_id: entry.originating_action_id,
        attempt: attempt + 1,
        error: error.message,
      })
    } catch (err) {
      console.warn(`${MODULE_NAME} threw`, {
        proposal_id: proposalId,
        user_id: userId,
        action_id: entry.originating_action_id,
        attempt: attempt + 1,
        error: err instanceof Error ? err.message : String(err),
      })
    }
    if (attempt < RETRY_DELAYS_MS.length - 1) {
      await new Promise(r => setTimeout(r, RETRY_DELAYS_MS[attempt]))
    }
  }
  // All retries exhausted — drop. Recordkeeping degrades silently, observable via console.
  console.warn(`${MODULE_NAME} dropped after retries`, {
    proposal_id: proposalId,
    user_id: userId,
    action_id: entry.originating_action_id,
  })
}
```

**Why module-level not hook-bound:** Promise lifetime decouples from React tree. Component unmount does not abort the in-flight RPC. The function is called as `void appendResolvedItem({...})` from the AIChatPanel handler.

### Pattern 3: "All edits terminal" derived selector

```typescript
// Source: derive at AIChatPanel level over SectionWorkspaceContext state.
// Add a useEffect that watches the message-keyed edit collection and fires
// once when the last pending edit transitions to a terminal resolution.

const TERMINAL: ChangeResolution[] = ['accepted', 'rejected', 'auto_rejected_stale']

// In AIChatPanel, after a propose_edit message lands:
const editsForMessage = useMemo(() => {
  // Walk all sections in SectionWorkspaceContext state.
  // Collect edits where message_id === thisMessageId.
  // Return list with resolutions.
}, [workspaceState, messageId])

const allTerminal = editsForMessage.length > 0 &&
  editsForMessage.every(e => TERMINAL.includes(e.resolution))

const resolutionSummary = useMemo(() => ({
  accepted: editsForMessage.filter(e => e.resolution === 'accepted').length,
  rejected: editsForMessage.filter(e => e.resolution === 'rejected').length,
  stale:    editsForMessage.filter(e => e.resolution === 'auto_rejected_stale').length,
}), [editsForMessage])

// Fire-once guard: track which message IDs have already been written.
const writtenRef = useRef<Set<string>>(new Set())

useEffect(() => {
  if (!allTerminal) return
  if (writtenRef.current.has(messageId)) return
  writtenRef.current.add(messageId)

  // Extract originating_action snapshot from the message's tool_data.
  // Bail (no write) if originating_action is null (free-text origin).
  const snapshot = message.toolData?.originating_action
  if (!snapshot) return

  // Build entry, fire-and-forget.
  void appendResolvedItem({...})
}, [allTerminal, messageId])
```

### Pattern 4: Edge-function prompt block construction (Haiku stateful context)

```typescript
// Source: supabase/functions/analyze-proposal-gaps/index.ts (modify)
// Insertion point: after Step 5 cooldown, before Step 6 LLM call

// Read resolved_items along with cooldown lookup (single round trip if possible).
const { data: session } = await supabase
  .from('chat_sessions')
  .select('last_updated, resolved_items')
  .eq('proposal_id', proposalId)
  .eq('user_id', userId)
  .single()

const resolvedItems: ResolvedItem[] =
  (session?.resolved_items as ResolvedItem[] | null) ?? []

// Compute per-section content hash for drift annotation.
// Same SHA-256 over TipTap-serialized HTML as client-side write path.
async function sha256Hex(input: string): Promise<string> {
  const buf = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(input))
  return Array.from(new Uint8Array(buf))
    .map(b => b.toString(16).padStart(2, '0')).join('')
}

const sectionHashes: Record<string, string> = {}
for (const s of sections) {
  sectionHashes[s.key] = await sha256Hex(s.content)
}

// Annotate each resolved entry with content_status flag.
const annotatedResolved = resolvedItems.map(item => ({
  ...item,
  content_status: sectionHashes[item.section_key] === item.section_content_hash_at_action
    ? 'content_unchanged_since_action'
    : 'content_changed_since_action',
}))

// Inject into system prompt only if non-empty (avoid distracting Haiku with empty block).
const resolvedBlock = annotatedResolved.length === 0 ? '' : `
The user has previously addressed the following items in this proposal:

RESOLVED_ITEMS:
${JSON.stringify(annotatedResolved, null, 2)}

When analyzing the proposal, use this context:
- If a section still has issues you would normally flag, but they overlap with a resolved item, describe what REMAINS rather than repeating the original finding.
- If a resolved item is marked content_changed_since_action and you observe the section has regressed, you may re-surface — but acknowledge what was previously done.
- If a user dismissed a finding and the section has not materially changed, do not re-surface that finding.
- When an acceptance_summary field is present: if accepted/(accepted+rejected) ratio is high, treat as substantially addressed; if low, the original concern may still apply.
- Findings should evolve, not repeat.

EVOLVED-FINDING EXAMPLES:

Example 1 — partial fix:
  Prior resolved_item: { section: "executive_summary", type: "gap",
    title: "Executive summary missing pricing and timeline",
    user_action: "fixed", applied_changes: "Added Q3 timeline" }
  Current state: pricing still absent, timeline complete.
  Good finding: "Executive summary still needs pricing detail (timeline added in prior pass)."
  BAD finding: "Executive summary missing pricing and timeline" — verbatim repeat.

Example 2 — dismissed with unchanged content:
  Prior resolved_item: { section: "scope", type: "compliance",
    title: "Scope lacks ISO citation", user_action: "dismissed",
    content_status: "content_unchanged_since_action" }
  Good behavior: do not re-flag.
  BAD behavior: re-emitting the same finding.
`

const ANALYSIS_SYSTEM_PROMPT_WITH_CONTEXT =
  ANALYSIS_SYSTEM_PROMPT + resolvedBlock
```

**Confidence:** HIGH on structure. The system-prompt position (vs user-turn injection) is the right slot because the instructions for *how* to use the context are static; only the JSON block varies per call.   // Stash in a ref keyed by an in-flight identifier so the propose_edit
```typescript
  // result handler can read it. The simplest carrier is a ref Map keyed
  // by section_key + cta_tool (matches the existing auto-dismiss heuristic).
  ctaSnapshotRef.current.set(`${action.section_key}:${action.cta_tool}`, snapshot)
  handleSendMessage(`[Action: ${action.cta_tool}] ${action.title}`, action.cta_payload, action.cta_tool)
}}

// At propose_edit tool result (line ~441-486):
if (event.tool === 'propose_edit' && event.result?.section_key) {
  const propPayload = event.result as ProposeEditPayload
  // Pull the matching snapshot (if any).
  const snapshotKey = `${propPayload.section_key}:propose_edit`
  const snapshot = ctaSnapshotRef.current.get(snapshotKey) ?? null
  ctaSnapshotRef.current.delete(snapshotKey)

  // Merge into toolData envelope before persist.
  const toolDataWithOrigin: ToolDataEnvelope = {
    ...toolData,
    originating_action: snapshot,  // null for free-text origin (D-10)
  }
  // ... pass toolDataWithOrigin into the message + INSERT.
}
```

**Why a ref Map and not state:** Snapshot capture happens synchronously at click; the result arrives after streaming. A ref is the lightest carrier. Key collision is acceptable per the existing auto-dismiss heuristic at line 466.

### Anti-Patterns to Avoid

- **Client-side fuzzy dedup against `resolved_items` titles.** Rejected explicitly in CONTEXT.md decisions 1 + 8. Haiku reads the structured block and reasons.
- **Persisted retry queue for failed writes.** Rejected (D-25); best-effort recordkeeping with structured logging is the contract.
- **A `partially_addressed` enum value.** Rejected (D-13); use `acceptance_summary` structural counters instead.
- **Title-only fingerprint match.** Rejected (D-20); the primary match is `originating_action_id`. Title is fallback inside identity-key tuple.
- **Writing on every accept rather than once-per-message at terminal.** Rejected (D-23); one write per propose_edit message at all-terminal.
- **Hook-bound retry helper.** Rejected (D-24); module-level async fn survives unmount.

## Common Pitfalls

### Pitfall 1: Edge function reads stale `resolved_items` if analyze fires before write completes

**What goes wrong:** User dismisses, autosave fires immediately, analyze run kicks off 3s later. If the fire-and-forget RPC is still in-flight or has retried into the future, Haiku sees the pre-write state and re-emits the dismissed finding.
**Why it happens:** Two async pipelines without sequencing.
**How to avoid:** The current analyze-trigger debounce (3s) + the fast single-column UPDATE in the RPC make this theoretical. Don't engineer around it. Spot-check after deploy.
**Warning signs:** Observed re-emission of the exact-same finding immediately after dismissal during normal-speed user interaction.

### Pitfall 2: Realtime UPDATE payload does not carry full row

**What goes wrong:** Filter Set hydration on Realtime payload reads `row.resolved_items` as undefined, defaulting to empty Set.
**Why it happens:** `REPLICA IDENTITY` default is `DEFAULT` (PK columns only). Must be `FULL` for JSONB columns to ride the payload.
**How to avoid:** Already addressed — `REPLICA IDENTITY FULL` is set in migration `20260515000040`. Verify the migration ran on the target environment.
**Warning signs:** `row.resolved_items === undefined` in console after RPC successfully writes.

### Pitfall 3: SECURITY DEFINER footgun

**What goes wrong:** Engineer marks RPC as `SECURITY DEFINER` to "make it work past RLS," accidentally letting one user write to another's row.
**Why it happens:** RPC permissions are confusing.
**How to avoid:** Use `SECURITY INVOKER` (the default). RLS on `chat_sessions` already requires `user_id = auth.uid()` in both USING and WITH CHECK. The RPC honors that — no special permissions needed. Caller passes the correct `p_user_id`; if it doesn't match the JWT, the UPDATE fails via RLS.
**Warning signs:** RPC code paths reference `auth.uid()` inside the function body (unnecessary if INVOKER) — sign that the author was working around perceived permission issues.

### Pitfall 4: Concurrent INSERT race when first-action predates row

**What goes wrong:** Two tabs both invoke the RPC for a user/proposal with no existing `chat_sessions` row. Both try to INSERT; one fails the unique constraint.
**Why it happens:** `FOR UPDATE` only locks existing rows. Pre-existence is not guaranteed.
**How to avoid:** Use `INSERT … ON CONFLICT DO NOTHING` then re-SELECT under FOR UPDATE (pattern shown above). The losing INSERT silently no-ops; the second SELECT picks up the winner's array and appends.
**Warning signs:** `duplicate key value violates unique constraint` errors in Postgres logs.

### Pitfall 5: `change_summary` concat in click order instead of document order

**What goes wrong:** Users accept edits non-sequentially; the `applied_changes` string reads "Updated indication. Added pricing. Updated indication." — confusing.
**Why it happens:** Natural impulse is to append in interaction order.
**How to avoid:** D-16 mandates document order. Use `pending_edits.sort((a, b) => a.change_index - b.change_index)` (or by paragraph position) before concat.
**Warning signs:** Resolved-item `applied_changes` shows different ordering than `propose_edit`'s `changes` array.

### Pitfall 6: `applied_changes` truncated mid-word

**What goes wrong:** "Added Labcorp coverage data and updat" — UX-degraded prompt context.
**Why it happens:** Naive `.slice(0, 200)`.
**How to avoid:** Find the last `\b[.!?]\s|\b\s` boundary before 200 chars. If none, fall back to last space; if none, hard-truncate at 200 with ellipsis.
**Warning signs:** Resolved-item entries with `applied_changes` ending mid-word.

### Pitfall 7: Free-text propose_edit triggers a no-op resolved_items write

**What goes wrong:** User typed "make this section punchier" → propose_edit → accept; with no originating_action snapshot, the writer fires anyway with `originating_action_id: null` and an entry that doesn't correspond to any prior queue finding.
**Why it happens:** Missing branch on snapshot existence.
**How to avoid:** D-10 — bail before write if `originating_action === null`. The fingerprint Set doesn't see these, but they also shouldn't enter the prompt context (no Haiku finding to "evolve" from).
**Warning signs:** Resolved-items entries with `originating_action_id === null` accumulating.

### Common Operation 2: applied_changes concat with boundary-safe truncation

```typescript
// Source: src/chat/resolved-items.ts

export function concatChangeSummaries(
  acceptedEditsInDocOrder: { change_summary: string }[],
  maxChars = 200
): string {
  const joined = acceptedEditsInDocOrder
    .map(e => e.change_summary.trim())
    .filter(Boolean)
    .join(' ')
  if (joined.length <= maxChars) return joined

  // Truncate to nearest sentence boundary first, then word boundary.
  const slice = joined.slice(0, maxChars)
  const sentenceEnd = Math.max(slice.lastIndexOf('. '), slice.lastIndexOf('! '), slice.lastIndexOf('? '))
  if (sentenceEnd > maxChars * 0.6) return slice.slice(0, sentenceEnd + 1)
  const wordEnd = slice.lastIndexOf(' ')
  if (wordEnd > 0) return slice.slice(0, wordEnd) + '…'
  return slice + '…'
}
```

### Common Operation 3: Building the ResolvedItem entry

```typescript
// Source: src/chat/resolved-items.ts

export async function buildResolvedItemEntry(args: {
  snapshot: OriginatingActionSnapshot
  resolutionSummary: { accepted: number; rejected: number; stale: number }
  acceptedEditsInDocOrder: { change_summary: string }[]
  sectionHtml: string  // TipTap-serialized HTML
}): Promise<ResolvedItem> {
  const { snapshot, resolutionSummary, acceptedEditsInDocOrder, sectionHtml } = args
  const userAction: 'fixed' | 'dismissed' =
    resolutionSummary.accepted >= 1 ? 'fixed' : 'dismissed'

  const appliedChanges = userAction === 'fixed'
    ? concatChangeSummaries(acceptedEditsInDocOrder, APPLIED_CHANGES_MAX_CHARS)
    : ''

  const hash = await sha256Hex(sectionHtml)

  return {
    originating_action_id: snapshot.id,
    section_key: snapshot.section_key,
    finding_type: snapshot.finding_type,
    title: snapshot.title,
    description: snapshot.description,
    user_action: userAction,
    applied_changes: appliedChanges,
    section_content_hash_at_action: hash,
    timestamp: new Date().toISOString(),
    // D-14: include acceptance_summary for propose_edit-originated entries only.
    acceptance_summary: resolutionSummary,
  }
}
```

## Open Questions

1. **Should the `useGapAnalysisTrigger` SHA-256 be extracted to a shared util now?**
   - What we know: It's the same primitive needed in the client write path AND the edge function.
   - What's unclear: Whether the client-side hash function will be invoked outside the writer module.
   - Recommendation: Extract to `src/utils/sectionHash.ts`. Two call sites (trigger + writer) cross the threshold. Edge function gets its own copy (Deno can't import client utils anyway).

2. **`section_content_hash_at_action` — hash entire section's TipTap HTML or just the body excerpt?**
   - What we know: `useGapAnalysisTrigger.ts:33` hashes `JSON.stringify(sortedSummaries)` (all sections, sorted).
   - What's unclear: For per-section drift in `resolved_items`, the hash input should be a single section's serialized content — NOT the trigger's all-sections hash.
   - Recommendation: Define a separate `sha256OfSection(html: string)` util taking one section's content. Don't reuse the trigger's signature directly. The trigger hashes for cooldown-debounce; the writer hashes for per-section regression.

3. **Where does `orgId` come from at write time?**
   - What we know: AIChatPanel uses `orgId` at line 345 for the proposal_chats insert.
   - What's unclear: Whether it's prop, context, or hook.
   - Recommendation: Planner traces the `orgId` source during task scoping. The writer's API signature includes `orgId` regardless.

4. **Should free-text-originated propose_edits write to resolved_items at all?**
   - What we know: D-10 says they skip the local Set; CONTEXT.md says they're optional on tool_data.
   - What's unclear: Whether the entry is still useful for Haiku context (a "user accepted some unrelated edit on this section" signal).
   - Recommendation: Per Pitfall 7 — bail. Free-text writes muddy the prompt context (no prior finding to "evolve"). Locked.

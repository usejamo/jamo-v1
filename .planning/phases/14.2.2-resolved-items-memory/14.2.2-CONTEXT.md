# Phase 14.2.x: Wire `resolved_items` as Stateful Co-pilot Memory

## Mission

Implement the missing lifecycle for action queue findings so they **evolve** based on what the user has already addressed, instead of being repeatedly re-surfaced. Write a context.md, then plan, then implement.

## Background

Phase 14.2 shipped the action queue with `chat_sessions.pending_actions` and a `chat_sessions.resolved_items` JSONB column. `pending_actions` is replaced on every `analyze-proposal-gaps` run. `resolved_items` was specified during planning but never wired up — it is currently never read or written by any code path.

Two symptoms surface from this gap:

1. **Immediate bug:** When a user dismisses or acts on an action queue item, the dismissal is set in local React state only. No DB write. On navigation back to the proposal, `AIChatPanel` mount fetches `pending_actions` from DB and the items return with `dismissed: false`.
2. **Conceptual problem:** Even if dismissal were persisted, the next `analyze-proposal-gaps` run replaces `pending_actions` wholesale. Haiku reads the still-incomplete section and emits the same finding (possibly with slightly different wording — titles are not stable). Persisting dismissal does not solve this.

## Reframing: this is not a dedup problem

The instinctive fix is to dedup new findings against dismissed ones. Don't do that. Dedup is the wrong framing because:

- Titles are model output and not stable. Exact-match suppression fails on cosmetic rewording; fuzzy-match suppression is brittle in different ways.
- Suppressing a title permanently blocks legitimate re-surfacing if the section regresses or the finding meaningfully evolves.
- Most importantly: Haiku flagging a section as still-incomplete after a surgical fix is **correct behavior** — the section IS still incomplete. The finding shouldn't disappear; it should evolve to reflect what's *still* missing now that one aspect has been addressed.

The right reframing: `resolved_items` is **stateful context for Haiku**, not a deny-list. It tells Haiku what the user has already worked on so the next analysis can refine, skip, or evolve findings rather than repeating them verbatim.

The "user dismissed and items came back" bug fixes itself as a side effect of doing this right — once `resolved_items` is wired in both directions (writes on user action, reads in the prompt), dismissed items stop reappearing because Haiku has the context to know they've been addressed.

## Architectural Decisions (Locked)

Do not relitigate these in the planning phase.

### 1. `resolved_items` is stateful prompt input, not dedup state

The edge function constructs the Haiku prompt with structured `resolved_items` context. The prompt explicitly instructs Haiku how to use it: refine, skip, or evolve findings — never repeat verbatim. This is the central change.

### 2. `resolved_items` is per-user per-proposal

`chat_sessions` is already per-user per-proposal (composite key `proposal_id + user_id`). `resolved_items` rides on that — User A's history does not affect User B's queue. Matches the rest of the per-user model from 14.2.

### 3. Don't ship dismissal-persistence as a separate quick fix

Skip the "persist dismissal locally now, wire `resolved_items` later" path. The persist-dismissal-only code gets deleted the moment `resolved_items` lands. Do it once, do it right.

### 4. `resolved_items` entry shape

Each entry captures:

- `section_key` — which section the finding was about
- `finding_type` — `'gap'` | `'conflict'` | `'compliance'` | `'missing'` (matches `pending_actions` type taxonomy)
- `title` — the finding's title as Haiku produced it
- `description` — the finding's description as Haiku produced it
- `user_action` — `'fixed'` | `'dismissed'`
- `applied_changes` — short natural-language summary of what the user accepted (for `'fixed'`). Hard-truncate to ~200 chars. Empty/null for `'dismissed'`.
- `section_content_hash_at_action` — content hash of the section at the time of action, for regression detection
- `timestamp` — ISO timestamp, for ordering and roll-off

### 5. Cap `resolved_items` to most recent 25 per user per proposal

Older entries roll off (FIFO). Prevents prompt bloat over long-iterated proposals. 25 is the working starting value; surface it as a constant for easy tuning.

### 6. Don't delete from `pending_actions` on user action

When a user dismisses or acts on an item, write to `resolved_items`. Leave `pending_actions` alone. The next `analyze-proposal-gaps` run replaces `pending_actions` cleanly anyway. Local UI hides items already represented in `resolved_items` for the active session.

### 7. Section regression handling

`section_content_hash_at_action` is captured per resolved_items entry. Include the current hash for each section in the Haiku prompt context alongside resolved_items. The prompt instructs Haiku that if a section's current hash differs significantly from the hash when the user took action, the resolved_items entry is "potentially stale" and Haiku should use judgment about whether to re-surface. **Don't engineer a threshold or decision logic on the client/edge side — let Haiku reason about it given the structured context.**

### 8. Haiku is the dedup mechanism

There is no client-side or edge-side title-matching or fuzzy-matching dedup. The model reads `resolved_items`, reasons about the section's current state, and produces findings that reflect both. Trust the model with the structured input.

## Deliverables

### Migration

- Confirm `chat_sessions.resolved_items` exists as `jsonb DEFAULT '[]'::jsonb`. If not, add it via migration.
- No schema changes needed beyond ensuring the column shape supports the entry structure above. (JSONB is flexible — no enforced schema needed.)

### Edge function changes (`analyze-proposal-gaps`)

- Read `resolved_items` from the `chat_sessions` row for the requesting user + proposal.
- Compute current content hash per section.
- Include both in the Haiku prompt as structured context (suggested: JSON block clearly labeled `RESOLVED_ITEMS` with each entry annotated `[content_unchanged_since]` or `[content_changed_since]` based on hash comparison).
- Update the system prompt to explicitly instruct Haiku: refine findings that partially overlap with resolved items, skip findings the user has explicitly dismissed unless content has materially changed, evolve findings that are still relevant in light of what's been addressed. Provide one or two short examples in the system prompt — model behavior on this kind of instruction is much better with concrete examples than with abstract directives alone.
- Continue to replace `pending_actions` wholesale on each run. No deduplication logic in the edge function.

### Client changes (`AIChatPanel.tsx` and related)

- **On dismiss:** write a new `resolved_items` entry with `user_action: 'dismissed'`, empty `applied_changes`, current section hash, current timestamp. DB write to `chat_sessions.resolved_items`. Fire-and-forget pattern matching the existing `persistToolDataState` precedent.
- **On accepting changes from a queue-originated `propose_edit`:** write a new `resolved_items` entry with `user_action: 'fixed'`, a short natural-language summary of what was accepted, current section hash, current timestamp.
- **On mount and on `pending_actions` Realtime updates:** filter the displayed queue against `resolved_items` for the current session — items whose finding fingerprint matches a recent `resolved_items` entry are hidden from view. This handles the "next analyze run hasn't fired yet but user just dismissed" gap visually.
- **Cap enforcement:** when writing a new entry, if length is at cap, roll off the oldest. Do this client-side; the edge function trusts whatever it reads.

### Prompt revision

Spell out in the system prompt template:

```
The user has previously addressed the following items in this proposal:

RESOLVED_ITEMS:
[
  {
    section: "executive_summary",
    type: "gap",
    title: "Executive Summary — incomplete product and indication details",
    user_action: "fixed",
    applied_changes: "Added Labcorp, Avera, and Stage IV details",
    content_status: "content_changed_since_action"
  },
  ...
]

When analyzing the proposal, use this context:
- If a section still has issues you would normally flag, but they overlap with a resolved item, describe what REMAINS rather than repeating the original finding.
- If a resolved item is marked content_changed_since_action and you observe the section has regressed, you may re-surface — but acknowledge what was previously done.
- If a user dismissed a finding and the section has not materially changed, do not re-surface that finding.
- Findings should evolve, not repeat.
```

Include 1-2 inline examples of evolved findings in the system prompt. Model adherence to this kind of instruction is much higher with examples.

### `applied_changes` summary generation

When the user accepts changes from a queue-originated `propose_edit` flow, generate a short summary of what was accepted. Two options for the planner to evaluate:

- **Option A:** client-side heuristic — concatenate a few words from each accepted paragraph's `change_summary` field (already produced by Haiku in the `propose_edit` tool output) into a single short string.
- **Option B:** one extra Haiku call to summarize accepted changes into a sentence.

Recommendation: **Option A**. It's free, deterministic, and the level of summary needed for downstream Haiku context doesn't justify a model call. If quality is insufficient in practice, Option B is a follow-up upgrade.

## Acceptance Criteria

1. User dismisses an action queue item. Navigates to the dashboard. Navigates back. The item does not reappear.
2. User uses "Fix it" on an action queue item flagging a section as thin. Accepts the proposed changes. Saves. Waits for next `analyze-proposal-gaps` run. The next finding for that section is **meaningfully different** — it reflects the work the user just did rather than repeating the original finding verbatim. (If the section is fully fleshed out, no finding for that section. If it's still incomplete in a different way, the new finding describes the new gap.)
3. User edits a previously-resolved section so that it regresses (substantial content removed). On the next analyze run, Haiku may re-surface a related finding, with phrasing that acknowledges or evolves from the prior context. (This is harder to test deterministically; the agent should manually verify with a clear regression case.)
4. `resolved_items` does not grow unbounded — at 25 entries per user per proposal, the oldest entry rolls off when a new one is written.
5. User A dismisses an item. User B opens the same proposal. User B's queue shows the item normally — A's history does not affect B's view.
6. The Haiku prompt token usage with `resolved_items` populated stays reasonable. Spot-check a worst-case scenario (25 entries, full descriptions) and confirm it doesn't blow up prompt size meaningfully.

## Open Questions for Discuss

- **Hash function for `section_content_hash_at_action`.** Suggest SHA-256 of the section's TipTap-serialized HTML, but the planner should confirm there's nothing in the existing codebase already doing content hashing that should be reused for consistency. If `useAutosave` or `chat_sessions` activity tracking already hashes content somewhere, follow that precedent.
- **"Material change" threshold for hash comparison.** The current design has hash-equality only: either content matches the hash-at-action or it doesn't. This is binary and works fine for "did anything change at all." Haiku handles the nuance from there. If the planner sees a need for a similarity score (Levenshtein, embedding distance, etc.), flag it but default to binary equality unless there's a real reason to upgrade.
- **Where the queue UI filters `resolved_items`-matched items.** Local React state in `AIChatPanel`, or via a derived selector on `chat_sessions` state? Either works; pick whichever is most consistent with existing patterns in the panel.
- **Handling user A's `resolved_items` when user B's analyze run fires.** Each user's analyze call reads their own `resolved_items`. Confirm the edge function signature supports user-scoped session lookup (it should, given chat_sessions is per-user, but verify).
- **Should the `resolved_items` write happen before or after the propose_edit accept transaction commits?** Recommend after — the user's commit is the source of truth, and `resolved_items` is a record of what they did. If the accept fails, no `resolved_items` write fires. Confirm in the plan that this ordering is implementable cleanly with the existing flow.
- **Migration of existing rows.** Existing `chat_sessions` rows have `resolved_items` as either null or default empty array. Both cases should be handled identically as "no prior context." Confirm the edge function and the client both no-op gracefully when the array is empty.

## Discussion-Locked Decisions (via /gsd-discuss-phase 14.2.2, 2026-05-28)

The locked architectural decisions above remain authoritative. The following resolve the "Open Questions for Discuss" and additional gaps surfaced during the codebase scan. Numbering picks up from the locked block (treat as D-9 onward in cross-phase references).

### A. Queue → propose_edit traceability (NEW from scan)

- **D-9:** Originating-action snapshot is captured **at CTA-click time** (not at accept time) and attached to the resulting `propose_edit` message via `tool_data.originating_action`. Captured in the CTA handler where the action object is already in scope — do not reach back through state at message-arrival time. Stable even if a re-analyze run replaces `pending_actions` mid-review.
- **D-10:** `originating_action` is **optional** on `tool_data`. Free-text-originated `propose_edits` (no queue origin) have no snapshot and are accepted without writing a `resolved_items` entry.
- **D-11:** Snapshot shape: `{ id, section_key, finding_type, title, description }` — the minimum surface needed to populate the `resolved_items` entry on terminal-state.

### B. Resolved-items lifecycle, write timing, and shape

- **D-12:** **Single write per propose_edit message, fire-and-forget**, triggered once **all edits in that message reach a terminal resolution state**. Terminal states include `accepted`, `rejected`, AND `auto_rejected_stale` — auto-reject counts as user-resolved for write-triggering purposes.
- **D-13:** `user_action` taxonomy stays binary: `'fixed'` if ≥1 edit accepted, `'dismissed'` if all-reject. No `'partially_addressed'` enum value.
- **D-14:** Entry shape gains an **optional** `acceptance_summary: { accepted: number, rejected: number, stale: number }` field, present only for `propose_edit`-originated entries. Provides quantitative partial-acceptance context for Haiku without complicating the taxonomy.
- **D-15:** `auto_rejected_stale` resolutions populate the `stale` field — semantically distinct from explicit `rejected` ("anchor moved out from under suggestion" vs "user said no").
- **D-16:** `applied_changes` is a **required string** (not nullable). Empty string `""` when `user_action='dismissed'`. When `user_action='fixed'`, concat the `change_summary` of accepted edits **in document order** (not click order — the record describes section state, not interaction history), then truncate at 200 chars to the **nearest word/sentence boundary** (not mid-token).
- **D-17:** The system prompt template must reference `acceptance_summary` when present with concrete reasoning instructions, e.g., "If accepted/(accepted+rejected) ratio is high, treat as substantially addressed; if low, the original concern may still apply." Include this alongside the existing inline examples.

### D. Resolved-items UI filter

- **D-18:** Filter lives in **local AIChatPanel React state** — a `Set` of dismissed/fixed entries for the current session. Matches the existing dismiss pattern at `AIChatPanel.tsx:628`.
- **D-19:** Entry shape gains `originating_action_id: string | null` — required, explicit. Populated from `action.id` on dismiss path and from `originating_action.id` snapshot on accept path. **Null reserved** for free-text-originated `propose_edit` entries (these still serve Haiku-context purposes but skip the local Set).
- **D-20:** Set membership is checkable **two ways**: by `originating_action_id` (primary) AND by an identity-key tuple `(section_key, finding_type, title)` (fallback for cross-session entries whose id is stale against the current `pending_actions`). Filter checks both.
- **D-21:** Hydration: on AIChatPanel mount AND on every `chat_sessions` Realtime payload (piggyback the existing subscription) — not on every render. Multi-tab updates flow in via the existing Realtime channel.
- **D-22:** **No Set pruning across reloads.** Stale ids naturally fail to match refreshed `pending_actions`, which is correct behavior. The local Set handles in-session immediate hiding; Haiku reasoning over `resolved_items` handles cross-run finding evolution. Clean division of labor.

### E. Write ordering and race safety

- **D-23:** Write fires **after** the accept commit, **fire-and-forget**. Trigger sequence: `ACCEPT_PENDING_EDIT` → ProseMirror transaction → "are all edits in this message terminal?" check → if yes, dispatch resolved_items write. **Once per message, not per accept.**
- **D-24:** The write **must survive component unmount.** Implement as a standalone module-level async function (not a hook-bound effect). In-flight promises must resolve even if the user navigates away mid-write.
- **D-25:** **3 in-memory retries with exponential backoff**, then log and drop. Do NOT persist a retry queue — `resolved_items` is best-effort recordkeeping and tab-close loss is acceptable.
- **D-26:** Structured failure logging with `{proposal_id, user_id, action_id, attempt, error}` even though there's no user-visible surface. Silent drops degrade the proactive co-pilot invisibly; observability must catch failure patterns.
- **D-27:** Race safety: a new **Postgres RPC `append_resolved_item(entry)`** with `SELECT … FOR UPDATE`. Single round trip, atomic against rapid same-user double-action AND cross-tab races (a common real-world failure mode this RPC is the canonical mitigation for).
- **D-28:** The RPC **upserts** the `chat_sessions` row if missing — first-action might predate row creation. The RPC contract handles "no row yet" atomically; callers do not need to ensure the row exists.
- **D-29:** Cap enforcement (slice to most recent 25) happens **inside the same `FOR UPDATE` transaction** as the append. No separate trim query; no window where the array briefly holds 26 entries.
- **D-30:** Slice ordering: sort by **entry `timestamp`** before slicing, not by JSONB array insertion order. Insertion order works in practice but explicit timestamp sort is robust against any future non-append write path.

### Auto-resolved from codebase scan (not relitigated)

- **D-31:** Content hashing reuses the SHA-256 pattern already in `src/hooks/useGapAnalysisTrigger.ts:34` (`crypto.subtle.digest('SHA-256', ...)`). Planner to extract a shared util if both call sites benefit, or duplicate the small fragment if extraction is heavier than the savings. Hash input is the section's TipTap-serialized HTML.
- **D-32:** `"material change"` threshold is **binary equality only** — content matches the hash-at-action or it doesn't. Haiku handles the nuance via the `content_changed_since` prompt flag. Do not introduce similarity scoring (Levenshtein, embeddings) unless real-world behavior demands it.
- **D-33:** User-scoped session lookup in `analyze-proposal-gaps` is already implemented (`index.ts:99-114, 169` — JWT-derived `userId`, `.eq('user_id', userId)` on `chat_sessions`). No edge function signature changes needed for the read path; the existing per-user fetch is the source of truth for `resolved_items`.
- **D-34:** Existing-row migration: `chat_sessions` rows with `resolved_items` as `null` or `[]` both treated identically as "no prior context." No backfill, no shape-coercion migration — the RPC and client both no-op gracefully on empty.

## Risks and Mitigations

- **Risk: Haiku ignores or misapplies the `resolved_items` instruction.** Mitigation: include 1-2 worked examples in the system prompt. Spot-check the first several real runs after deploy and refine prompt wording based on observed behavior. Plan for a follow-up prompt-tuning pass if needed.
- **Risk: Prompt size grows uncomfortably with 25 entries.** Mitigation: the 200-char `applied_changes` cap and the 25-entry list cap together bound prompt growth tightly. Worst case is roughly 25 × (~300 char per entry) = ~7.5KB of structured context, which Haiku handles easily.
- **Risk: Race between user action and next analyze run.** User dismisses, immediately makes an edit, autosave fires, analyze run kicks off 3s later — the `resolved_items` write must complete before the analyze call reads it. Mitigation: the dismiss write is fast (single column update on a known row); the autosave-debounce + 3s analyze-debounce window is long enough that the race is theoretical. Don't engineer around it unless observed.
- **Risk: Stale resolved_items entries accumulate in inactive proposals.** Mitigation: 25-entry cap rolls off naturally as users work. No active cleanup needed.
- **Risk: User wants to "unresolve" something they dismissed or fixed.** Out of scope for this phase. Document as a known limitation. Future work could add an "undo dismissal" affordance that removes a `resolved_items` entry.

### NEW 1. RPC migration header + GRANT conventions

**Analog:** `supabase/migrations/20260320000016_match_chunks_functions.sql` (verified via Grep — repeated `CREATE OR REPLACE FUNCTION` + `SECURITY DEFINER` + `LANGUAGE plpgsql` + explicit `REVOKE/GRANT` pattern across multiple project migrations).

**Pattern to copy for the new migration file:**

```sql
-- supabase/migrations/<timestamp>_append_resolved_item_rpc.sql
-- Phase 14.2.2 — atomic append + cap + timestamp-sort for chat_sessions.resolved_items.
-- Multi-tab race safety per D-27. SECURITY INVOKER so RLS on chat_sessions applies.
--
-- Existing call sites that read this column:
--   - supabase/functions/analyze-proposal-gaps/index.ts (added in this phase)
-- Existing call sites that write this column:
--   - src/chat/resolved-items.ts (added in this phase)

CREATE OR REPLACE FUNCTION append_resolved_item( ... ) ...
LANGUAGE plpgsql
SECURITY INVOKER          -- distinct from migration 16's helpers (those use DEFINER for cross-org reads)
SET search_path = public
AS $$ ... $$;

REVOKE ALL ON FUNCTION append_resolved_item(uuid, uuid, uuid, jsonb) FROM public;
GRANT EXECUTE ON FUNCTION append_resolved_item(uuid, uuid, uuid, jsonb) TO authenticated;
```

**Key contrast with existing RPCs:** All other project RPCs (`get_user_org_id`, `match_chunks_*`, `vault_*`) use `SECURITY DEFINER` because they need to cross RLS boundaries (read user_profiles, search across orgs, access vault secrets). The `append_resolved_item` RPC is the **first SECURITY INVOKER RPC in the codebase** — call this out in the migration comment so reviewers understand the deliberate divergence. RESEARCH §Pattern 1 covers WHY; this PATTERNS doc surfaces that it's a project-first.

**Full RPC body:** See RESEARCH.md §Pattern 1 (lines 220-293). Do not re-derive.

### NEW 3. Dismiss-handler call site — exact line target

**Current code at `AIChatPanel.tsx:628-632`** (verified via Grep):

```typescript
onDismiss={(actionId) => {
  setPendingActions(prev => prev.map(a => a.id === actionId ? { ...a, dismissed: true } : a))
  // ...
  onUndo={(actionId) =>
    setPendingActions(prev => prev.map(a => a.id === actionId ? { ...a, dismissed: false } : a))

```

**Pattern to apply (insert BEFORE the existing `setPendingActions`):**

```typescript
onDismiss={(actionId) => {
  // 1. Capture the action snapshot from current state BEFORE we mutate it.
  const action = pendingActions.find(a => a.id === actionId)
  if (action) {
    const snapshot: OriginatingActionSnapshot = {
      id: action.id,
      section_key: action.section_key,
      finding_type: action.type,
      title: action.title,
      description: action.description ?? '',
    }
    // 2. Compute current section hash (TipTap-serialized HTML for action.section_key).
    //    Use sectionHash utility (see NEW 6 below).
    void (async () => {
      const sectionHtml = await getSectionHtml(action.section_key) // see "Section HTML resolver" below
      const entry = await buildResolvedItemEntry({
        snapshot,
        resolutionSummary: { accepted: 0, rejected: 1, stale: 0 },  // dismiss = synthetic 1-reject
        acceptedEditsInDocOrder: [],
        sectionHtml,
      })
      void appendResolvedItem({ proposalId, userId, orgId, entry, client: supabase })
    })()
    // 3. Optimistically add the id to the local filter Set (immediate hide).
    setResolvedFilterSet(prev => {
      const next = new Set(prev)
      next.add(`id:${actionId}`)
      next.add(`ik:${identityKey(snapshot)}`)
      return next
    })
  }
  setPendingActions(prev => prev.map(a => a.id === actionId ? { ...a, dismissed: true } : a))
}}
```

**Why this is the right shape:** Mirrors the existing in-line mutation idiom at line 628. Captures snapshot from current state (no re-read), fires the writer outside React's state mutation flow. Does NOT touch `onUndo` (per D-15 — `auto_rejected_stale` is terminal, but explicit user-undo is in-scope only for the local visual state, not for resolved_items).

### NEW 6. Section HTML resolver — gap not covered by RESEARCH

RESEARCH §Open Q 2 flags that the hash input must be a single section's TipTap HTML. **NEW finding:** the planner must identify how to get "the section's current TipTap-serialized HTML" at write time. Two candidate sources:

| Source | How to reach it | Tradeoff |
|---|---|---|
| `SectionWorkspaceContext` state | `workspaceState.sections[section_key].body` (or equivalent serialized field) | In-memory, synchronous, no DB round trip. **Preferred.** |
| `proposal_sections` DB read | `supabase.from('proposal_sections').select('body').eq(...)` | Source-of-truth but adds latency + race against in-flight autosave. |

**Recommendation:** Use the in-memory context state. The hash is "as of user action moment" — using the in-memory state captures exactly that moment, even before autosave persists. `useGapAnalysisTrigger.ts:33` hashes from the same in-memory source (sorted summaries), so this matches established precedent.

**Open for planner:** confirm the exact field name on `WorkspaceSection` that holds the TipTap-serialized HTML. Grep `WorkspaceSection` in `src/types/workspace.ts` to verify.

### Query A — function exists AND is SECURITY INVOKER

```sql
SELECT proname, prosecdef, pronargs

WHERE proname = 'append_resolved_item'
  AND pronamespace = 'public'::regnamespace;
```

**Result:**
```json
[{"proname":"append_resolved_item","prosecdef":false,"pronargs":4}]
```

Interpretation: `proname = append_resolved_item`, `prosecdef = false` (SECURITY INVOKER confirmed — DEFINER would be true), `pronargs = 4` (uuid, uuid, uuid, jsonb).

### Query B (initial, pre-fix) — EXECUTE privilege grants

```sql
SELECT
  has_function_privilege('authenticated', 'public.append_resolved_item(uuid, uuid, uuid, jsonb)', 'EXECUTE') AS authenticated_can_execute,
  has_function_privilege('anon',          'public.append_resolved_item(uuid, uuid, uuid, jsonb)', 'EXECUTE') AS anon_can_execute,
  has_function_privilege('service_role',  'public.append_resolved_item(uuid, uuid, uuid, jsonb)', 'EXECUTE') AS service_role_can_execute;
```

**Initial result (FAIL):**
```json
[{"authenticated_can_execute":true,"anon_can_execute":true,"service_role_can_execute":true}]
```

Failure mode: `anon_can_execute = true`. Expected false per plan must_have ("EXECUTE granted to authenticated only").

### Query C — ACL inspection (root cause)

```sql
SELECT proacl::text
FROM pg_proc
WHERE proname = 'append_resolved_item';
```

**Result:**
```text
"{postgres=X/postgres,anon=X/postgres,authenticated=X/postgres,service_role=X/postgres}"
```

Root cause: Supabase `ALTER DEFAULT PRIVILEGES` auto-grants EXECUTE to anon, authenticated, and service_role on new functions in the public schema. The original migration's `REVOKE ALL ... FROM PUBLIC` only revokes the PUBLIC pseudo-role grant — it does NOT touch the explicit per-role grants Supabase adds.

### Corrective action

Applied migration `restrict_append_resolved_item_to_authenticated` (file: `supabase/migrations/20260601000001_restrict_append_resolved_item_to_authenticated.sql`):

```sql
revoke execute on function public.append_resolved_item(uuid, uuid, uuid, jsonb) from anon;
```

### Query B (post-fix) — EXECUTE privilege grants, re-run

**Result (PASS):**
```json
[{"authenticated_can_execute":true,"anon_can_execute":false,"service_role_can_execute":true}]
```

Final state: `authenticated = true`, `anon = false`, `service_role = true`. Matches plan must_have. (service_role retains EXECUTE via Postgres superuser bypass; expected and acceptable for service-side admin paths.)

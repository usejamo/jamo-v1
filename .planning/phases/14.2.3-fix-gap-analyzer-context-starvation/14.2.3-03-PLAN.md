<objective>
Close the ~1500ms resolve-time divergence window so the resolved-items staleness hash is provably consistent (Decision 6). During the ~1.5s autosave debounce after an edit, workspace = V2 (new) while DB = V1 (stale); the dominant co-pilot flow (see finding → edit section → dismiss finding) hits this window, and hashing the DB at resolve-time would falsely re-surface the just-dismissed finding. Flush-then-hash removes the window entirely.

Two pieces:
1. Plumbing: expose the existing `saveNow` (useAutosave.ts:46–62) through the editor imperative ref handle alongside `setContent`/`getContent`, and add it to the `SectionEditorHandle` type.
2. Sequence: in the dismiss resolve handler, `await saveNow(html)` → hash THAT EXACT string (via buildResolvedItemEntry's internal sha256OfSection) → write the resolved_items entry. On saveNow failure, fall back to hashing in-memory content and log — never block the resolve. Confirm the accept path's equality already holds (its content is flushed via saveNow at accept time).

Independent of the migration (Plan 02) and the edge changes (Plan 01) — runs in Wave 1.

Purpose: ship the 14.2.2 staleness guarantee into the most common edit-then-dismiss flow without the false re-surface bug. Also resolves the two pre-existing stale dismissals (Acceptance #8) — they self-correct via content_changed_since_action once content changes.
Output: `saveNow` on the handle + type; flush-then-hash in the dismiss path; accept-path equality confirmed.
</objective>

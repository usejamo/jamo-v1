<objective>
Persist the whole-proposal content hash so the mount trigger skips a redundant Haiku call across navigate-away-and-back (Decision 3). The hash gate already exists in memory (`computeHash`); this plan makes it durable.

Three coupled pieces, in order:
1. [BLOCKING] migration adding nullable `chat_sessions.pending_actions_content_hash text`, applied to the live project, with `database.types.ts` regenerated and committed together.
2. Edge: accept the hash in `RequestSchema` and write it in the SAME `chat_sessions` upsert as `pending_actions` (the desync guard).
3. Client: send `computeHash` output in the invoke body, and on mount read the persisted hash, compare, and skip the invoke when unchanged — checked BEFORE the call.

Purpose: The in-memory `hashRef` resets on unmount, so navigate-away-and-back re-fires Haiku. Persisting the hash stops the redundant call beyond the 30s server cooldown window (Acceptance #4).
Output: New migration + regenerated types + edge write-path + client mount read-gate.

NOTE this plan is `autonomous: false` — Task 1 applies a migration to the live Supabase project, which may require credentials/MCP interaction.
</objective>

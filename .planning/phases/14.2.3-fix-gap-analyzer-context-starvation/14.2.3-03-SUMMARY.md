# Phase 14.2.3 Plan 03: Resolve-Time Flush-Then-Hash Summary

Closed the ~1500ms autosave-debounce divergence window (Decision 6) so the resolved-items staleness hash is provably consistent: the dismiss resolve handler now flushes the in-memory section HTML to the DB via the editor handle's `saveNow` and hashes that exact string, eliminating the false re-surface bug in the dominant edit-then-dismiss co-pilot flow.

## What Was Built

**Task 1 — `saveNow` plumbing (commit `8bba968`)**
- `src/types/workspace.ts`: added `saveNow: (html: string) => Promise<void>` to `SectionEditorHandle`, matching `useAutosave.ts:46–62`.
- `src/components/editor/SectionEditorBlock.tsx`: added `saveNow: (html) => saveNow(html)` to the `useImperativeHandle` object (delegating to the already-destructured `useAutosave.saveNow` at :75) and added `saveNow` to the dependency array. No persistence logic duplicated — the `isEffectivelyEmpty` guard and canonical update stay in `useAutosave`.

**Task 2 — flush-then-hash in the dismiss handler (commit `5138e22`)**
- `src/components/AIChatPanel.tsx` (dismiss handler ~:710–765): before building the resolved-items entry, it now does `await editorRefs.current?.get(sectionKey)?.saveNow(html)` inside a `try`, then passes the **same `html`** string as `sectionHtml` to `buildResolvedItemEntry` (which internally calls `sha256OfSection`). No re-fetch between flush and hash.
- Failure fallback: a `catch` logs via `console.debug` and does **not** re-throw or early-return — `buildResolvedItemEntry` + `appendResolvedItem` still run with the in-memory `html` (benign: errs toward safe re-surface).
- The optimistic `setResolvedFilterSet` and `setPendingActions(... dismissed: true)` are unchanged.
- No direct `proposal_sections` write was introduced — `saveNow` (→ `useAutosave`) remains the only persistence path.
- Also fixed the `SectionEditorHandle` mock in `AIChatPanel.test.tsx` (added `saveNow: vi.fn()`) — required because Task 1 made `saveNow` mandatory on the interface (Rule 1; see Deviations).

## Accept-Path Equality Confirmation (plan output requirement)

The accept-path resolved-items write is owned by `useResolvedItemsWriteOnTerminal` → `computeTerminalWrites` (`src/hooks/useResolvedItemsWriteOnTerminal.ts:142–152`), which reads `sectionHtml` from `workspaceState.sections[key].content`. It has no `editorRefs` access and runs in a reactive effect, so an inline `saveNow` there is the wrong shape — and is **not needed**:

- `src/components/editor/SectionEditorBlock.tsx:354` — the accept handler runs `editor.commands.setContent(acceptedHtml, { emitUpdate: true })` then **`await saveNow(acceptedHtml)`** immediately.
- The `emitUpdate: true` on `setContent` fires `onUpdate` (:101–105), synchronously dispatching `UPDATE_CONTENT` so `workspaceState.sections[key].content === acceptedHtml`.
- By the time the terminal-write effect's `computeTerminalWrites` reads that workspace content, the DB has already converged to `acceptedHtml` (the :354 flush completed). So the client hash input == flushed DB content == what the edge later re-hashes. **Equality holds.**

**No gap found:** the terminal-write path is driven by accepted `propose_edit` resolutions, which always pass through the accept handler at :354. There is no terminal resolution that writes a resolved_items entry without first going through the accept-time `saveNow`.

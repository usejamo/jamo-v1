## Hash storage location (Decision 3)

| Option | Description | Selected |
|--------|-------------|----------|
| New chat_sessions column | Nullable `pending_actions_content_hash text`, written in the existing upsert | ✓ |
| Embed in pending_actions JSON | Wrap the bare array in `{hash, actions}` | |

**User's choice:** New nullable column `pending_actions_content_hash`.
**Notes:** The hash is metadata about the run, not a member of the action list; embedding it would force every `pending_actions` reader to unwrap an envelope (breaking read-shape change). Column gets atomicity without contaminating the read shape. Nullable; `null` = "no prior analysis → run" (same path as mismatch); existing rows null, no backfill. Verify no other write path touches `pending_actions` alone (desync would fire the gate wrong both ways). One trivial `ALTER` + types regen.

## Resolve-time hash input (Decision 6)

| Option | Description | Selected |
|--------|-------------|----------|
| Hash DB `proposal_sections.content` at resolve-time | Read persisted column, hash that | ✗ (broken — see trace) |
| Keep in-memory workspace content + equality test | Hash `workspaceState` content as today | (viable, not chosen) |
| Flush-then-hash (`saveNow` → hash that string) | Persist in-memory content, then hash it | ✓ |

**User's choice:** Flush-then-hash.
**Notes:** A code trace (requested by the user before locking) found a real ~1500ms window where workspace content (V2) leads DB content (V1) — `onUpdate` updates workspace synchronously while `triggerAutosave` debounces the DB write 1500ms; resolve handlers have no autosave gate. This **inverts** the original framing: workspace is the leading value the DB converges to, and the edge's staleness re-hash runs post-convergence, so hashing the DB at resolve-time captures stale V1 and falsely re-surfaces a just-dismissed finding (the exact 14.2.2 bug) in the most common edit-then-dismiss flow. Option 1 removed from consideration. Flush-then-hash chosen over in-memory because it removes the window rather than tolerating it (no timing dependency; resolve becomes a guaranteed save point). Plumbing: expose `saveNow` via the editor ref handle (no second write path from AIChatPanel). Sequence: `await saveNow(html)` → hash the literal string → write entry. On save failure: fall back to hashing in-memory + log, never block the resolve.

## Truncation marker (Decision 1)

| Option | Description | Selected |
|--------|-------------|----------|
| Inline sentinel at end | Append `[…section truncated for length…]` after the 5000-char cut | ✓ |
| Structured `truncated: true` field | Sibling field on the summary object | |
| Prepend marker before content | Lead with the truncation note | |

**User's choice:** Inline sentinel appended at end.
**Notes:** Self-describing at the cut with zero prompt coupling; model reads real content first. Structured field would need a separate prompt instruction that can silently drift; prepending interrupts content-first reading. Implementation: marker must read as clearly meta so it doesn't collide with the placeholder patterns being hunted (avoid spurious findings); optional (planner's call) prompt line telling the model not to infer completeness of the unseen tail.

# Phase 14.7 Plan 04: Proposal-Association Wiring (ingest proposal_id + client-to-RPC current_proposal_id thread) Summary

Threaded the proposal association end-to-end: `extract-document` now writes `proposal_id` on every inserted proposal chunk at ingest time (R2), and `current_proposal_id` flows client (`useProposalGeneration.fetchRagChunks`) → edge (`retrieve-context`) → both `match_chunks_*_proposals` RPCs (R7), with the regulatory retrieval path and the 14.3 internal-service-role trust boundary left byte-for-byte unchanged.

## What Was Built

**Task 1 — extract-document (R2):** `chunkAndEmbedProposal`'s params type gained `proposalId: string | null`; the `rows` map now sets `proposal_id: params.proposalId` on every chunk row alongside `org_id`/`doc_type: 'proposal'`. The call site passes `proposalId: doc.proposal_id ?? null` — `doc` was already fetched via `.select('*')`, so no new query was added. `test.ts` gained an `ignore: true` scaffold (function not exported; requires `OPENAI_API_KEY` + live Supabase) naming 14.7-07 as the live-validation owner.

**Task 2 — retrieve-context (R7):** `RetrieveRequest` gained `proposalId?: string` with a `// NEW (14.7) — proposal-history scoping` comment matching the existing convention. It is destructured alongside `orgId` at the body-parse line with **no JWT cross-check** — it is a filter param, not an identity claim, so the `isInternalServiceRoleCall`/`effectiveOrgId` trust-boundary block (14.3-03) is untouched. Both proposal RPC calls (`match_chunks_vector_proposals`, `match_chunks_fts_proposals`) gained `current_proposal_id: proposalId ?? null` — exactly 2 occurrences, grep-verified. The regulatory relaxation loop (`match_chunks_vector`/`match_chunks_fts`, lines ~226-276) was not touched. `test.ts` gained 2 `ignore: true` scaffolds (proposalId-threading integration + regulatory/trust-boundary-unchanged regression), both naming 14.7-07.

**Task 3 — fetchRagChunks client thread (R7):** `fetchRagChunks` gained a `proposalId: string` parameter, inserted as the 2nd positional arg (right after `orgId`) — chosen over converting to an options object as the lower-churn edit. It is included in the `retrieve-context` invoke body: `{ orgId, proposalId, query, therapeuticArea, studyPhase, geography }`. Both call sites (`generateAll` ~line 480, `generateSection` ~line 548) pass the enclosing `useProposalGeneration(proposalId)` closure's `proposalId` — confirmed in scope via `grep -n "function useProposalGeneration"` (line 278) before editing. The split return contract (`regulatoryChunks`/`proposalChunks`/`regulatoryCount`, 14.6-01) and the non-blocking zeroed-error-path behavior are unchanged.

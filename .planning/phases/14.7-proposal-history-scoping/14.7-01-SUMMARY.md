# Phase 14.7 Plan 01: Proposal-History Scoping Schema + Backfill Summary

Additive DDL for `chunks.proposal_id`/`proposals.reference_override`/`organizations.learn_from_*` plus a fail-closed, generically-resolving backfill migration with a disposable unresolved-chunk audit table — both authored as SQL only, live apply deferred to Plan 06.

## What Was Built

### Task 1: `supabase/migrations/20260710000001_chunks_proposal_scope_columns.sql`

Six additive statements, all idempotent (`IF NOT EXISTS`):

1. `chunks.proposal_id uuid NULL REFERENCES public.proposals(id) ON DELETE CASCADE` — the single source of truth for proposal scope (R1). Nullable so regulatory chunks are unaffected; cascades so chunks die with their proposal.
2. `chunks_proposal_id_idx` btree index on `chunks(proposal_id)` for Plan 02's RPC join.
3. `proposals.reference_override boolean NULL` — no default clause, so it defaults to NULL (R4 tri-state: NULL=follow master switch, true=force eligible, false=force excluded).
4. `organizations.learn_from_won boolean NOT NULL DEFAULT true`
5. `organizations.learn_from_submitted boolean NOT NULL DEFAULT false`
6. `organizations.learn_from_lost boolean NOT NULL DEFAULT false`

All three org columns use constant defaults (R5) per the live-verified D-01a guarantee: on PostgreSQL 17.6, `ADD COLUMN ... NOT NULL DEFAULT <constant>` is metadata-only — the 2 existing orgs land on the safe state (won=on, submitted/lost=off) with zero backfill UPDATE required. `chunks_tier_pairing` and `chunks_doc_type_check` were left untouched (out of scope for this plan); no RLS was written here (write-gating is Plan 03).

### Task 2: `supabase/migrations/20260710000002_backfill_proposal_chunks.sql`

- Creates disposable audit table `public._backfill_unresolved_proposal_chunks (chunk_id uuid, document_id text, reason text, recorded_at timestamptz DEFAULT now())`. Leading underscore signals disposable lifecycle (D-05b — intended to be dropped after inspection, not dropped by this migration).
- `UPDATE public.chunks` resolves `proposal_id` via `metadata->>'document_id' → proposal_documents.id → proposal_documents.proposal_id`, scoped to `doc_type='proposal' AND proposal_id IS NULL`, and only when the join lands on a non-null `proposal_documents.proposal_id` (T-14.7-01 mitigation: exact-match only, never guessed).
- `INSERT` records every row still unresolved after the UPDATE with a specific reason (missing document_id / orphaned document_id / null proposal_id on the joined row) — generic logic, not hardcoded to the known-live count of 0 unresolved (per explicit plan instruction: must hold for future prod data).
- `RAISE NOTICE` inside a `DO $$` block plus a final `SELECT count(*)` both surface the unresolvable count as the headline signal (R3 / BRIEF verification case 7).
- No `DELETE`/`TRUNCATE` on `chunks` anywhere — unresolved chunks are left NULL, which fails closed at retrieval (T-14.7-02 mitigation), never purged (D-05a: deletion is irreversible).
- Regulatory chunks are never touched — the `doc_type='proposal'` filter on both the UPDATE and INSERT excludes them entirely.

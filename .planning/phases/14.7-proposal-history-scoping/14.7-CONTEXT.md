<decisions>
## Implementation Decisions

### Org master-switch storage
- **D-01:** Store the three switches as dedicated `boolean NOT NULL` columns on `organizations`: `learn_from_won DEFAULT true`, `learn_from_submitted DEFAULT false`, `learn_from_lost DEFAULT false`. Chosen over `feature_flags` jsonb keys: typed, enforceable NOT NULL, clear migration, easy RPC join-read — appropriate strength for a confidentiality gate. Matches the existing `plan`/`is_active` column pattern on `organizations`.
- **D-01a (VERIFIED, not assumed — per user blocker):** On **PostgreSQL 17.6**, `ADD COLUMN … boolean NOT NULL DEFAULT <constant>` is a metadata-only operation; all existing rows read the constant default. The **2 existing orgs** therefore auto-land on won=true / submitted=false / lost=false (the intended safe state) with **no separate backfill UPDATE**. The migration MUST use constant defaults (not a volatile expression) to keep this guarantee. Do not hand-write a backfill UPDATE for these columns.

### RPC eligibility read (single source of truth)
- **D-02:** Both proposal RPCs (`match_chunks_vector_proposals`, `match_chunks_fts_proposals`) are `SECURITY DEFINER` and **self-join `organizations` + `proposals`** to read the three master switches + `reference_override` themselves. The full eligibility decision lives in ONE place, next to the existing `org_id = org_id_filter` isolation and the fail-closed `proposal_id IS NOT NULL` check. REJECTED: passing switches from `retrieve-context` as params — it splits a confidentiality rule across the edge function and SQL (lockstep drift risk). Express the rule exactly once, in the RPC.
- **D-03 (fail-closed on unknown status):** Any non-draft status with no matching *enabled* master switch → **NOT eligible**. A new status (e.g. `archived`, `on_hold`) must NOT silently become retrievable by being added; it stays excluded until someone deliberately adds AND enables a master switch for it. Accepted failure mode = visible under-include (we notice and wire it up); never a silent over-include (content leaks with no signal). Coherent with the null-`proposal_id` fail-closed posture: anything the rules don't explicitly permit is denied.
- **D-04 (ordered evaluation, not a flat boolean):** Write RPC eligibility as ordered branch evaluation with the **draft-floor gate evaluated FIRST**, then override, then master switch — not a single flat boolean expression. Ordered branches make the fail-closed default structural rather than an easy-to-miss edge case. (Reinforces the BRIEF's INVARIANT: `own_proposal OR (draft-floor AND category/toggle AND per-proposal logic)`; toggles/overrides are a filter layered ON TOP of the draft floor, never a replacement.)

### Backfill reporting + orphan handling
- **D-05:** The one-time backfill leaves unresolvable proposal chunks' `proposal_id` **NULL** (fail-closed, non-retrievable) AND records them in a **disposable audit table `_backfill_unresolved_proposal_chunks`** (columns: chunk `id` + `document_id`, joinable back to the affected proposals so we can answer "why isn't my uploaded doc used"). The migration ALSO emits the count (RAISE NOTICE or final SELECT) as the headline signal — audit table is the detail, count is the headline.
- **D-05a (do NOT purge):** Do not delete unresolvable/orphaned proposal chunks. Deletion is irreversible; "orphaned" is an assumption — some may be recoverable mis-migrations, not dead rows; and NULL already fails closed at retrieval, so purging gains nothing while destroying the only forensic trace. Keep the option to diagnose/recover first.
- **D-05b (audit table lifecycle):** `_backfill_unresolved_proposal_chunks` is an explicit ONE-TIME backfill artifact with a lifespan — once the gap is inspected and recoverable rows backfilled (or the rest confirmed dead), drop it. Not a permanent schema addition. (Leading underscore signals disposability.)
- **D-05c (VERIFIED scope):** 171 existing `doc_type='proposal'` chunks; **0 have a NULL `metadata.document_id`** — so the join resolves for 100% of them at the document_id level. Unresolvable rows can only come from a `document_id` that points to a deleted/orphaned `proposal_document` (or a document whose proposal was deleted). The audit table is expected to be empty or small.

### Settings UI — permission model (locked) + component (deferred)
- **D-06 (self-serve org settings, NOT platform /admin):** A CRO's policy on whether its lost/submitted bids inform future proposals is the customer's own confidentiality/strategy call, and the feature exists specifically to give users toggles they flip themselves. The 3 org toggles live in a **customer-accessible org Settings surface**; the per-proposal control lives **with the proposal**. REJECTED: the platform `/admin` surface (don't make customers file through platform-admin to change their own learning policy).
- **D-07 (org-admin gating — planner must confirm existing pattern):** These controls change a confidentiality boundary, so **mutating them is gated to the org-admin role** (match or tighten whatever role-gating existing org Settings controls use) — NOT editable by every authenticated org member. Planner MUST scout and REPORT the existing Settings role-gating pattern before wiring, then match/tighten it. Reads may be broader; writes are admin-only.

### Claude's Discretion
- **D-08 (exact UI component — deferred to planner scout):** Behavior is locked (3 org toggles: won default-on, submitted/lost default-off; per-proposal tri-state = follow-settings / always-include / never-include; NO draft include-path). The exact Settings section (an "AI grounding" / "Reference Library" section is a reasonable home) and the exact per-proposal placement (near the status control vs. the Phase-13 dashboard lifecycle menu) are chosen by the planner AFTER scouting the real Settings + proposal-detail components. Do not hard-code a component in the plan without scouting.

# Phase 14.7: Proposal-History Scoping — Research

**Researched:** 2026-07-10
**Domain:** Postgres RLS/RPC confidentiality scoping, Supabase Edge Functions, live deploy-first migration
**Confidence:** HIGH (live-verified against production project `fuuvdcvbliijffogjnwg` via Supabase Management API `database/query`)

## Summary

This phase's design is fully locked by `14.7-BRIEF.md` (authoritative) and `14.7-SPEC.md` (9 requirements). This research does not propose alternatives — it confirms the LIVE state the plan will be written against and surfaces four implementation landmines the BRIEF does not cover in mechanical detail: (1) both proposal RPCs are `LANGUAGE sql` (not `plpgsql`), so eligibility must be expressed as a single WHERE-clause boolean expression, not procedural branches — the BRIEF's pseudocode already fits this shape; (2) changing an RPC's parameter list requires `DROP FUNCTION IF EXISTS <old signature>` before `CREATE OR REPLACE`, confirmed by an in-repo precedent (14.5's regulatory RPC migration) that hit exactly this trap — skipping it leaves the OLD unscoped overload live and callable; (3) the `organizations` table currently has **no RLS write path for the org-admin role at all** — only `super_admin` can UPDATE via an `ALL`-command policy — so D-06/D-07's "self-serve org-admin settings" requires a NEW RLS policy (or RPC), not just re-using an existing one; (4) `proposals_update` RLS is currently open to ANY org member with no role check, so gating `reference_override` to admin-only (D-07) cannot be done via the existing row-level policy alone — it needs either a column-guard trigger or a dedicated RPC, mirroring the real admin-gating precedent that already exists on `templates` (`templates_insert_admin`/`templates_delete_admin`, INSERT/DELETE only, not UPDATE).

Backfill risk is verified LOW: all 171 existing `doc_type='proposal'` chunks resolve cleanly through the `metadata.document_id → proposal_documents → proposals` join (0 unresolvable), confirming D-05c. Live data also provides real fixtures for every BRIEF verification case: 2 won, 1 submitted, 1 lost, 56 draft proposals across 2 orgs.

**Primary recommendation:** Implement both RPC rewrites as single SQL statements using ordered `CASE`/boolean-AND expressions (per D-04), `DROP FUNCTION IF EXISTS` the old 3-arg/4-arg signatures explicitly, add the `chunks.proposal_id`/`proposals.reference_override`/`organizations.learn_from_*` columns via the Management API SQL endpoint (migration-diverged project — same mechanism used for this research), and resolve the org-admin write-gating gap with a purpose-built RLS policy or RPC before wiring the Settings UI — do not assume org-admin write access to `organizations` already exists.

## Live RPC Definitions (authoritative — on-disk migration is stale)

[VERIFIED: `pg_get_functiondef` via Management API, 2026-07-10]

```sql
CREATE OR REPLACE FUNCTION public.match_chunks_fts_proposals(query_text text, org_id_filter uuid, match_count integer)
 RETURNS TABLE(id uuid, content text, source text, agency text, therapeutic_area text, doc_type text, text_score double precision)
 LANGUAGE sql
 SECURITY DEFINER
 SET search_path TO 'public', 'extensions'
AS $function$
  SELECT
    id, content, source, agency, therapeutic_area, doc_type,
    ts_rank(search_vector, plainto_tsquery('english', query_text))::FLOAT AS text_score
  FROM chunks
  WHERE org_id = org_id_filter
    AND doc_type = 'proposal'
    AND search_vector @@ plainto_tsquery('english', query_text)
  ORDER BY text_score DESC
  LIMIT match_count;
$function$

CREATE OR REPLACE FUNCTION public.match_chunks_vector_proposals(query_embedding vector, org_id_filter uuid, similarity_threshold double precision, match_count integer)
 RETURNS TABLE(id uuid, content text, source text, agency text, therapeutic_area text, doc_type text, vector_score double precision)
 LANGUAGE sql
 SECURITY DEFINER
 SET search_path TO 'public', 'extensions'
AS $function$
  SELECT
    id, content, source, agency, therapeutic_area, doc_type,
    1 - (embedding <=> query_embedding) AS vector_score
  FROM chunks
  WHERE org_id = org_id_filter
    AND doc_type = 'proposal'
    AND 1 - (embedding <=> query_embedding) >= similarity_threshold
  ORDER BY vector_score DESC
  LIMIT match_count;
$function$
```

**Both are `LANGUAGE sql`, not `plpgsql`.** This constrains the RPC rewrite: no `IF/ELSE`, no `RAISE`, no local variables — the entire eligibility rule (own-proposal OR draft-floor-gated-history) must be one boolean expression in the `WHERE` clause, exactly as the BRIEF's pseudocode already models it. This is good news — the BRIEF's shape is directly implementable in `LANGUAGE sql` with no refactor to `plpgsql` needed.

**Current grants (all four grantees have EXECUTE):** `service_role`, `authenticated`, `anon`, `postgres`, `PUBLIC` [VERIFIED: `information_schema.role_routine_grants`]. This means `anon` (unauthenticated) callers can invoke `match_chunks_vector_proposals`/`match_chunks_fts_proposals` directly via the Supabase client `.rpc()` today, bypassing `retrieve-context` entirely, if they know (or enumerate) an `org_id` UUID. This is a pre-existing gap, not introduced by 14.7, and the BRIEF does not list grants as in-scope — flagged in Open Questions below rather than treated as a phase requirement, since the BRIEF governs on scope.

## Architecture Patterns

### System Data Flow (current → target)

```
CURRENT (bleed):
  Client (any proposalId) → retrieve-context (no proposalId passed)
     → match_chunks_*_proposals(org_id_filter)  [org-wide, all statuses]
     → generation prompt: [PROPOSAL HISTORY] = any org proposal's chunks

TARGET:
  Client (current proposalId) → fetchRagChunks sends proposalId
     → retrieve-context accepts proposalId, passes current_proposal_id
     → match_chunks_*_proposals(org_id_filter, current_proposal_id)
         WHERE org_id = org_id_filter                        -- defense-in-depth (unchanged)
           AND chunks.proposal_id IS NOT NULL                 -- fail-closed NULL gate (new)
           AND (
             chunks.proposal_id = current_proposal_id          -- tier A: own, any status
             OR (                                              -- tier B: other, eligible
               proposals.status <> 'draft'                     -- draft floor, FIRST-evaluated
               AND proposals.reference_override IS DISTINCT FROM false
               AND ( proposals.reference_override = true
                     OR ( proposals.reference_override IS NULL
                          AND org_master_switch(proposals.status) ) )
             )
           )
     → generation prompt: [PROPOSAL HISTORY] = own (any status) ∪ eligible-other (non-draft)
```

### Pattern: DROP-before-CREATE for signature changes

**What:** When an RPC's parameter list changes (adding `current_proposal_id uuid`), `CREATE OR REPLACE FUNCTION` registers a NEW overload rather than replacing the old one — Postgres function identity includes the parameter signature.
**When to use:** Any time this phase edits `match_chunks_vector_proposals` or `match_chunks_fts_proposals` (both change signature).
**Evidence this bites in this exact codebase:** 14.5's regulatory RPC migration (`supabase/migrations/20260708000004_regulatory_match_rpcs.sql`) hit this exact issue and explicitly documents it:
```sql
-- Source: supabase/migrations/20260708000004_regulatory_match_rpcs.sql, lines 9-15
-- DEVIATION (Rule 1 - correctness): the new signatures add phases_filter/geographies_filter params,
-- so CREATE OR REPLACE would register NEW overloads and leave the OLD pre-join signatures callable
-- (returning stale results ...). Drop the old signatures explicitly so only the joined versions exist.
DROP FUNCTION IF EXISTS match_chunks_vector(extensions.vector(1536), UUID, TEXT[], TEXT[], FLOAT, INT);
DROP FUNCTION IF EXISTS match_chunks_fts(TEXT, UUID, TEXT[], TEXT[], INT);
```
**Apply to 14.7 as:**
```sql
DROP FUNCTION IF EXISTS match_chunks_vector_proposals(extensions.vector(1536), uuid, double precision, integer);
DROP FUNCTION IF EXISTS match_chunks_fts_proposals(text, uuid, integer);
-- then CREATE OR REPLACE with the new 5-arg / 4-arg signatures (adding current_proposal_id uuid)
```
**Verification:** After migration, `select proname, pg_get_function_identity_arguments(oid) from pg_proc where proname like 'match_chunks_%_proposals'` must return exactly ONE row per function name.

### Pattern: fail-closed master-switch read via CASE (LANGUAGE sql compatible)

Since the functions are `LANGUAGE sql`, `org_master_switch(status)` from the BRIEF's pseudocode cannot be a separate `plpgsql` helper with branching — express it inline as a `CASE` with an explicit `ELSE false`, which structurally satisfies D-03 (unknown/new status defaults to NOT eligible):

```sql
-- Source: derived from BRIEF pseudocode + D-01/D-02/D-03/D-04, adapted for LANGUAGE sql
AND ( CASE proposals.status
        WHEN 'won'       THEN o.learn_from_won
        WHEN 'submitted' THEN o.learn_from_submitted
        WHEN 'lost'      THEN o.learn_from_lost
        ELSE false   -- D-03: unmapped/new status categories fail closed, never silently eligible
      END )
```

### Anti-Patterns to Avoid

- **Passing master switches as RPC params from `retrieve-context`:** REJECTED explicitly by D-02 — splits the confidentiality rule across two code paths (edge fn + SQL) with lockstep-drift risk. Read them via the RPC's own join to `organizations`.
- **Collapsing eligibility into a single flag lookup:** D-04 requires the draft-floor to be a structurally distinct, first-evaluated gate. In `LANGUAGE sql` this means writing `proposals.status <> 'draft' AND (...)` as the leading conjunct of tier B, not folding it into one combined boolean column.
- **Relying on `organizations_super_admin` ALL policy for org-admin writes:** See Pitfall 3 below — this policy does not grant org-admin users write access; only `super_admin` (platform role).
- **Trusting `proposals_update` RLS to gate `reference_override` to admins:** See Pitfall 4 below — this policy has no role check at all today.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Admin-only column write within a broader-permission table | A custom app-layer permission check only | A `BEFORE UPDATE` trigger checking `NEW.reference_override IS DISTINCT FROM OLD.reference_override` + role, OR a dedicated `SECURITY DEFINER` RPC (`set_reference_override(proposal_id, value)`) that validates role server-side | RLS is row-level, not column-level; a naive broader UPDATE policy re-check would let admins edit fields they shouldn't, and a client-only check is bypassable via direct `supabase.from().update()` calls |
| Org-admin self-serve settings write | A new blanket "admin can update anything on organizations" RLS policy | A narrowly-scoped policy (or RPC) that only permits the 3 `learn_from_*` columns to change, following the `templates_insert_admin`/`templates_delete_admin` role-check pattern already in this codebase | Matches existing precedent; avoids accidentally opening `plan`/`is_active`/`slug` to org-admin mutation |

**Key insight:** This codebase already has a real, live, role-checked RLS admin-gating pattern (`templates` table) — the planner should copy its shape (`role = ANY(ARRAY['admin','super_admin'])` subquery against `user_profiles`) rather than inventing a new one. It does NOT yet have any admin-write pattern on `organizations` itself, which is what D-06/D-07 need — that gap must be built, not assumed.

## Common Pitfalls

### Pitfall 1: RPC parameter signature change leaves the old overload live
**What goes wrong:** `CREATE OR REPLACE FUNCTION match_chunks_vector_proposals(..., current_proposal_id uuid, ...)` creates a second overload; any caller still invoking the 4-arg form (stale client cache, a forgotten call site, a cached PostgREST schema) gets the OLD org-wide-unscoped behavior — the exact bug this phase exists to fix, silently un-fixed for some callers.
**Why it happens:** Postgres identifies functions by name + parameter types; adding a parameter is a new identity, not a replacement.
**How to avoid:** `DROP FUNCTION IF EXISTS <exact old signature>` before `CREATE OR REPLACE` (see pattern above and the 14.5 precedent).
**Warning signs:** `pg_proc` shows two rows for the same `proname`; PostgREST schema cache exposes both arities as callable RPCs.

### Pitfall 2: Org-admin has no RLS write path to `organizations` today
**What goes wrong:** The plan assumes "org settings toggles are self-serve for org-admins" (D-06) will work once the UI is built, but the ONLY write policy on `organizations` is `orgs_super_admin` (`ALL`, `role = 'super_admin'`) [VERIFIED: `pg_policies`]. A regular `admin`-role user hits a silent RLS denial (0 rows updated, no error by default with Supabase client `.update()`) when saving toggles.
**Why it happens:** `organizations` was built platform-admin-only; this phase is the first feature asking org-admins to write to it.
**How to avoid:** Add a new RLS policy scoped to `org_id = private.get_user_org_id() AND private.get_user_role() = ANY(ARRAY['admin','super_admin'])`, ideally column-scoped via a trigger guard limiting it to the 3 `learn_from_*` columns (ordinary `admin` should very likely NOT get blanket UPDATE on `plan`/`slug`/`is_active` as a side effect) — or route the write through a dedicated RPC instead of direct table UPDATE.
**Warning signs:** Settings UI "save" appears to succeed (Supabase client doesn't error on 0-row RLS-filtered updates without `.select()`) but the toggle doesn't persist on reload.

### Pitfall 3: `proposals_update` RLS has no role check — any org member can flip `reference_override`
**What goes wrong:** D-07 requires the per-proposal reference control to be admin-gated, but the live `proposals_update` policy is `org_id = get_user_org_id()` with no role clause [VERIFIED: `pg_policies`]. Hiding the control in the UI for non-admins does not stop a non-admin from calling `supabase.from('proposals').update({ reference_override: true }).eq('id', ...)` directly.
**Why it happens:** `proposals_update` was designed for general proposal editing (status, title, etc.) where any org member legitimately has write access; `reference_override` is a new field riding on that same broad policy.
**How to avoid:** Either (a) a `BEFORE UPDATE` trigger on `proposals` that raises when `reference_override` changes and the caller's role isn't admin/super_admin, or (b) a dedicated `SECURITY DEFINER` RPC for this one field, called by the UI instead of a raw table update.
**Warning signs:** A non-admin user can toggle "use as reference" in browser devtools even if the UI hides the control.

### Pitfall 4: Unknown/new proposal status silently becoming eligible
**What goes wrong:** `proposals.status` has no CHECK constraint [VERIFIED: `pg_constraint`] — a future status value (e.g., `archived`) added only at the application layer would hit the `status <> 'draft'` branch and, without an explicit `ELSE false`, could either error (if the CASE has no matching WHEN and no ELSE, Postgres returns NULL — and `NULL` in a boolean AND context evaluates as not-true, so the row is actually excluded, matching fail-closed... but this is fragile and easy to get wrong if someone later "helpfully" adds a `COALESCE(..., true)`).
**Why it happens:** Status is unconstrained TEXT; the RPC is the only enforcement point.
**How to avoid:** Explicit `ELSE false` in the master-switch CASE (shown in Architecture Patterns above) — never rely on implicit NULL-is-falsy behavior; make the fail-closed default textually visible in the SQL.
**Warning signs:** A new status value added to the app without a corresponding CASE branch update.

### Pitfall 5: Direct RPC invocation bypasses `retrieve-context`'s org/proposal scoping entirely
**What goes wrong:** `anon` and `PUBLIC` currently have `EXECUTE` on both proposal RPCs [VERIFIED: `role_routine_grants`]. Even after 14.7 ships correct eligibility logic, a client-side caller who knows (or enumerates) `org_id_filter` and a `current_proposal_id` could call the RPC directly via `supabase.rpc()`, achieving the SAME eligibility result the edge function would produce (this is NOT a new hole introduced by 14.7 — the eligibility logic itself is correctly enforced server-side per D-02 regardless of caller). The real residual risk is `org_id_filter`/`current_proposal_id` values being attacker-suppliable at all from an `anon` context, i.e., cross-tenant enumeration, which is a PRE-EXISTING grant-hygiene gap, not a defect in this phase's design.
**Why it happens:** Supabase's default privilege grants EXECUTE to `anon`/`authenticated`/`PUBLIC` on new `public` schema functions unless explicitly revoked (documented inline in this repo's own `ingest_regulatory_document` migrations).
**How to avoid (optional, out of strict BRIEF scope — flag to user):** `REVOKE EXECUTE ... FROM PUBLIC, anon` + `GRANT EXECUTE ... TO authenticated, service_role` on both proposal RPCs, mirroring the pattern already used for `ingest_regulatory_document`/vault RPCs in this codebase. Not requested by the BRIEF; surfaced as an Open Question, not a requirement.
**Warning signs:** N/A for this phase's acceptance criteria — this is a defense-in-depth observation, not a BRIEF requirement.

-- Supabase's default privileges GRANT EXECUTE to anon/authenticated/service_role directly on

REVOKE ALL ON FUNCTION public.ingest_regulatory_document(TEXT,TEXT,TEXT,TEXT,TEXT[],TEXT[],DATE,TEXT,TEXT,TEXT,JSONB) FROM PUBLIC, anon, authenticated;

## Open Questions

1. **Should EXECUTE be revoked from `anon`/`PUBLIC` on both proposal RPCs as part of this phase?**
   - What we know: current grants include `anon` and `PUBLIC` [VERIFIED live]; this is inconsistent with the "privileged RPC" REVOKE/GRANT pattern already used elsewhere in this codebase for write-side functions.
   - What's unclear: the BRIEF doesn't mention grants at all, and doing so touches `authenticated` access patterns that might have callers this research didn't enumerate (e.g., a direct client `.rpc()` call site, if one exists — not found in the canonical_refs list, which only names `retrieve-context` as caller).
   - Recommendation: leave grants untouched for 14.7 (BRIEF governs, out of stated scope) but log this as a candidate follow-up item (similar in spirit to backlog 999.3) rather than silently fixing or silently ignoring it.

2. **Exact mechanism for admin-gating `reference_override` writes — trigger vs. RPC?**
   - What we know: `proposals_update` RLS has no role check today; `templates` shows a real RLS role-check precedent but only for INSERT/DELETE, not UPDATE (no existing UPDATE-with-role-check precedent in this codebase to copy verbatim).
   - What's unclear: whether a `BEFORE UPDATE` trigger (raises on unauthorized column change) or a dedicated `SECURITY DEFINER` RPC (`set_reference_override`) is the better fit given this codebase's conventions — both are viable; the codebase leans RPC-heavy for `SECURITY DEFINER` confidentiality logic (D-02 precedent) which slightly favors the RPC approach for consistency.
   - Recommendation: planner picks one during task breakdown; RPC approach is recommended for consistency with D-02's "express the rule once" philosophy, but either satisfies the requirement.

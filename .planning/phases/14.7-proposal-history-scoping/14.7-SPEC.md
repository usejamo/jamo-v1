# Phase 14.7: Proposal-History Scoping — Specification

**Created:** 2026-07-10
**Ambiguity score:** 0.06 (gate: ≤ 0.20)
**Requirements:** 9 locked
**Source:** Derived from the authoritative, user-authored `14.7-BRIEF.md` (locked design) + live codebase/schema scouting. See that BRIEF for the full rationale, the RPC pseudocode, and the draft-floor invariant — it governs on any conflict with this summary.

## Goal

Scope the `[PROPOSAL HISTORY]` RAG retrieval tier so a chunk from an uploaded proposal document is retrievable at generation time only when it belongs to (A) the current proposal (any status) or (B) another **non-draft** proposal that is **eligible** per org master switches + per-proposal override — eliminating the current within-org bleed where any org proposal's document chunks surface while generating any other proposal.

## Background

Proposal-document chunks are org-scoped, not proposal-scoped. `chunks` has no `proposal_id` column (confirmed live: columns are `id, org_id, doc_type, source, content, embedding, agency, guideline_type, therapeutic_area, search_vector, metadata, created_at, regulatory_document_id`). The proposal retrieval RPCs `match_chunks_vector_proposals` / `match_chunks_fts_proposals` filter `WHERE org_id = org_id_filter` only, and `retrieve-context` never receives a `proposalId` (the client `fetchRagChunks` sends none). So the `[PROPOSAL HISTORY]` tier returns top-K similar proposal chunks across the whole org → Sponsor A's confidential in-flight RFP can bleed into Sponsor B's draft. Blast radius is within-org only (cross-org RLS/org_id isolation intact). This predates Phase 14.6.

Verified: the current proposal's own document content already reaches generation proposal-scoped via the assumptions channel (`extract-assumptions` selects docs `.eq('proposal_id', …)` → writes `proposal_assumptions` (`proposal_id NOT NULL`) → `proposalContext.assumptions`). Raw full-text reaches generation ONLY through this org-wide RAG tier — so the tier's legitimate job is cross-proposal HISTORY, and the fix is to scope it, not remove it.

Confirmed live facts used by this spec: `proposals.status ∈ {draft, submitted, won, lost}` (text, no enum); `proposals.reference_override` does not yet exist; `organizations` has a `feature_flags` jsonb column and there is no dedicated settings table.

## Requirements

1. **`chunks.proposal_id` column (single source of truth)**: proposal chunks carry a real proposal association.
   - Current: `chunks` has no `proposal_id`; proposal scope is only implicit via `metadata.document_id`.
   - Target: add `proposal_id uuid NULL` FK `proposals(id) ON DELETE CASCADE` to `chunks`. Nullable (regulatory chunks have no proposal). This column — not the `metadata.document_id → proposal_documents.proposal_id` join — is the permanent scoping key.
   - Acceptance: column exists with the FK + `ON DELETE CASCADE`; after backfill, every `doc_type='proposal'` chunk with a resolvable source has non-null `proposal_id`; every `doc_type='regulatory'` chunk has `proposal_id IS NULL`.

2. **Ingest sets `proposal_id` (extract-document)**: new proposal chunks are written with the association, never relying on later backfill.
   - Current: `extract-document` inserts proposal chunks with `org_id`, `doc_type='proposal'`, `metadata.document_id` only.
   - Target: `extract-document` resolves the document's `proposal_id` (association exists at upload via `proposal_documents.proposal_id`) and writes it onto every inserted chunk.
   - Acceptance: a freshly uploaded+extracted document produces chunks whose `proposal_id` equals the owning proposal's id, with zero reliance on the backfill migration.

3. **Fail-closed backfill (one-time migration)**: existing proposal chunks get `proposal_id`, unresolvable ones are counted, not guessed.
   - Current: existing `doc_type='proposal'` chunks have no `proposal_id`.
   - Target: migration populates `chunks.proposal_id` via `metadata->>'document_id' → proposal_documents.id → proposal_documents.proposal_id`. Any chunk whose `proposal_id` cannot be resolved (missing/null `document_id`, orphaned document, deleted `proposal_document`) is LEFT NULL and COUNTED; the migration reports that count. Regulatory chunks untouched.
   - Acceptance: after the migration, resolvable proposal chunks are populated; unresolvable ones remain NULL; the migration output/return surfaces the exact count of unresolvable proposal chunks.

4. **`proposals.reference_override` column (per-proposal tri-state)**: an explicit include/exclude override per proposal.
   - Current: no such column.
   - Target: add `reference_override boolean NULL` to `proposals` (NULL = follow category/master switch; `true` = force eligible; `false` = force excluded).
   - Acceptance: column exists, default NULL; setting it true/false changes an OTHER non-draft proposal's eligibility per Requirement 6; it has NO effect on a draft (Requirement 6 floor wins).

5. **Org master switches (status-category eligibility)**: org-level defaults gate history by proposal status.
   - Current: no org-scoped "learn from" setting exists; `organizations` has a `feature_flags` jsonb column.
   - Target: three org-scoped boolean master switches — `learn_from_won` (default **true**), `learn_from_submitted` (default **false**), `learn_from_lost` (default **false**) — readable by the RPCs. (Exact storage — dedicated columns vs `feature_flags` keys — is a discuss-phase decision; the requirement is org-scoped booleans with these defaults.)
   - Acceptance: a new org exposes won=on, submitted=off, lost=off; toggling a switch flips eligibility of that whole status category for OTHER proposals (subject to per-proposal override and the draft floor).

6. **RPC eligibility logic (both proposal RPCs)**: server-side scoping with a first-evaluated draft floor and fail-closed NULL.
   - Current: `match_chunks_vector_proposals` and `match_chunks_fts_proposals` filter `org_id` only; no `proposal_id`/status/override logic.
   - Target: both RPCs accept a new `current_proposal_id uuid`, keep the `org_id = org_id_filter` clause (defense-in-depth), join `proposals ON chunks.proposal_id = proposals.id`, and return a chunk only if `chunks.proposal_id IS NOT NULL` AND (`chunks.proposal_id = current_proposal_id` OR (`proposals.status <> 'draft'` AND (`reference_override = true` OR (`reference_override IS NULL` AND org_master_switch(status) = true)) AND `reference_override IS DISTINCT FROM false`)). The draft-floor (`status <> 'draft'`) is a distinct, first-evaluated gate in tier B — not folded into a single flag lookup. NULL `proposal_id` is never returned (fail-closed, not org-wide).
   - Acceptance: SQL-level tests confirm each branch (see Acceptance Criteria 1–7); a `proposal_id IS NULL` proposal-tier chunk is never returned by either RPC.

7. **Thread `current_proposal_id` (client → edge → RPC)**: the proposal id reaches the RPCs at generation time.
   - Current: `fetchRagChunks` calls `retrieve-context` with no proposalId; `retrieve-context` has no `proposalId` field.
   - Target: `fetchRagChunks` sends the current `proposalId`; `retrieve-context` accepts it and passes `current_proposal_id` into both proposal RPCs. Regulatory retrieval path UNCHANGED.
   - Acceptance: a generation request carries the proposalId end-to-end; retrieval for a proposal returns its own chunks (any status) and excludes other-proposal drafts; the regulatory tier's behavior/results are byte-for-byte unchanged by this phase.

8. **Settings UI (org toggles + per-proposal control)**: users can manage history eligibility, with no draft include-path.
   - Current: no UI for either the master switches or a per-proposal reference control.
   - Target: org settings expose three toggles ("Learn from won proposals" default on; "Learn from submitted (in-flight) proposals" default off, labeled live/in-flight; "Learn from lost proposals" default off). Non-draft proposals expose a tri-state "use as reference" control (follow settings / always include / never include) writing `reference_override`. The include control is NOT surfaced as an include-path on drafts.
   - Acceptance: the three org toggles render with correct defaults and persist; the per-proposal control appears on non-draft proposals and writes `reference_override`; on a draft proposal there is no UI affordance that would make it includable as another proposal's reference.

9. **Regulatory retrieval untouched (guard)**: no collateral change to the 14.6 work.
   - Current: regulatory retrieval uses `match_chunks_vector`/`match_chunks_fts` with the geography/phase/TA/relaxation logic from 14.5/14.6.
   - Target: no change to regulatory RPCs, the regulatory tier, tiering, or the assumptions channel (`proposal_assumptions`).
   - Acceptance: the 14.6 live e2e (US-GCP grounded → E6R3 + ICH-GCP; Japan/zero → marker) still passes unchanged after this phase deploys.

## Boundaries

**In scope:**
- `chunks.proposal_id` column + FK (schema migration).
- `extract-document` sets `proposal_id` on ingest.
- One-time fail-closed backfill migration with unresolvable-count reporting.
- `proposals.reference_override` column (tri-state per-proposal override).
- Org master switches (`learn_from_won`/`_submitted`/`_lost`) with won=on, submitted=off, lost=off defaults.
- `match_chunks_vector_proposals` + `match_chunks_fts_proposals` eligibility rewrite (draft floor, fail-closed NULL, `current_proposal_id` param).
- Threading `current_proposal_id` through `fetchRagChunks` → `retrieve-context` → both proposal RPCs.
- Settings UI: 3 org toggles + per-proposal tri-state reference control.
- Live deploy of the two edge functions + two RPCs (deploy-first) before verification.

**Out of scope:**
- Any draft opt-in mechanism — deliberately cut; drafts are a hard floor.
- Any change to regulatory retrieval, tiering, or the 14.6 work — separate concern; must remain byte-for-byte unchanged.
- Any change to the assumptions channel (`proposal_assumptions`) — the proposal's own content already reaches generation there, scoped correctly.
- Ranking/threshold changes — that is backlog 999.3 (design-section retrieval strategy).

## Constraints

- **Draft-floor invariant:** eligibility is `own_proposal OR (draft-floor AND category/toggle AND per-proposal logic)`. The draft floor (`status <> 'draft'`) MUST be a distinct, first-evaluated gate in tier B — never collapsed into a single flag lookup, never overridable by `reference_override` or a master switch.
- **Fail-closed NULL:** a proposal-tier chunk with NULL `proposal_id` is never retrievable (must NOT default to org-wide match). A backfill miss fails closed.
- **Defense-in-depth:** the existing `org_id = org_id_filter` tenant clause is retained in both RPCs (in addition to the new proposal scoping).
- **Single source of truth:** `chunks.proposal_id` is the permanent scoping key; the `metadata.document_id → proposal_documents` join is used ONCE (backfill only).
- **Deploy-first:** this is a live confidentiality fix — the edge functions and RPCs must be deployed/applied to prod (`fuuvdcvbliijffogjnwg`) and verified live before phase completion. (Regulatory edge path unchanged; only proposal retrieval + extract-document change.)
- Confirmed status domain: `proposals.status ∈ {draft, submitted, won, lost}` — the master switches cover the three non-draft categories exactly.

## Acceptance Criteria

- [ ] The current proposal's own chunks are retrieved for that proposal at ANY status — including when the current proposal is itself a draft.
- [ ] Another proposal with `status='draft'` is NEVER retrieved by the current proposal — no parameter, toggle, or override makes it retrievable.
- [ ] A won proposal (other) IS retrieved by default (master default on).
- [ ] A submitted and a lost proposal (other) are NOT retrieved by default; each becomes retrievable after its master switch is turned on, and stops when turned off.
- [ ] `reference_override=false` on an otherwise-eligible won proposal excludes it; `reference_override=true` on an otherwise-ineligible lost proposal includes it — but `reference_override=true` on a DRAFT does NOT include it (floor wins).
- [ ] Fail-closed: a proposal chunk with NULL `proposal_id` is not returned by either proposal RPC.
- [ ] The backfill migration reports the count of unresolvable proposal chunks.
- [ ] `current_proposal_id` is threaded client → `retrieve-context` → both proposal RPCs (proposal retrieval no longer runs org-wide).
- [ ] Regulatory retrieval + the 14.6 e2e are unchanged after deploy.
- [ ] Settings UI: 3 org toggles (correct defaults, persist) + per-proposal tri-state control on non-draft proposals; no draft include-path.

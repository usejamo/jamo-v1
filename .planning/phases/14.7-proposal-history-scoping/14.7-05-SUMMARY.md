# Phase 14.7 Plan 05: Settings UI — Reference Library Toggles + Per-Proposal Control Summary

Authored the two customer-facing confidentiality controls (3 org master toggles + per-proposal tri-state override) as pure React components with mocked-supabase unit tests — no live RPC or DB call in this plan, per the deploy-first boundary revision.

## What Was Built

### Task 1: `ReferenceLibraryTab.tsx` (3 org master toggles)

**Scout finding (D-07 requirement):** the existing Settings admin-gating pattern is a **full-tab hide**, not a disabled-in-place control. `Settings.tsx`'s `visibleTabs` filter excludes `'Templates'` from the tab list entirely unless `profile?.role === 'admin' || profile?.role === 'super_admin'` (line 463-465 pre-change). `ReferenceLibraryTab` was wired into this exact same filter (now `isOrgAdmin` shared flag, excluding both `'Templates'` and `'Reference Library'`). This **matches** the existing pattern per D-07's instruction (not tightened, since Templates itself was already tab-hidden, the strictest existing precedent).

Because the tab is hidden from non-admins at the Settings level, the toggles inside `ReferenceLibraryTab` are additionally `disabled` (not just relying on the outer hide) whenever `profile?.role === 'user'` — defense-in-depth per the plan's explicit instruction, in case the component is ever reached by another route. The `Toggle` primitive is copied verbatim from `Settings.tsx` lines 138-154 with an added `disabled`/`aria-disabled` variant.

- Loads `learn_from_won, learn_from_submitted, learn_from_lost` from `organizations` on mount, scoped by `profile.org_id`, falling back to the fresh-org defaults (won=on/submitted=off/lost=off) if the row hasn't loaded yet or the columns aren't present (pre-Plan-06 safety).
- On any toggle click, calls `supabase.rpc('set_org_learning_switches', { p_learn_from_won, p_learn_from_submitted, p_learn_from_lost })` with the **full current trio** (RPC sets all three per its signature from Plan 03). Optimistic update + pending flag (StatusSelector-style); on RPC error the toggle reverts and an inline error banner renders, with a friendlier message when the error text contains `'not authorized'`.
- Verbatim labels used: "Learn from won proposals", "Learn from submitted (in-flight) proposals" (with an explicit sub-label clarifying live/in-flight meaning), "Learn from lost proposals".

### Task 2: `ProposalReferenceControl.tsx` (per-proposal tri-state)

Modeled on `StatusSelector.tsx`'s dropdown + async-onChange + pending-state shape. Options: Follow settings (`null`) / Always include (`true`) / Never include (`false`) — maps directly to `reference_override`.

**Render guard (load-bearing, BRIEF invariant):** the component returns `null` entirely when `status === 'draft'` — there is no disabled/greyed affordance on a draft, no include-path of any kind. Written as `if (status !== 'draft') { ...control... } return null` so the source literally satisfies the plan's grep contract (`status\s*!==\s*'draft'`).

- Owns its own `supabase.rpc('set_reference_override', { p_proposal_id, p_value })` call (not delegated to the parent), with the same optimistic-update/revert/error-message pattern as the Settings tab.
- `disabled` prop passed in from `ProposalDetail.tsx` based on `profile?.role`.
- Mounted in `ProposalDetail.tsx` directly adjacent to `<StatusSelector />` (line ~567), initialized from `proposal.reference_override ?? null`.

**Supporting type plumbing (Rule 3 — blocking dependency):** `proposal.reference_override` didn't exist anywhere in the client yet. Added it as an optional nullable field to `src/types/proposal.ts` and to `ProposalsContext.tsx`'s `mapRow` (`row.reference_override ?? null`). This is a no-op against the current live database (column doesn't exist until Plan 06 applies the migration; `row.reference_override` is simply `undefined` today, and `?? null` keeps `mapRow` safe either way) — it exists purely so `ProposalReferenceControl` has a real (if currently always-null) value to initialize from.

## Deviations from Plan

**1. [Rule 3 - blocking dependency] Extended `Proposal` type + `ProposalsContext.mapRow` with `reference_override`**
- **Found during:** Task 2, mounting `ProposalReferenceControl` in `ProposalDetail.tsx`.
- **Issue:** `proposal.reference_override` (needed to initialize the control per the plan's own action item 4) did not exist anywhere in the client type system or the context's row-mapping function.
- **Fix:** Added `reference_override?: boolean | null` to `src/types/proposal.ts`; added `reference_override: row.reference_override ?? null` to `ProposalsContext.tsx`'s `mapRow`. Both changes are additive/optional and are no-ops against the current live schema (the column doesn't exist until Plan 06 applies it — `row.reference_override` is `undefined` today, `?? null` handles that safely).
- **Files modified:** `src/types/proposal.ts`, `src/context/ProposalsContext.tsx`.
- **Commit:** 197dc9a (Task 2).

**2. `(supabase as any)` cast for the two new RPC names and the three new `organizations` columns** — not a deviation from plan behavior, but worth flagging: `database.types.ts` has not been regenerated yet (Plan 06 applies the migrations live and Plan 06/07 would be the natural point to run `npm run db:types`), so `set_org_learning_switches`, `set_reference_override`, and `organizations.learn_from_*` are not in the generated `Database` type. `npm run build` is `vite build` only (no `tsc` gate), so this does not block the build; the cast is a narrow, deliberate bridge documented inline in both component files, to be removed naturally once types are regenerated post-Plan-06.

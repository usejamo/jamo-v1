# PHASE 14.7 — PROPOSAL-HISTORY SCOPING

Deploy-first confidentiality phase. Touches schema + backfill + 2 edge functions + 2 RPCs + client + settings UI. Same plan→verify rigor as 14.6.

> This BRIEF is authoritative. It was authored by the user as a locked design. Do not weaken or reinterpret the draft-floor invariant, the fail-closed NULL semantics, or the out-of-scope cuts during planning.

---

## PROBLEM

Proposal-document chunks are org-scoped, not proposal-scoped. The proposal RPCs filter `WHERE org_id = org_id_filter` only; `chunks` has no `proposal_id` column. At generation, the `[PROPOSAL HISTORY]` tier returns top-K similar proposal chunks across the entire org — so documents uploaded for Proposal A can surface while generating Proposal B in the same org. For a CRO serving competing sponsors, Sponsor A's confidential in-flight RFP can bleed into Sponsor B's draft.

Blast radius: **within-org only.** Cross-org isolation (org_id filter + RLS) is intact. This predates 14.6 and is not a regression from it.

**Verified context:** the current proposal's own uploaded-doc content ALREADY reaches generation proposal-scoped, via the assumptions channel (`extract-assumptions` → `proposal_assumptions`, `proposal_id NOT NULL` → `proposalContext.assumptions`). Raw full-text reaches generation ONLY through the org-wide RAG proposal tier. Therefore the RAG proposal tier's legitimate job is cross-proposal HISTORY, and the fix is to **scope** it — not remove it.

---

## CORE DESIGN — retrieval eligibility

The `[PROPOSAL HISTORY]` tier returns the union of:

- **(A)** the current proposal's own chunks — ALWAYS, regardless of the current proposal's status (including when it is itself a draft), and
- **(B)** OTHER proposals' chunks — only where eligible per the rule below.

**ELIGIBILITY of an OTHER proposal P** (evaluated server-side in the RPC, in order):

1. If `P.status == 'draft'` → **NOT eligible. Hard floor.** No override, no toggle, nothing reaches past this. Drafts are structurally never retrievable by any other proposal.
2. Else if `P.reference_override == true` → eligible
3. Else if `P.reference_override == false` → NOT eligible
4. Else (override IS NULL) → eligible IFF the org master switch for `P.status` is ON.

Master switch defaults (org-level): **won = ON, submitted = OFF, lost = OFF.** Flipping a master switch ON makes that whole category eligible, minus any per-proposal exclusions (`override=false`). This is the "won opt-out" behavior.

DRAFT has: no category, no master switch, no per-proposal override path. It is categorically excluded from tier B. The `reference_override` field is meaningless on a draft (step 1 wins before it is read). **Do NOT add a draft opt-in.**

**INVARIANT (state this in code, do not collapse):** eligibility is

```
own_proposal OR (draft-floor AND category/toggle AND per-proposal logic)
```

The toggles and overrides are a filter LAYERED ON TOP of the draft floor — never a replacement for it. Do not implement eligibility as a single flag lookup; the draft-floor check must be a distinct, first-evaluated gate.

## SCHEMA

**chunks:**
- Add `proposal_id uuid NULL` FK `proposals(id) ON DELETE CASCADE`. Nullable because regulatory chunks have no proposal (they are org NULL / `regulatory_document_id` set). Proposal chunks must be non-null after backfill.
- This column is the single source of truth for proposal scope. **Do NOT** use the `metadata.document_id → proposal_documents.proposal_id` join as the permanent scoping path; the join is used ONCE, for backfill only.

**proposals:**
- Add `reference_override boolean NULL` (default NULL = follow category/master switch; true = force eligible; false = force excluded). Per-proposal toggle.

**org settings** (wherever org-scoped settings live — confirm the table):
- `learn_from_won boolean NOT NULL default true`
- `learn_from_submitted boolean NOT NULL default false`
- `learn_from_lost boolean NOT NULL default false`

## BACKFILL (one-time migration)

Populate `chunks.proposal_id` for existing `doc_type='proposal'` chunks via `chunks.metadata->>'document_id'` → `proposal_documents.id` → `proposal_documents.proposal_id`.

**Fail-closed reporting:** any proposal chunk whose `proposal_id` cannot be resolved (null/missing `document_id`, orphaned document, deleted `proposal_document`) must be LEFT NULL and COUNTED. The migration must report the count of unresolvable proposal chunks rather than silently leaving them. These rows will be non-retrievable by the new RPC logic (see below) — which is the safe outcome, but the count must be surfaced so we know the size of any gap.

Regulatory chunks (`doc_type='regulatory'`) are untouched — `proposal_id` stays NULL.

---

## RPC CHANGES (`match_chunks_vector_proposals` AND `match_chunks_fts_proposals`)

- Accept a new parameter: `current_proposal_id uuid`.
- Keep the existing `org_id = org_id_filter` tenant clause (defense-in-depth stays).
- Join `proposals ON chunks.proposal_id = proposals.id` to read `status` + `reference_override`, and read the org master switches.
- Return a chunk only if:

```
chunks.proposal_id IS NOT NULL          -- fail-closed: null proposal_id is
                                        --   NEVER retrievable on the proposal
                                        --   tier (not org-wide). A backfill
                                        --   miss fails CLOSED, not open.
AND (
  chunks.proposal_id = current_proposal_id          -- tier A: own docs, any status
  OR (                                              -- tier B: eligible history
    proposals.status <> 'draft'
    AND ( proposals.reference_override = true
          OR ( proposals.reference_override IS NULL
               AND org_master_switch(proposals.status) = true ) )
    AND proposals.reference_override IS DISTINCT FROM false
  )
)
```

- **NULL semantics, explicit:** a proposal-tier chunk with NULL `proposal_id` is not retrievable. Do NOT let NULL default to org-wide match.

## EDGE FUNCTIONS + CLIENT

- **extract-document:** set `chunks.proposal_id` at ingest time (resolve from the document's `proposal_id` — the association exists at upload). New proposal chunks must be written WITH `proposal_id`, never relying on later backfill.
- **retrieve-context:** accept and thread `current_proposal_id` into both proposal RPCs.
- **fetchRagChunks (client):** send the current `proposalId` to `retrieve-context`. (Today it sends none — this is the missing thread the whole fix depends on.)
- **Regulatory retrieval path:** UNCHANGED.

## SETTINGS UI

- Org settings: three master toggles — "Learn from won proposals" (default on), "Learn from submitted (in-flight) proposals" (default off), "Learn from lost proposals" (default off). Label submitted clearly as live/in-flight.
- Per-proposal: a "use as reference" control on non-draft proposals, tri-state (default = follow settings / always include / never include) → writes `reference_override`. Do NOT surface this control as an "include" path on drafts.

## VERIFICATION (must run live before phase completion)

1. Current proposal's own chunks are retrieved for that proposal at ANY status, including when the current proposal is itself a draft.
2. Another proposal in `status='draft'` is NEVER retrieved by the current proposal — confirm there is no parameter/toggle/override that makes it retrievable.
3. A won proposal (other) IS retrieved by default (master default on).
4. A submitted and a lost proposal (other) are NOT retrieved by default; each becomes retrievable after its master switch is turned on, and stops when off.
5. `reference_override=false` on an otherwise-eligible won proposal excludes it; `reference_override=true` on an otherwise-ineligible lost proposal includes it — but `reference_override=true` on a DRAFT does NOT include it (floor wins).
6. Fail-closed: a proposal chunk with NULL `proposal_id` is not returned by either proposal RPC.
7. Backfill reports the count of unresolvable proposal chunks.

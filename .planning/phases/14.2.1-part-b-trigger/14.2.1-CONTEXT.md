# Phase 14.2.1 — Wire the Part B gap-analysis trigger

**Status:** Pending — discovered during Phase 14.2 verification (`14.2-08-PLAN.md`), deferred so 14.2 could close.
**Owner:** TBD
**Surface affected:** AI chat panel's ActionQueue / proactive co-pilot.

---

## Why this phase exists

Phase 14.2 Part B built the full **proactive co-pilot** stack: the `analyze-proposal-gaps` edge function, the `chat_sessions` table with `pending_actions` / `active_task` / `resolved_items` columns, a Realtime subscription on `chat_sessions`, and the `ActionQueue`, `WalkthroughProgress`, and `ResumeTaskBanner` components. All of it works **except the first arrow**:

```
section content → analyze-proposal-gaps → chat_sessions.pending_actions → Realtime → ActionQueue UI
                  ^^^^^^^^^^^^^^^^^^^^
                  never fires
```

`AIChatPanel.tsx:228` defines `triggerAnalysis`, but `:241–242` is:

```ts
// Expose triggerAnalysis for potential future use (suppresses unused warning)
void triggerAnalysis
```

`triggerAnalysis` is **never called**. There is also no DB trigger, no `pg_cron` job, and no other client invocation. In normal usage the edge function never runs, `chat_sessions` rows are never created, and the ActionQueue is permanently empty.

A targeted audit of the 14.2 surface (`void IDENT`, "future use", `TODO`/`FIXME`/`HACK`) found this is the **only** stub of its kind — no other surprises.

## Design intent (from 14.2 planning docs)

From `14.2-DISCUSSION-LOG.md` and `14.2-CONTEXT.md`:

**D-30 (decided):** Gap analysis fires **fire-and-forget after each section save**, debounced ~3s after the last keystroke (sitting after the existing 1.5s autosave debounce, so analysis reads stable persisted content). Rules:
- Content-hash skip — if the section's content hasn't actually changed, don't analyze.
- Full-proposal context — send summaries of all sections, not just the changed one.
- Run-ID tagging — client generates a fresh UUID per call; server picks latest-wins on races.
- Server-side 30s-per-proposal cooldown.

**D-35 (was undecided, now decided here):** **Fire analysis on panel open when no prior analysis exists** for the proposal. Matches Step 12's verification wording ("items appear within ~10s of opening the panel") and gives first-time users immediate suggestions. The alternative (wait for first save) leaves freshly opened proposals showing no suggestions even when sections are clearly thin.

## Decisions for this phase

1. **D-35 resolution:** On-panel-open analysis if no prior `chat_sessions` row exists for `(proposal_id, user_id)`.
2. **Wiring (Option A — Realtime on `proposal_sections`):** `AIChatPanel` opens a Supabase Realtime channel on `proposal_sections` filtered to this `proposal_id`. On UPDATE, it debounces ~3s, then fetches the **full current section content** from the DB (not from the Realtime payload — analysis needs whole-proposal context, the payload only carries the changed row) and calls `triggerAnalysis(sectionSummaries)`.
3. **Server cooldown is reject-style and stays that way for 14.2.1.** The edge function returns `HTTP 429` (empty body) when the `chat_sessions.last_updated` row is younger than 30s (`analyze-proposal-gaps/index.ts:146-159`). The client should treat 429 as expected silence — no toast, no retry. **Cross-feature coupling concern (worth noting, do not fix in 14.2.1):** the cooldown key is `chat_sessions.last_updated`, which any feature that writes to that row (walkthrough updates, ask_user resolution, etc.) advances — so unrelated session activity can falsely throttle a legitimate gap-analysis request for up to 30s. If this becomes a UX problem, the right fix is a dedicated `last_analyzed_at` column, not changing the cooldown semantics.
4. **`run_id` flow stays as-is:** client generates `crypto.randomUUID()` per call; server already handles latest-wins.

## Implementation outline

Files expected to change:

- `src/components/AIChatPanel.tsx` — replace `void triggerAnalysis` with the actual wiring: (a) the on-open one-shot when no `chat_sessions` row exists, (b) a Realtime subscription on `proposal_sections` with a 3s debounce + content-hash skip + a fresh fetch of all section summaries before calling `triggerAnalysis`. Suppress 429s silently.
- Possibly a small hook (e.g. `useGapAnalysisTrigger`) so the wiring isn't a fourth `useEffect` clump inside `AIChatPanel`.

No edge function changes. No schema changes. No `triggerAnalysis` body changes — only its call sites.

## Test plan

Once wired, re-run Steps 12, 14-26 of `14.2-08-PLAN.md` end-to-end. Also add unit coverage for the debounce + content-hash skip logic since that's the most likely place for regressions (over-firing → 429 floods, under-firing → stale queue).

## Out of scope

- Refactoring the cooldown semantics or the `chat_sessions.last_updated` coupling (note above).
- Any change to the `analyze-proposal-gaps` edge function.
- Any change to the ActionQueue / WalkthroughProgress / ResumeTaskBanner components — those are intact and rendered the moment `pending_actions` is populated.

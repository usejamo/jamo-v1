# Phase 14.4: Deterministic Multi-Section Substitution - Context

**Gathered:** 2026-07-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Make the AI chat perform deterministic bulk placeholder substitution across sections: the chat model classifies which placeholders a supplied value can fill, and the client deterministically locates matching `data-placeholder-id` spans, substitutes the literal value, and fans out into per-section reviewable changesets plus one aggregate review control. No LLM generation of edit content; all three outcomes (full / partial / zero-match) honestly reported.

</domain>

<spec_lock>
## Requirements (locked via SPEC.md)

**7 requirements are locked.** See `14.4-SPEC.md` for full requirements, boundaries, and acceptance criteria.

Downstream agents MUST read `14.4-SPEC.md` before planning or implementing. Requirements are not duplicated here.

**In scope (from SPEC.md):**
- Chat natural-language entry → deterministic intent-parse (classify + route; extracts value, scope, per-placeholder decision)
- Deterministic locate of matching placeholder spans by `data-placeholder-id` / `data-placeholder-label` across all in-scope sections
- Deterministic literal substitution of single-value placeholders (no LLM produces edit content)
- Heterogeneity routing with bias-to-skip on uncertainty (single-value → substitute; multi-part/uncertain → skip + reason)
- Multi-section fan-out: N per-section reviewable changesets in a single turn, reusing the existing ghost-decoration / per-section accept-reject UX
- Aggregate review control: enumerated applied (per section) + skipped (section + label + reason), with accept-all / reject-all across sections
- Chat one-line summary on every run + an honest zero-match message when the target is not a placeholder
- Default scope = all sections containing a matching placeholder when the user does not name specific sections

**Out of scope (from SPEC.md):**
- A UI affordance / placeholder-panel "fill all" button (engine-first)
- Arbitrary literal-text find-and-replace on non-placeholder content
- Any LLM generation of edit content (LLM limited to classification/routing)
- Auto-filling multi-part placeholders (skipped-and-reported, never force-filled)
- Ask-then-fill routing (Phase 14.2.4)
- A brand-new dedicated multi-section review panel that replaces the per-section review UX
- Adding a single/multi flag to the placeholder data model

</spec_lock>

<decisions>
## Implementation Decisions

### Substitution locus + tool contract
- **D-01: Client-side deterministic locate + substitute.** The chat model emits only structured routing; the browser walks each section's live TipTap doc, locates spans by `data-placeholder-id`, substitutes the literal value, builds `PendingEdit`s, and materializes per section. No new edge endpoint. `chat-with-jamo` only registers the new tool and forwards its result through the existing `tool_result` SSE → materialize path. Strongest determinism because it acts on the actual doc of record.
- **D-02: New dedicated tool `substitute_placeholders`** (do NOT extend `propose_edit`). Shape: `substitute_placeholders(value, targets: [{ section_key, placeholder_id, decision: 'substitute' | 'skip', skip_reason? }])`. Leaves the shipped single-section `propose_edit` path 100% untouched (SPEC constraint).
- **D-03: The tool carries classification, NOT edits.** No `after_html`, no generated content in the tool payload — `decision` + `skip_reason` are the model's routing output only. This is the guardrail that keeps the feature from regressing into generative find-replace. The turn produces routing; the client produces edits.
- **D-04: Client doc-walk is authoritative over the tool's targets.** Every `placeholder_id` in `targets` is a *proposal* the client validates against the live doc. An id the client cannot resolve becomes a skip+report, regardless of what the tool claimed. The tool contract is the model's claim; the client's doc-walk is the truth.
- **D-05: Unified skip channel.** Model-authored skips (multi-part placeholder a single value can't satisfy) and client-generated skips (unresolvable id, no-match) flow into the SAME reporting path — aggregate panel + chat line. One skip-reporting surface, multiple skip sources.
- **D-06: Fan-out integration seam (call out in plan).** One `substitute_placeholders` result fans out into N per-section materializations feeding the multi-section review surface. This is the FIRST real multi-section batch that 14.3's per-section-scoped ghost-isolation guard sees in production — the most likely place for a bug. Design the fan-out with that guard in mind and test it explicitly.

### Granularity bridge + mark fate
- **D-07: Paragraph-level replace (reuse the whole pipeline).** The client resolves each validated placeholder span to its containing paragraph and emits a standard `PendingEdit` (`operation: 'replace'`, `paragraph_id` = containing paragraph, `after_html` = that paragraph's HTML with the span's content replaced by the value). Reuses anchor-by-paragraph-id, `ghostContentLeakDetected`, existing decorations, and materialize unchanged. `change_summary` reads "filled `<label>` placeholder" so the ghost + `EditSummaryCard` are self-describing. NO new mark-granularity edit operation.
- **D-08: Bulk edits are ORDINARY PendingEdits.** Because they're normal paragraph replaces, the multi-section fan-out and the 14.3 per-section guard handle them as ordinary edits. Confirm the fan-out produces N normal PendingEdits, each anchored by its own paragraph id.
- **D-09: Group targets by containing paragraph → one PendingEdit per paragraph.** When multiple target placeholders share a paragraph (e.g. the value appears twice, or two filled placeholders in one paragraph), compose ALL substitutions for that paragraph into a single `after_html` and emit ONE `PendingEdit` per paragraph. The naive "one PendingEdit per placeholder" would create two competing `replace` edits on the same `paragraph_id` and collide.
- **D-10: Strip the placeholder mark on accept → resolved plain text.** The value replaces the placeholder as normal text and the `data-placeholder-id` mark is removed, so it no longer shows as an unresolved issue in the analyzer walk. Baked into `after_html` (plain value, no mark) since materialize applies as an `aiApplied` transaction that bypasses `resolutionPlugin`. Matches how manual edits resolve placeholders.

### Classifier execution
- **D-11: Classification folded into the main chat turn.** The existing chat model — which already receives all sections' HTML with placeholder spans — classifies each target AS it emits `substitute_placeholders` (`decision` + `skip_reason` per target). Zero extra round-trips, one structured emission, no separate Haiku call. "Cheap intent-parse" is cheap because it's classification, not generation.
- **D-12: Bias-to-skip-on-uncertainty lives in the tool description + system prompt.** When the model is unsure whether a single value satisfies a label, it emits `skip`, not `substitute`. A false-skip is safe (user told to fill manually); a false-substitute inserts incoherent content. Per-section ghost review is the backstop either way.

### Aggregate review UI
- **D-13: `BulkSubstitutionSummaryCard`, rendered once from the `substitute_placeholders` tool message.** Composes `EditSummaryCard`'s existing visual + accept/reject patterns (not a new design language). Contents: affected sections + applied count; enumerated skips (section + placeholder label + skip reason); accept-all / reject-all across all sections. One new composed component built from shipped parts.
- **D-14: Both review levels stay active.** Per-section `EditSummaryCard`s and ghost decorations remain beneath the aggregate card. Accept/reject works individually (per section) AND as a batch (aggregate). Accept-all fires as one coherent batch = a single undo step, consistent with the established batch-accept behavior.
- **D-15: Card renders from the RECONCILED CLIENT OUTCOME, not the raw tool proposal.** Applied/skipped counts reflect post-validation reality: a target the model proposed to substitute but the client couldn't resolve moves from "applied" to "skipped (unresolvable)". Counts must be honest — derived after id-validation + materialize, not from the tool's proposed target list.
- **D-16: Skip enumeration is the panel half of "aggregate panel + chat line" (SPEC R7).** All skip sources land in the card with their reason; the chat one-liner remains the spoken summary alongside it.

### Claude's Discretion
- Exact `after_html` construction mechanics (PM node walk vs HTML serialize/replace) — planner/researcher decides, must be deterministic.
- Naming of the tool fields and the summary component, wiring specifics in `AIChatPanel.tsx` render branches.
- How the chat one-liner string is composed (counts + section names) — must cover full / partial / zero-match per SPEC R7.
- System-prompt phrasing that teaches the model when to call `substitute_placeholders` vs `propose_edit`, and how to scope from NL ("this section" vs "every section" vs a named section; default = all sections with a matching placeholder per SPEC).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- **`PendingEdit` + `materializePendingEdits` + ghost decorations**: the entire per-section review pipeline is reused unchanged — bulk substitution just emits ordinary paragraph `replace` edits (D-07, D-08).
- **`sections: Record<section_key, { pending_edits }>`**: state shape already holds N sections' changesets concurrently — no reducer reshape needed; the new work is a cross-section batch action + aggregate render.
- **`EditSummaryCard`**: visual + accept/reject patterns composed into the new `BulkSubstitutionSummaryCard` (D-13).
- **`tool_result` SSE → materialize plumbing**: `substitute_placeholders` forwards through the same path `propose_edit` uses today.
- **Placeholder enumeration**: `collectPlaceholderRanges` (PlaceholderMark) + the analyzer walk (`SectionEditorBlock.tsx:310-316`) already locate placeholder spans by id/label.

### Established Patterns
- **Single-turn edge dispatch**: no tool-result→continue loop; one model turn emits all tool calls (index.ts). Fits D-11 (one turn in, deterministic execution out).
- **`aiApplied` transactions bypass `resolutionPlugin`**: so mark-strip (D-10) must be baked into `after_html`, not left to the plugin.
- **Per-section editor instances**: one `PendingEditsPlugin` + one `SectionEditorHandle` per `SectionEditorBlock`, keyed in `editorRefs`.

### Integration Points
- **`chat-with-jamo` tool registry** (index.ts:72-78) — add `substitute_placeholders`.
- **`AIChatPanel` materialize call site** (~line 582) — extend to fan out one bulk result into N per-section `materializePendingEdits` calls.
- **`AIChatPanel` render branches** (~line 910) — add a `tool-substitute-placeholders` branch rendering `BulkSubstitutionSummaryCard`.
- **14.3 per-section ghost-isolation guard** — the fan-out (D-06) is its first real multi-section exercise.

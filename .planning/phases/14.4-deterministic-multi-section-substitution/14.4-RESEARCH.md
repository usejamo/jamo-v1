## Summary

The entire per-section pipeline this phase needs already exists and is battle-tested by 14.2/14.3: `PendingEdit` (paragraph-granular `replace` with `after_html`), `materializePendingEdits` (validation + `anchor_hash` + `ghostContentLeakDetected` guard + `SET_PENDING_EDITS`), ghost decorations, and `EditSummaryCard`. **This phase is 90% orchestration and 10% one pure function.** The one genuinely new deterministic primitive is a paragraph-HTML rewriter that, given a section's HTML + a `data-placeholder-id`, returns the containing paragraph's HTML with the target span's content replaced by the literal value and the span unwrapped (mark stripped) — pure, jsdom/happy-dom-testable, byte-identical on repeat.

The three highest-risk seams are all in `AIChatPanel.tsx`: (1) the SSE `tool_result` branch (~line 530), (2) the fan-out driving N per-section `materializePendingEdits` calls from one tool message (extends the single-section call at ~line 582/597), and (3) the render branch + `KNOWN_TOOL_CARD_TYPES` set (~line 35, ~line 912). The 14.3 ghost-isolation guard (`ghostContentLeakDetected`) is **per-section and stateless** — it will NOT false-positive on a correct fan-out because each section's edits only declare their own paragraph's `data-id` as anchor. The guard's real failure mode is D-09: two placeholders in one paragraph emitted as two competing `replace` edits on the same `paragraph_id`. Grouping-by-paragraph is mandatory, not optional.

Edge work is minimal: register `substituteePlaceholdersTool` in the `tools` array (`index.ts:72`), add a pass-through `case` in the dispatch switch (`index.ts:258`), and add tool-selection + bias-to-skip guidance to `buildSystemPrompt` (`context.ts:42-55`). The SSE emit at `index.ts:350` is already tool-agnostic. **Deno is unavailable and `supabase/**` is excluded from vitest** — edge changes get grep/static acceptance; all deterministic logic lives client-side where vitest (happy-dom) runs it.

**Primary recommendation:** Build the `after_html` rewriter as a pure module (`src/editor/placeholders/substitute.ts`) with three exported pure functions — `resolvePlaceholderTarget`, `groupTargetsByParagraph`, `buildSubstitutedParagraphHtml` — unit-tested in isolation; then wire the thin orchestration layer (fan-out + reconciliation + card) into `AIChatPanel.tsx`, reusing `materializePendingEdits` and `EditSummaryCard` unchanged.

### Pattern 1: Deterministic `after_html` via DOM string manipulation (RECOMMENDED)
**What:** Operate on the section's HTML string (`handle.getContent()` → `editor.getHTML()`), not on live PM nodes.
**Why over PM-node-walk:** (a) pure + unit-testable with no editor instance; (b) `getContent()` is already the authoritative serialized doc including `data-id` (UniqueID serializes `id`→`data-id`, `SectionEditorBlock.tsx:90`) and `data-placeholder-id`/`data-placeholder-label` (renderHTML `PlaceholderMark.ts:114-120`); (c) matches how existing `after_html` is consumed — on accept, replace does `deleteRange({from,to})` over the whole paragraph node then `insertContentAt(from, after_html)` (`SectionEditorBlock.tsx:186-189`), so `after_html` MUST be the full `<p data-id="…">…</p>` element.
**Deterministic recipe (pure):**
```ts
// Source pattern verified against PlaceholderMark.ts:114-129 + SectionEditorBlock.tsx:186-189
export function buildSubstitutedParagraphHtml(
  paragraphOuterHtml: string,   // e.g. '<p data-id="uuid">Name: <span data-placeholder-id="p1" data-placeholder-label="product name">product name</span>.</p>'
  placeholderIds: string[],     // all target spans in THIS paragraph (D-09)
  value: string,                // literal user-supplied value
): string {
  const doc = new DOMParser().parseFromString(paragraphOuterHtml, 'text/html')
  const para = doc.body.firstElementChild!            // the <p>/<li>/<td> block
  for (const id of placeholderIds) {
    const span = para.querySelector(`[data-placeholder-id="${CSS.escape(id)}"]`)
    if (!span) continue
    span.replaceWith(doc.createTextNode(value))       // strip mark (D-10) + insert literal
  }
  return para.outerHTML                               // preserves data-id anchor
}
```
- Placeholder value inserted as a plain text node → **span (mark) removed** so the analyzer walk (`SectionEditorBlock.tsx:310-316`) no longer reports it as an unresolved issue (D-10). The `aiApplied` transaction bypasses `resolutionPlugin` (`PlaceholderMark.ts:35`), so whatever `after_html` says is authoritative — no plugin re-strip needed, none available.
- `data-id` on the paragraph is preserved → `ghostContentLeakDetected` allows it (`id === edit.paragraph_id`, `decorations.tsx:27`).
- Byte-identical on repeat (pure function, no timestamps/UUIDs inside).

**Note on `CSS.escape` / `querySelector` in happy-dom:** verify `CSS.escape` availability in happy-dom; if absent, escape the attribute-selector value manually or iterate `querySelectorAll('[data-placeholder-id]')` and compare `getAttribute`. LOW risk, but write the test to pin it.

### Pattern 2: Fan-out one tool_result → N materializations (D-06 seam)
**What:** In the SSE branch, loop sections; call `handle.materializePendingEdits(bulkMsgId, sectionEdits)` per section with ONLY that section's edits.
**Why safe against the guard:** `ghostContentLeakDetected(editorHtml, pending)` (`decorations.tsx:21-32`) takes the CURRENT section's HTML and only that section's edits. A leak fires only when an edit's `after_html` declares a block `data-id` that (a) is not its own anchor and (b) already exists committed. A substitution `after_html` contains exactly one block whose `data-id` == `paragraph_id` == anchor → skipped by the guard's own-anchor exception. **No cross-section registry exists to false-positive** (comment at `decorations.tsx:7-10`). Use the SAME `bulkMsgId` for every section (SET_PENDING_EDITS is per `section_key`, `SectionWorkspaceContext.tsx:214`); give each edit a globally-unique `id` like `${bulkMsgId}-${section_key}-${i}`.

### Pattern 3: Reconciled outcome (D-15) — mirror the propose_edit inline-materialize
**What:** Follow the propose_edit precedent at `AIChatPanel.tsx:582-612`: build edits, call materialize inline, and on failure push a user-visible chat message (`formatEditApplyFailure`). For bulk, aggregate every section's `MaterializeResult.applied` plus per-target skip reasons into a reconciled structure stored on `toolData.state` (so counts survive reload, like `EditSummaryCard`'s persisted resolutions at `AIChatPanel.tsx:920`).

### Anti-Patterns to Avoid
- **One PendingEdit per placeholder** when two share a paragraph → two competing `replace` on one `paragraph_id`: the second overwrites/duplicates. MUST group (D-09).
- **Passing all sections' edits to one section's `materializePendingEdits`** — edits whose `paragraph_id` isn't in that section's doc get dropped (`SectionEditorBlock.tsx:397-410`) → silent under-application. Fan out per section.
- **Trusting the tool's proposed count for the card** — violates D-15; always count post-materialize.
- **Emitting `after_html` as bare inner text without the `<p data-id>` wrapper** — accept does a full-node `deleteRange`+`insertContentAt` (`:186-189`); a wrapperless fragment loses the anchor id and can merge nodes.
- **Generating substituted content on the edge** — violates D-01/D-03; the tool carries routing only.

## Detailed Findings (research questions)

### Finding 1 — Building `after_html` deterministically
- Placeholder mark serialization: `id`→`data-placeholder-id`, `label`→`data-placeholder-label` (`PlaceholderMark.ts:114-120`); rendered as `<span data-placeholder-id data-placeholder-label class="bg-amber-100 …">Label</span>` (`:129-137`), `spanning:true, inclusive:false` (`:107-108`).
- Existing `after_html` is applied by full-node replace: `deleteRange({from,to})` then `insertContentAt(from, after_html)` where `from/to` span the whole paragraph node (`SectionEditorBlock.tsx:167,186-189`). ⇒ **`after_html` must be the entire `<p data-id="…">…</p>`.**
- Recommended builder = Pattern 1 (DOM string manipulation on `handle.getContent()`). Confidence HIGH.

### Finding 2 — `materializePendingEdits` internals (`SectionEditorBlock.tsx:374-455`)
Signature: `(messageId: string, edits: PendingEdit[]) => MaterializeResult` (`workspace.ts:185`). Sequence: (1) editor-mounted check → `editor-not-mounted`; (2) section-active check → `section-not-active`; (3) idempotency (same edit ids already present → no-op ok); (4) per-edit anchor validation via `doc.descendants` on `node.attrs?.id === edit.paragraph_id`, keeping `collectFutureAnchorIds` chained anchors, dropping others (`:397-410`); (5) shape check (`id`, `operation`, `message_id`) (`:413-419`) → empty ⇒ `no-valid-edits`; (6) `computeAnchorHash` per edit (`:427-436`); (7) `ghostContentLeakDetected(editor.getHTML(), editsWithHash)` → `ghost-leak` (`:438-443`); (8) `workspaceDispatch(SET_PENDING_EDITS)` (`:445-448`); returns `{ok:true, applied}`.
**A clean synthetic replace `PendingEdit` must set:** `id` (unique), `paragraph_id` (existing block `data-id`), `section_key`, `operation:'replace'`, `before_html` (optional, current paragraph HTML — informational), `after_html` (full paragraph HTML, span filled+stripped), `change_summary:"filled <label> placeholder"`, `resolution:'pending'`, `message_id` (=bulkMsgId), `change_index` (per-paragraph order), `created_at`. `anchor_hash` is added by materialize; `anchorFrom/To` are runtime-only.

### Finding 3 — Fan-out seam + 14.3 guard (highest risk)
Guard lives in `decorations.tsx:21-32`, invoked inside `materializePendingEdits` (`:440`); keys on block `data-id`s in `after_html` vs committed `data-id`s in the section's own HTML, with the own-anchor exception (`:27`). Current single-section call site: `AIChatPanel.tsx:597` `editorRefs.current?.get(propPayload.section_key)?.materializePendingEdits(...)`. Drive N by looping `targets` grouped by `section_key`; per section build grouped edits and call materialize. Guard passes because each edit's only declared `data-id` is its own anchor. **Test explicitly** (SPEC + D-06): two sections, confirm each renders independent ghosts and neither trips `ghost-leak`.

### Finding 5 — Placeholder enumeration / location
`collectPlaceholderRanges` (`PlaceholderMark.ts:9-25`) walks `doc.nodesBetween` collecting mark ranges by id — server-of-truth for the *live editor*. The analyzer walk (`SectionEditorBlock.tsx:310-316`) collects `{id,label}` per unique placeholder into section issues. For the client fan-out, the simplest deterministic locate is a DOM walk of `handle.getContent()`: `querySelectorAll('[data-placeholder-id]')`, match by `data-placeholder-id` (id) and/or `data-placeholder-label` (label). Resolve to containing paragraph by walking up to the nearest ancestor carrying `data-id` (the block). Multiple-placeholders-in-one-paragraph = multiple matched spans whose nearest `data-id` ancestor is the same element → group (D-09). If a matched span has NO `data-id` ancestor, materialize can't anchor it → skip+report.

### Finding 6 — System prompt / tool description (`context.ts:16-62`)
`buildSystemPrompt` builds `toolNames` from the `tools` array (`:21`) and a "Tool selection guide" (`:42-47`) plus per-tool CRITICAL blocks (`:49-59`). Add: (a) a selection line for `substitute_placeholders` ("User supplies ONE literal value to drop into a named placeholder across one/several/all sections"); (b) bias-to-skip rule (D-12: "If unsure a single value satisfies a multi-part placeholder label, set decision:'skip' with a short skip_reason — never substitute"); (c) scoping rule (default = all sections containing a matching placeholder). **Reconcile with existing line `:55`** ("PRESERVE PLACEHOLDERS … never replace, inline, or remove them") — that instruction governs `propose_edit`; `substitute_placeholders` is the *sanctioned* path to fill them, so scope the preserve-rule to propose_edit and route fills to the new tool.

### Finding 7 — Honest reporting (R7)
- `propose_edit` today derives the chat bubble text from `event.result.overall_summary` (`AIChatPanel.tsx:569`) and pushes a failure chat message on non-ok materialize (`:604-611`, `formatEditApplyFailure`). For bulk, compose the one-liner CLIENT-side after reconciliation (D-15): full = "Substituted <value> in N sections."; partial = "Substituted in N sections, skipped M."; zero-match = "'<target>' isn't a fillable placeholder — nothing to substitute." (no card rendered, per SPEC "no empty panel").
- Zero-match detection: reconciled `applied === 0` AND every target skip reason is client-unresolvable/no-match (not a genuine model multi-part skip). In that case push only the chat message and suppress `BulkSubstitutionSummaryCard`. Partial/full render the card (skips enumerated via D-16) + the chat line.

## Common Pitfalls

### Pitfall 1: Same-paragraph edit collision
**What goes wrong:** Two placeholders in one paragraph → two `replace` edits, same `paragraph_id`. Batch accept re-resolves anchor each iteration (`SectionEditorBlock.tsx:164-168`); the second delete/insert operates on already-rewritten content → duplication or lost fill.
**Avoid:** `groupTargetsByParagraph` before building edits (D-09). **Warning sign:** duplicated value or dropped placeholder in the multi-placeholder fixture test.

### Pitfall 2: Placeholder span without a `data-id` ancestor
**What goes wrong:** UniqueID assigns `data-id` to block nodes, but a span inside an unexpected container (or a freshly split node) may resolve to a block missing `data-id`; materialize drops the edit silently (`:408`).
**Avoid:** Treat "no `data-id` ancestor" as a client skip with reason (D-04/D-05); count it in the aggregate, never drop.

### Pitfall 3: Attribute-selector escaping in happy-dom
**What goes wrong:** `querySelector('[data-placeholder-id="…"]')` with an id containing special chars, or `CSS.escape` unavailable in happy-dom, throws or mis-matches.
**Avoid:** Iterate `querySelectorAll('[data-placeholder-id]')` + compare `getAttribute`, or guard `CSS.escape`. Pin with a test.

### Pitfall 4: Reusing propose_edit's edit-id scheme across sections
**What goes wrong:** `${msgId}-${i}` (used at `AIChatPanel.tsx:585,930`) collides across sections when one bulk message fans out.
**Avoid:** Namespace by section: `${bulkMsgId}-${section_key}-${i}`.

### Pitfall 5: Card counts drift from reality on reload
**What goes wrong:** Rendering counts from the tool proposal (D-15 violation) shows "applied" for a target the client couldn't resolve.
**Avoid:** Persist the reconciled outcome on `toolData.state`; derive counts from live `workspaceState.sections[k].pending_edits` when present (mirror `AIChatPanel.tsx:924-927`).

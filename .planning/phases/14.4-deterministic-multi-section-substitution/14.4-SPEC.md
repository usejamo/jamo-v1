# Phase 14.4: Deterministic Multi-Section Substitution — Specification

**Created:** 2026-07-06
**Ambiguity score:** 0.14 (gate: ≤ 0.20)
**Requirements:** 7 locked

## Goal

When a user asks the chat to fill a placeholder across the proposal (e.g. "replace every section's Investigational product name placeholder with albacore"), the system deterministically locates every matching `data-placeholder-id` span across all in-scope sections and produces N per-section reviewable changesets in a single turn — substituting the literal supplied value into single-value placeholders, skipping-and-reporting multi-part/uncertain ones, and honestly reporting full-success, partial, and zero-match outcomes — with no LLM generation of edit content and no silent failures.

## Background

The chat-edit path is singular end-to-end. `propose_edit` takes one scalar `section_key` (`supabase/functions/chat-with-jamo/tools/propose-edit.ts:12`); the edge function is single-turn with no tool-result→continue loop (`index.ts:185`, dispatch at `258`); client materialization is keyed to one section via `editorRefs.current?.get(section_key)?.materializePendingEdits(...)` (`AIChatPanel.tsx:597`); review is one `EditSummaryCard` per section (`AIChatPanel.tsx:947`); and the server `active_task` is a single object scoped to one section (`index.ts:43-65`).

Live capture (isolated Anthropic repro + browser SSE tee) proved the model already fans out into N *correct* parallel `propose_edit` calls (`stop_reason=tool_use`, not truncation), but because the contract, the single-turn loop, the review UX, and `active_task` are all singular, ambiguous bulk requests deflect to `set_focus` (a dead end) or a clarifying question instead of editing.

Placeholders are inline TipTap marks with exactly two attributes — `id` ↔ `data-placeholder-id` and `label` ↔ `data-placeholder-label` (`PlaceholderMark.ts:110-122`). `label` is **free text**: there is **no data-model flag** distinguishing a single-value placeholder ("investigational product name") from a multi-part prompt ("Confirm name, mechanism of action, drug class, and regulatory precedent"). Placeholder spans are already enumerable (`collectPlaceholderRanges`, analyzer walk at `SectionEditorBlock.tsx:310-316`), so they are deterministically locatable by id/label — but classification of heterogeneity is not encoded anywhere.

Pending-edits state is already section-keyed (`sections: Record<section_key, { pending_edits: PendingEdit[] }>`, reducer at `SectionWorkspaceContext.tsx:207-225`), so the state *shape* can hold N sections' changesets concurrently — but every action carries exactly one `section_key` and there is no cross-section batch action. A known granularity gap: placeholders are inline span marks, whereas pending edits operate at paragraph/block granularity.

This phase builds on the already-shipped, deployed reliability fix-class (commit `3da0b40`: id-based ghost-isolation guard, `MaterializeResult` errors, error SSEs on `max_tokens`/parse-fail edge v17, buffered SSE parser, `set_focus` status line) so failures are visible, not silent.

## Requirements

1. **Deterministic intent-parse (classify, never generate)**: The chat turn parses a bulk-substitution request into a structured plan without generating edit content.
   - Current: The chat model emits free-form `propose_edit` tool calls or deflects to `set_focus`/a clarifying question; no structured intent-parse exists.
   - Target: A cheap intent-parse step extracts `{ value, scope, per-placeholder routing decision }` as structured output. The LLM classifies and routes only; it never produces the substituted content.
   - Acceptance: For "replace every section's X placeholder with Y", the parse yields the value `Y`, a scope covering all sections with a matching placeholder, and a substitute/skip decision per matched placeholder — verifiable from the structured output, with no model-generated edit HTML.

2. **Placeholder-span locate (span-only, by id/label)**: Matching targets are located deterministically by placeholder attributes.
   - Current: The only deterministic locator is `data-id` (paragraph) matching (`SectionEditorBlock.tsx:403`); placeholders travel inline in HTML and are not used as a locate key.
   - Target: A placeholder-id/label locator finds every matching `data-placeholder-id` span across the in-scope sections. Arbitrary literal text is never matched.
   - Acceptance: Given a proposal with a known placeholder in K sections, the locator returns exactly those K spans; a request naming a string that is not a placeholder returns zero matches (no fuzzy/text-search fallback).

3. **Deterministic literal substitution**: Single-value placeholders are filled with the literal supplied value.
   - Current: All edit content is model-generated via `propose_edit`.
   - Target: For each substitute-routed placeholder, the engine inserts the literal user-supplied value into the span deterministically — no LLM call produces the edit.
   - Acceptance: The proposed `after` content for every substitution equals the user-supplied value inserted into the placeholder span; running the same request twice yields byte-identical proposed substitutions.

4. **Heterogeneity routing with bias-to-skip**: Multi-part and uncertain placeholders are skipped and reported, not force-filled.
   - Current: No routing exists; a forced `propose_edit` rewrites the section (the 14.2.4 failure mode).
   - Target: Single-value placeholders → substitute; multi-part placeholders a single value can't satisfy → skip with a reason. On classifier uncertainty, default to **skip** (false-skip is safe; false-substitute inserts incoherent content).
   - Acceptance: A known multi-part placeholder (e.g. "Confirm name, mechanism of action, drug class, and regulatory precedent") is skipped with a reason and never receives the literal value; a plainly single-value placeholder is routed to substitute.

5. **Multi-section fan-out review**: Every affected section gets an independent, reviewable changeset in one turn.
   - Current: Materialization and review are keyed to one `section_key`; only one section can be reviewed per tool message.
   - Target: One bulk request produces per-section changesets for all affected sections, each with its existing ghost-decoration review (per-section accept/reject) intact.
   - Acceptance: A request matching placeholders in ≥2 sections renders reviewable ghost decorations in each of those sections; accepting/rejecting one section's changeset does not affect another's.

6. **Aggregate review control**: A cross-section summary enumerates and controls all changesets at once.
   - Current: One `EditSummaryCard` per section; no aggregate view and no cross-section batch action.
   - Target: An aggregate control lists all applied substitutions grouped by section AND all skipped items (section + placeholder label + reason), with accept-all / reject-all across every affected section.
   - Acceptance: The aggregate control shows every applied and skipped item; accept-all applies all substitutions across all sections in the run; reject-all discards all of them.

7. **Honest reporting of all three outcomes**: Full-success, partial, and zero-match each produce a visible, non-silent result.
   - Current: Ambiguous bulk requests dead-end silently or deflect; a non-placeholder target can regress to a blank bubble.
   - Target: The chat always emits a one-line summary ("substituted in N sections, skipped M"). A zero-match request (target is not a placeholder) returns a clear chat message stating it isn't a fillable placeholder — never a blank bubble and never an empty review panel.
   - Acceptance: Full-success shows all substitutions + a chat summary; partial shows both applied and skipped in the aggregate panel + a chat summary; zero-match shows a clear chat message and no empty panel.

## Boundaries

**In scope:**
- Chat natural-language entry → deterministic intent-parse (classify + route; extracts value, scope, per-placeholder decision)
- Deterministic locate of matching placeholder spans by `data-placeholder-id` / `data-placeholder-label` across all in-scope sections
- Deterministic literal substitution of single-value placeholders (no LLM produces edit content)
- Heterogeneity routing with bias-to-skip on uncertainty (single-value → substitute; multi-part/uncertain → skip + reason)
- Multi-section fan-out: N per-section reviewable changesets in a single turn, reusing the existing ghost-decoration / per-section accept-reject UX
- Aggregate review control: enumerated applied (per section) + skipped (section + label + reason), with accept-all / reject-all across sections
- Chat one-line summary on every run + an honest zero-match message when the target is not a placeholder
- Default scope = all sections containing a matching placeholder when the user does not name specific sections

**Out of scope:**
- A UI affordance / placeholder-panel "fill all" button — engine-first; the deterministic engine can power a UI entry point later if usage justifies it (Q1)
- Arbitrary literal-text find-and-replace on non-placeholder content — reintroduces the fuzzy/generative disambiguation this design exists to eliminate (Q2)
- Any LLM generation of edit content — violates the deterministic substitution principle (the LLM is limited to classification/routing)
- Auto-filling multi-part placeholders — they are skipped-and-reported, never force-filled (Q3 / R2)
- Ask-then-fill routing (Phase 14.2.4) — live capture proved it redundant here (the model already emits correct edits; the user already supplied the value)
- A brand-new dedicated multi-section review panel that replaces the per-section review UX — this phase reuses the proven per-section engine and adds an aggregate control on top (Q3)
- Adding a single/multi flag to the placeholder data model — classification happens at intent-parse time, not via a schema migration

## Constraints

- **Substitution must be deterministic**: no LLM call produces the substituted content; the LLM is limited to classification/routing output. Same input → byte-identical proposed substitutions.
- **Classifier biases to skip on uncertainty**: a false-skip (told to fill manually) is safe; a false-substitute (incoherent content) is harmful. Per-section ghost review is the backstop, but the classifier must not confidently force-fill.
- **Reuse existing per-section primitives**: ghost decorations, `SectionEditorHandle.materializePendingEdits(messageId, edits): MaterializeResult`, and the `SET_PENDING_EDITS` reducer. The pending-edits state is already `Record<section_key, { pending_edits }>` and can hold N sections; the new work is orchestration + the aggregate control, not replacing the per-section engine.
- **Granularity bridge (known gap)**: placeholders are inline marks (span granularity); pending edits are paragraph/block granularity. Substitution must bridge this (e.g. a paragraph-level change whose `after_html` carries the filled span). Flagged for discuss/plan — not solved in this spec.
- **Backward compatibility**: the existing single-section `propose_edit` path must remain unchanged and working.
- **No silent failures**: builds on commit `3da0b40`; every run resolves to a visible outcome (no blank bubbles, no empty panels, no silent no-ops).
- **Deployment/env (CLAUDE.md)**: edge functions must be deployed explicitly; only `VITE_`-prefixed env vars reach the client; secrets stay server-side; `supabase db push` fails here (migrations via Supabase MCP + a repo migration if any DB change is introduced).

## Acceptance Criteria

- [ ] A chat request "replace every section's `<placeholder-label>` with `<value>`" produces per-section reviewable changesets for every section containing a matching placeholder span, in a single turn.
- [ ] Each proposed substitution inserts the literal user-supplied value into the placeholder span — no model-generated content; the same request run twice yields byte-identical proposed substitutions.
- [ ] Placeholders classified multi-part or uncertain are skipped (never force-filled); each skip is reported with section + placeholder label + reason.
- [ ] On a known multi-part placeholder the classifier skips-and-reports rather than substituting (bias-to-skip verified).
- [ ] The aggregate review control lists all applied substitutions grouped by section AND all skipped items (section + label + reason).
- [ ] Aggregate accept-all applies every proposed substitution across all affected sections; reject-all discards all of them.
- [ ] Per-section accept/reject continues to work independently (existing ghost-decoration review) for each fanned-out changeset.
- [ ] A request whose target is not a placeholder span (e.g. "replace any CRO name with Labcorp" with no matching placeholder) returns a clear chat message that it isn't a fillable placeholder — never a blank bubble and never an empty review panel.
- [ ] A partial run (some substituted, some skipped) shows both in the aggregate panel AND emits a one-line chat summary ("substituted in N sections, skipped M").
- [ ] Full-success, partial, and zero-match outcomes each produce a visible, non-silent result.
- [ ] Non-placeholder (arbitrary literal-text) find-and-replace is NOT performed — confirmed by no substitution on non-placeholder text.
- [ ] The existing single-section `propose_edit` path is unchanged and still works.

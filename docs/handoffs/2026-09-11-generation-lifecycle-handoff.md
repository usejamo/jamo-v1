## 2. What the assessment found (verified by reading the code, 2026-09-11)

Proposal sections are generated by `src/hooks/useProposalGeneration.ts`. `generateAll` (~line 458)
runs a sequential loop over every section:

```ts
const sections = sectionRows.map(row => ({ ...row, status: 'pending' }))   // ~line 505
dispatch({ type: 'START_GENERATION', sections })                            // ~line 515

const completedSections = []
let anchor = ''
for (const section of sections) {
  const rag = await fetchRagChunks(...)
  const content = await streamSection(section, desc, completedSections, anchor, ctx, rag, isDebug, signal)
  if (abortController.signal.aborted) break
  if (content) {
    completedSections.push({ id, name, content })
    const newAnchor = await extractAnchor(content, session)   // rolling, re-derived EVERY section
    if (newAnchor) anchor = newAnchor
    dispatch({ type: 'SET_ANCHOR', anchor })
  }
}
```

`stopGeneration` (~line 631) is only:
```ts
abortControllerRef.current?.abort()
dispatch({ type: 'GENERATION_COMPLETE' })
```

**So re-calling `generateAll` is NOT a resume.** It would (a) reset every section to `pending` via
`START_GENERATION`, discarding completed state, (b) loop over ALL sections with no skip, (c)
regenerate and OVERWRITE sections already written to the DB, (d) spend the tokens again. A naive
Stop→Resume button swap would silently destroy the user's completed work — worse than no button.

**Two pieces of accumulating state do not survive a stop:**

| state | what it is | how to recover |
|---|---|---|
| `completedSections` | content of all prior sections, passed to each generation for continuity | easy — read `proposal_sections.content` where status complete; the hook already hydrates these on mount |
| `anchor` | rolling consistency string, re-derived by `extractAnchor()` after every section | one `extractAnchor` call on the last completed section, OR persist it as generation proceeds |

Rough size: ~100–150 lines plus tests. Tractable, but a generation-lifecycle change, not a button swap.

## 3. Why #9 and #12 are one piece of work

Both need the same machinery: **"where did we get to, and how do we pick up from there"**.

- #9 = pick up after a deliberate stop, same tab.
- #12 = pick up after the client went away (navigation, refresh, tab close).

If #9 is built client-side only, #12 will require rebuilding it server-side and #9's work is thrown
away. Decide the architecture ONCE, up front. Specifically decide whether generation stays
client-driven (the loop lives in the browser; #12 becomes "rehydrate and continue on return") or
moves server-side (an edge function or job owns the loop; the client subscribes). The todo for #12
guesses server-side. That is a real fork with real cost — worth a `superpowers:brainstorming` pass
before any code, and worth raising with Aaron rather than assuming.

## 5. Things this session learned the hard way — read before you start

- **Edge functions are NOT deployed by committing.** `npx supabase functions deploy <name> --project-ref fuuvdcvbliijffogjnwg`, with `SUPABASE_ACCESS_TOKEN` taken from `.env`. A frontend-only change needs no deploy; anything under `supabase/functions/` does.
- **`.env` must contain only `KEY=VALUE` lines.** A bare pasted command in there breaks EVERY supabase CLI invocation with a confusing "failed to parse environment file" error at config load. This bit us today.
- **Migrations: `supabase db push` does not work here** (history diverged). Apply SQL via the Management API: `POST https://api.supabase.com/v1/projects/fuuvdcvbliijffogjnwg/database/query` with the `sbp_` token. That endpoint also runs DDL, and `pg_get_functiondef` there is the authoritative source for what is actually live — the migration files have drifted from prod.
- **Verify in the real browser, not just jsdom.** jsdom has no layout engine. Two bugs today (button drift, clipped popover) were only provable by measuring `getBoundingClientRect` in Playwright. Dev server: `npm run dev` (port varies, read it from the log), login `usera@jamo.com` / `password123`. Note a different port is a different origin, so the session does not carry over.
- **Baselines:** `npx vitest run` → 625 passed / 16 skipped. `npx tsc --noEmit` → **303 pre-existing errors**; that is the baseline, not a regression. Compare counts before and after, and check your own files are clean rather than chasing the 303.
- **Don't trust the todo's stated cause.** Todo #6 blamed the proposal-list container; the actual clipper was the app shell's scroll area. Todo #5 named one bug and there were two. Reproduce and measure before designing the fix.
